# CloudFlow Pro OA 转型实施路线图 (Roadmap)

基于《OA 转型评估分析报告》，为确保系统从垂直 BPM 工具平稳过渡到综合性 OA 协同平台，特制定以下三阶段演进计划。

## 📅 阶段一：协作基石 - 任务管理模块 (Task Management)
**核心目标**：补齐“非流程化”工作管理能力，建立全员协作基础，提升系统日活 (DAU)。

*   **预计周期**：第 1 - 2 周
*   **实施范围**：
    *   **后端 (Backend)**：
        *   **数据模型**：新建 `WorkTask` 实体。
            *   字段：`id`, `title`, `description`, `assignee_id`, `due_date`, `priority` (P0-P2), `status` (TODO/DOING/DONE), `tags`.
            *   区别：与 `WfTask` 物理隔离，不绑定流程实例 `instanceId`。
        *   **接口**：CRUD 接口，状态变更接口，分配接口。
    *   **前端 (Frontend)**：
        *   **我的待办**：升级现有任务列表，聚合显示“流程任务”和“普通任务”。
        *   **看板视图 (Kanban)**：新增看板组件，支持拖拽变更任务状态。
        *   **快速创建**：支持在任意页面快速创建个人待办。
*   **关键交付物**：
    *   混合任务列表 (Unified Task List)
    *   项目协作看板 (Project Kanban)

## 📢 阶段二：信息枢纽 - 公告通知模块 (Announcement)
**核心目标**：建立企业信息分发中心，增强行政管理属性，实现信息的有效触达。

*   **预计周期**：第 3 周
*   **实施范围**：
    *   **后端 (Backend)**：
        *   **数据模型**：改造 `SysNotice` 或新建 `SysAnnouncement`。
            *   支持富文本内容 (`content_html`)。
            *   支持附件 (`attachments`)。
        *   **广播策略**：支持按部门 (`dept_id`)、全员 (`all`)、角色 (`role_id`) 发送。
        *   **阅读追踪**：记录已读人员列表，统计触达率。
    *   **前端 (Frontend)**：
        *   **富文本编辑器**：集成 Quill 或 TinyMCE。
        *   **公告中心**：支持公告置顶、分类显示。
        *   **强提醒**：实现“强制弹窗”通知（针对紧急公告）。
*   **关键交付物**：
    *   企业公告发布后台 (Admin Portal)
    *   员工通知中心 (User Notification Center)

## 🗓️ 阶段三：时间引擎 - 日程管理模块 (Schedule)
**核心目标**：引入时间维度，实现个人时间规划与团队资源管理。

*   **预计周期**：第 4 周
*   **实施范围**：
    *   **后端 (Backend)**：
        *   **数据模型**：
            *   `SysEvent`：日程实体（主题、起止时间、地点、参与人、提醒策略）。
            *   `MeetingRoom`：会议室资源实体。
        *   **算法**：会议室预订冲突检测，重复日程生成规则。
    *   **前端 (Frontend)**：
        *   **日历组件**：引入 FullCalendar 或类似库。
        *   **视图切换**：支持 日/周/月 视图。
        *   **预订系统**：会议室占用情况可视化展示及预订表单。
*   **关键交付物**：
    *   个人/团队日历 (Calendar)
    *   会议室预订系统 (Meeting Room Booking)

## 🛡️ 风险管理与应对
1.  **用户体验割裂风险**
    *   *描述*：流程任务与普通任务操作逻辑不一致导致困惑。
    *   *应对*：在前端 UI 层面进行深度统一，尽量抹平底层模型的差异，提供一致的操作反馈。
2.  **性能风险**
    *   *描述*：全员广播和即时通讯可能导致 WebSocket 服务压力过大。
    *   *应对*：
        *   引入 Redis Stream 消息队列进行削峰填谷。
        *   对 WebSocket 推送进行分批处理 (Batch Processing)。
3.  **数据迁移风险**
    *   *描述*：现有 `SysNotice` 数据结构不兼容新版。
    *   *应对*：编写平滑迁移脚本，保留旧数据，或在新表中通过 `version` 字段兼容。
