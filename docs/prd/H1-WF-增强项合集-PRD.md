# WF-11 草稿保存

## 1. 背景
表单填一半退出即丢失。用户填 30 字段的采购申请时如果被打断，全部重填。

对标 flowlong 的 `TaskType.saveAsDraft=25`（NOASSERTION，仅借鉴概念）：草稿作为一种状态存在，不产生正式实例，复用同一套表单数据结构。

## 2. 现状
| 项 | 现状 |
| --- | --- |
| 草稿 | **无** |
| 表单数据 | 提交时才落库 |
| 实例状态 | 批次 B 的 B2 已在 14 态中**预留 `DRAFT`** |

## 3. 功能需求
- FR-1 新增 `wf_form_draft`：`draft_id, tenant_id, definition_id, definition_name, form_id, user_id, title, form_data(JSON), node_assignees(JSON，发起人自选审批人), attachment_url, last_save_time, expire_time` + 审计列
  - 唯一索引 `uk_user_def(tenant_id, user_id, definition_id)`（一用户一流程一草稿，新草稿覆盖旧的）
- FR-2 保存草稿：`POST /wf/draft`，手工保存 + **自动保存**（前端每 30 秒或字段变更后 5 秒防抖）
- FR-3 草稿列表：`GET /wf/draft/list`（我的草稿）
- FR-4 从草稿发起：`POST /wf/start` 增 `draftId` 入参，发起成功后删除草稿
- FR-5 草稿过期清理：默认 30 天未更新自动删除（批次 A SYS-02 纳管）
- FR-6 前端：发起页检测到已有草稿时提示"是否恢复上次填写内容"

## 4. 验收标准
| # | 验收项 |
| --- | --- |
| AC-1 | 手工保存草稿成功；再次进入发起页提示恢复 |
| AC-2 | 自动保存生效（30 秒周期或字段变更防抖） |
| AC-3 | 同一用户同一流程重复保存覆盖旧草稿（不堆积） |
| AC-4 | 从草稿发起成功后草稿被删除 |
| AC-5 | 草稿含子表数据（批次 C LC-03）与发起人自选审批人（批次 B WF-03）时正确恢复 |
| AC-6 | 30 天未更新的草稿被自动清理 |
| AC-7 | 用户只能看自己的草稿 |

## 5. 依赖与风险
- 依赖：批次 C（表单结构，草稿要存新的树形结构含子表）、批次 A SYS-02（清理任务）
- 风险：自动保存频繁写库 → 用防抖 + 只在有变更时保存；草稿数据体积（含子表）→ 与表单数据同量级，可接受

# WF-09 代理人四态模型

## 1. 背景

**"委派"与"代理"是两回事**：
- 委派（delegate）：把任务交出去，处理结果归**受委派人**
- 代理（agent）：代表某人处理，处理结果仍归属**被代理人**

对标 flowlong 的 `agent=13 / agentReturn=14 / agentAssist=15 / agentOwn=16` 四态（NOASSERTION，仅借鉴概念）。

**关键发现**：`wf_task.proxy_user_id` 字段**已存在**（实测），说明设计时考虑过代理，但 `wf_task_delegation.delegation_type` 把委派与代理混用，无归还与协办语义。

## 2. 现状
| 项 | 现状 |
| --- | --- |
| `wf_task.proxy_user_id` | **字段已存在**，语义未落实 |
| `wf_task_delegation` | 13 列：`from_user_id, to_user_id, delegation_type, reason, status`（委派与代理混用） |
| 委派接口 | `POST /enhance/task/delegate` |
| `task_type` | 批次 B B1 已加，含 `DELEGATE` / `DELEGATE_RETURN` |

## 3. 功能需求
- FR-1 `wf_task_delegation` 增 `agent_mode`：
  | 取值 | 语义 | 结果归属 |
  | --- | --- | --- |
  | `DELEGATE` | 委派（现状） | 受委派人 |
  | `AGENT` | 代理（代某人处理） | 被代理人 |
  | `AGENT_ASSIST` | 协办（协助处理，不能最终决定） | 被代理人 |
- FR-2 代理设置：用户可设置"我的代理人"（如休假期间），可设时间范围与流程范围
  - 新增 `wf_agent_setting`：`setting_id, tenant_id, principal_user_id(被代理人), agent_user_id(代理人), agent_mode, definition_ids(JSON，限定流程，空表示全部), start_time, end_time, reason, status` + 审计列
- FR-3 任务分派时检测被代理人是否有生效代理设置，有则同时分派给代理人（`wf_task.proxy_user_id` 记代理人）
- FR-4 代理人处理时：审批结果记录中 `operator_id` 为代理人，但**业务归属仍为被代理人**（`wf_task_history` 增 `on_behalf_of_user_id`）
- FR-5 代理归还：`POST /enhance/task/agent-return`，代理人可把任务交还被代理人，`task_type=DELEGATE_RETURN`
- FR-6 协办：`AGENT_ASSIST` 时代理人可填意见但不能最终通过/驳回（意见记入历史供被代理人参考）
- FR-7 流程轨迹显示"张三（代李四审批）"

## 4. 验收标准
| # | 验收项 |
| --- | --- |
| AC-8 | 三种 `agent_mode` 行为正确区分 |
| AC-9 | 代理设置在时间范围内生效，范围外不生效 |
| AC-10 | 代理设置可限定流程范围 |
| AC-11 | 代理人处理后，`operator_id` 为代理人、`on_behalf_of_user_id` 为被代理人 |
| AC-12 | **业务归属统计（如绩效、工作量）按被代理人计** |
| AC-13 | 代理归还后任务回到被代理人待办 |
| AC-14 | `AGENT_ASSIST` 时代理人无法最终通过/驳回，只能填意见 |
| AC-15 | 流程轨迹正确显示"X（代 Y 审批）" |
| AC-16 | 回归：现有委派行为不变 |

## 5. 依赖与风险
- 依赖：批次 B B1（`task_type`）
- 风险：**代理审批的合规性** —— 某些高敏审批（如薪资、大额付款）不应允许代理。建议节点配置增 `allowAgent` 开关（复用批次 B B1 的节点级开关模式）；审计必须记录代理关系

# WF-10 包含网关与路由分支

## 1. 背景

现状有并行网关（`wf_parallel_join` 表已实现汇聚），缺两类：
- **包含网关（inclusive）**：满足条件的分支才走，且需等齐（并行是全部都走）
- **路由分支（route）**：命中即跳走，不回来

对标 warm-flow 的 `NodeType.INCLUSIVE=5`（Apache-2.0，**可直接参照实现**）与 flowlong 的 `inclusiveNodes` / `routeNodes`。

## 2. 现状
| 项 | 现状 |
| --- | --- |
| 节点类型 | 前端 `NodeType` 有 `CONDITION`（排他）/ `PARALLEL`（并行） |
| 并行汇聚 | `wf_parallel_join` **已实现** |
| 包含网关 | 无 |
| 路由分支 | 无 |
| 节点配置 | `WfNodeConfig.branchStrategy`（PARALLEL / EXCLUSIVE） |

## 3. 功能需求
- FR-1 `NodeType` 增 `INCLUSIVE`（包含网关）与 `ROUTE`（路由分支）
- FR-2 `WfNodeConfig.branchStrategy` 增取值 `INCLUSIVE` / `ROUTE`
- FR-3 包含网关执行：
  1. 逐分支求值条件，满足的分支全部激活
  2. 汇聚时**只等已激活的分支**（动态计算应到数，这是与并行网关的关键差异）
  3. 无分支满足时按 `defaultBranch` 走默认分支，无默认分支则报错
- FR-4 `wf_parallel_join` 扩展为通用汇聚表：增 `join_type(PARALLEL/INCLUSIVE)` 与 `expected_count`（动态应到数）
- FR-5 路由分支执行：命中条件即跳转到目标节点，**不产生汇聚等待**
- FR-6 设计器支持两种新网关的绘制与条件配置
- FR-7 流程图渲染区分四种网关形态

## 4. 验收标准
| # | 验收项 |
| --- | --- |
| AC-17 | 包含网关：3 个分支中 2 个条件满足时，只激活 2 个分支 |
| AC-18 | **包含网关汇聚只等已激活分支**（2 个分支完成即汇聚，不等第 3 个） |
| AC-19 | 无分支满足时走默认分支；无默认分支时报错并告警 |
| AC-20 | 路由分支命中后跳转且不产生汇聚等待 |
| AC-21 | 设计器可绘制并配置两种新网关 |
| AC-22 | 流程图正确区分排他/并行/包含/路由四种形态 |
| AC-23 | 回归：现有并行网关行为不变 |

## 5. 依赖与风险
- 依赖：批次 B B1/B2（节点配置扩展、状态机）
- 风险：
  - **汇聚逻辑是流程引擎最易出错的部分**：包含网关的动态应到数计算错误会导致流程卡死或提前流转。需充分测试边界（0 个分支满足、全部满足、部分满足后某分支被驳回）
  - `wf_parallel_join` 改造影响现有并行流程 → AC-23 回归
  - 实际业务用到包含网关的频率低 → **建议确认有真实场景再做**
