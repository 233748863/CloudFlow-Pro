| 项 | 内容 |
| --- | --- |
| 条目编号 | LC-03 |
| 所属批次 | 批次 C（第 2 份，依赖 C1 的树形结构） |
| 对标依据 | `docs/benchmark/06-lowcode-bi-表单报表对标.md` |
| 优先级 | P1 |
| 预估工作量 | M |
| 版本 | v1 · 2026-08-31 |

## 1. 背景与目标

### 1.1 问题

后端**已大量存在"主表 + 明细表"结构**，但这些明细全靠专用页面写死，走工作流表单时无法动态配置：

| 主表 | 明细表 |
| --- | --- |
| `biz_expense_claim` | `biz_expense_item` |
| `biz_purchase_request` | `biz_purchase_item` |
| `crm_quote` | `crm_quote_line`（22 列） |
| `oa_budget_plan` | `oa_budget_line` |

这意味着：用工作流表单发起一张报销单，**填不了多行费用明细**。子表是企业单据的基本形态（ERPNext 里几乎每张单据都靠子表），当前完全缺失。

### 1.2 目标
1. 新增 `SUB_TABLE` 字段类型，支持行内增删改
2. 支持列合计（报销总额、采购总价这类必需能力）
3. 移动端降级为卡片列表式编辑
4. 服务端递归校验子表数据

### 1.3 非目标
- 不做子表与后端明细表的自动映射（表单数据仍存 JSON，业务落库由各业务模块负责）
- 不做跨行计算（只做列合计）
- 不做子表分页（行数上限内一次渲染）

## 2. 现状基线

| 项 | 现状 |
| --- | --- |
| 字段类型 | C1 交付后 22 种，**无子表** |
| 结构 | C1 交付后为树形（`children`） |
| 可复用 | `react-window` 2.2.6（虚拟列表，行数多时用）、`table.tsx` / `table-row-actions.tsx`（已有表格组件）、`AmountInput`、`VirtualList` |
| 后端 | `wf_form_definition.fields_json`，C1 已建服务端 schema 校验器 |

## 3. 范围

### 3.1 做
1. `SUB_TABLE` 字段类型 + 列定义（列本身是 `FormField`）
2. 行内编辑表格渲染（增行、删行、行复制、行排序）
3. 列合计（`summaryColumns`）
4. 移动端卡片式编辑
5. 服务端子表校验（递归到列）
6. 设计器的子表列配置面板

### 3.2 不做
| 项 | 原因 |
| --- | --- |
| 子表落库映射 | 表单数据存 JSON，业务落库由业务模块处理；自动映射需要表元数据绑定，超出表单引擎职责 |
| 子表嵌套子表 | 二级子表实际业务少见，复杂度高 |
| 跨行公式 | 只做列合计（SUM/COUNT/AVG） |
| 子表分页 | 行数上限（默认 100）内一次渲染，超限用虚拟滚动 |

## 4. 功能需求

### FR-1 字段定义
- FR-1.1 `SUB_TABLE` 字段配置：
  ```
  columns: FormField[]        列定义，每列是一个 FormField
  minRows, maxRows            行数限制（默认 0 / 100）
  allowAdd, allowDelete       增删开关
  allowSort                   行排序开关
  allowCopyRow                行复制开关
  summaryColumns: [{ columnId, aggregation }]   合计列，aggregation: SUM|COUNT|AVG
  emptyText                   空态文案
  ```
- FR-1.2 列可用的字段类型（子集，排除不适合表格的）：
  `TEXT` / `NUMBER` / `AMOUNT` / `DATE` / `SELECT` / `DICT_SELECT` / `SWITCH` / `EMPLOYEE` / `DEPT` / `UPLOAD_FILE`
  **排除**：`TEXTAREA` / `RICH_TEXT` / `SUB_TABLE` / 布局容器 / `DESCRIPTION` / `DIVIDER`
- FR-1.3 列支持 `width`、`required`、`readonly`、`defaultValue`

### FR-2 Web 渲染
- FR-2.1 表格形态：表头为列名（必填列带 `*`），每行为一条数据，行末为操作列
- FR-2.2 行内编辑：单元格直接编辑，复用 C1 的字段渲染器
- FR-2.3 操作：新增行（底部按钮）、删除行、复制行、拖拽排序（`@dnd-kit` 已有）
- FR-2.4 合计行：固定在表格底部，按 `summaryColumns` 计算
- FR-2.5 行数超过 30 时启用虚拟滚动（`react-window` 已在依赖）
- FR-2.6 行级校验错误在对应单元格标红并提示
- FR-2.7 空态显示 `emptyText` + 新增按钮

### FR-3 移动端渲染
- FR-3.1 降级为**卡片列表**：每行渲染为一张卡片，卡片内字段纵向排列
- FR-3.2 卡片右上角操作菜单（删除 / 复制）
- FR-3.3 底部固定"新增一条"按钮与合计条
- FR-3.4 不支持拖拽排序（移动端交互成本高），改为上移/下移按钮

### FR-4 数据结构与提交
- FR-4.1 提交值为数组：`{ subTableFieldId: [ {colId: value, ...}, ... ] }`
- FR-4.2 每行带内部 `_rowId`（前端生成，用于 React key 与错误定位，提交时可保留）
- FR-4.3 服务端校验（扩展 C1 的校验器）：
  - 行数在 `minRows` / `maxRows` 之间
  - 每行每列按列定义递归校验
  - 列值不在 `options` 内则拒绝
  - **子表内未声明的列一律拒绝**
- FR-4.4 校验错误返回定位到行与列：`{fieldId: {rowIndex: {colId: errorMsg}}}`

### FR-5 设计器
- FR-5.1 拖入 `SUB_TABLE` 后，在属性面板配置列（列表可增删排序，每列可设类型与属性）
- FR-5.2 列配置复用 C1 的字段属性面板（限定为 FR-1.2 的类型子集）
- FR-5.3 配置 `summaryColumns` 时只能选数值类列（`NUMBER` / `AMOUNT`）
- FR-5.4 预览模式可试填子表数据
- FR-5.5 保存校验：至少 1 列、列 id 唯一、合计列必须是数值类型

## 5. 非功能需求

| 项 | 要求 |
| --- | --- |
| 服务端校验 | 必须递归到列（FR-4.3）；行数与列值都校验 |
| 性能 | 100 行 × 8 列渲染 < 500ms；超 30 行启用虚拟滚动；单元格编辑不触发整表重渲（行级 `React.memo`） |
| 合计精度 | `AMOUNT` 列合计用高精度计算，避免浮点误差 |
| 移动端 | 卡片式；触控目标 ≥ 44px |
| 无障碍 | 表格用 `<table>` 语义（非 div 模拟）；表头 `<th scope="col">`；操作按钮有 `aria-label` |
| 数据量 | `maxRows` 上限保护（默认 100，可配但硬上限 500），防单条表单数据过大 |

## 6. 验收标准

| # | 验收项 |
| --- | --- |
| AC-1 | 子表可增行、删行、复制行、拖拽排序；行内编辑正确取值 |
| AC-2 | FR-1.2 的 10 种列类型均可用；被排除的类型在设计器中不可选 |
| AC-3 | 合计列正确计算（SUM / COUNT / AVG）；`AMOUNT` 合计无浮点误差 |
| AC-4 | 行数低于 `minRows` 或超过 `maxRows` 时提交被拒绝 |
| AC-5 | **服务端递归校验：行内必填缺失、列值超范围、选项外的值、未声明的列全部被拒绝** |
| AC-6 | 校验错误定位到具体行与列，前端在对应单元格标红 |
| AC-7 | 移动端降级为卡片列表，可增删与上移下移，合计条正确显示 |
| AC-8 | 100 行 × 8 列渲染 < 500ms；超 30 行启用虚拟滚动 |
| AC-9 | 单元格编辑时不触发整表重渲（React DevTools 验证） |
| AC-10 | 设计器可配置列与合计列；合计列只能选数值类型 |
| AC-11 | 用子表配一张报销单（费用明细多行 + 金额合计），端到端可发起与审批 |
| AC-12 | 无障碍：表格用 `<table>` 语义，表头有 scope，操作按钮有 aria-label |

## 7. 依赖与风险

### 7.1 依赖
| 依赖 | 说明 |
| --- | --- |
| **C1（字段类型与布局）** | 树形结构、字段渲染器、服务端校验器基础 |
| `react-window` 2.2.6（已有） | 虚拟滚动 |
| `@dnd-kit/sortable`（已有） | 行排序 |
| `table.tsx` / `AmountInput`（已有） | 表格与金额组件 |

### 7.2 风险

| 风险 | 应对 |
| --- | --- |
| 行内编辑 + 虚拟滚动组合易出焦点丢失、滚动跳动问题 | 30 行以下不用虚拟滚动（覆盖多数场景）；超 30 行时仔细处理焦点保持；AC-8/9 验证 |
| 表单数据体积膨胀（100 行 × 8 列 JSON） | `maxRows` 硬上限 500（NFR）；`wf_form_definition` 存定义不存数据，数据在实例侧需评估字段长度 |
| 移动端卡片式与 Web 表格式差异大，用户认知不一致 | 属于必要降级；卡片内字段顺序与表格列顺序一致 |
| 服务端校验器复杂度（三层递归：容器→子表→列） | 复用 C1 的校验器架构，子表作为一种特殊字段类型接入 |
| 业务落库仍需各模块自己处理，可能出现"表单能填但业务存不了" | §3.2 已明确不做自动映射；需在业务侧对接时约定数据格式（见 §9-1） |

## 9. 待确认

| # | 问题 | 建议默认 |
| --- | --- | --- |
| 1 | 子表数据如何落到业务明细表（如 `biz_expense_item`） | 建议约定：业务侧在流程完成事件里解析表单 JSON 的子表数组并落库。表单引擎只负责收集与校验，不做映射。需在对接首个业务（建议报销）时定下数据格式契约 |
| 2 | 是否需要子表行级审批（某行单独审） | 建议不做，无此类需求且会大幅增加复杂度 |
| 3 | `maxRows` 默认值 | 建议 100（报销/采购明细通常 < 20 行），硬上限 500 |
| 4 | 子表列是否支持 `UPLOAD_FILE` | 建议支持但限 `maxCount=1`（每行一个附件，如每笔费用一张发票），多附件场景用主表附件字段 |
