## 1. 四处必须修正 PRD 的发现

### 修正一：现有架构已经是 outbox 事件流，不是"跨服务读表"

**PRD 原判断**（§2.1 第 3 条 + §3.2 第 1 条）：
> "命名混乱：OA 服务的 `SysNotice` 实体 `@TableName("wf_notice")`，OA 读工作流的表，跨服务表耦合"

**实测的真实链路**：
```
workflow 侧 SysNoticeServiceImpl
  → 不写库，构造 SystemNoticeDispatchEvent
  → OutboxPublisher.publish(BusinessEventEnvelope{eventType="SYSTEM_NOTICE_DISPATCH"})
       ↓ outbox_event 表
OA 侧 SystemNoticeDispatchEventConsumer（实现 BusinessEventConsumer）
  → 调 OA 的 ISysNoticeService.sendNotice()
  → OA 的 SysNoticeServiceImpl 写 wf_notice
```

**所以**：
- **不存在跨服务直接读写同一张表**。workflow 只发事件，OA 独占该表的读写
- 真实问题只是**表名前缀错了**（表由 OA 拥有，却叫 `wf_` 前缀），属命名问题不是耦合问题
- **现有链路已经是 A2 目标架构的形态**（SDK 写 outbox → 统一消费 → 落库），比 PRD 假设的完整得多
- 影响：A2 的收口不是"解耦"而是"改表名 + 统一模型"，风险显著低于 PRD 预估

### 修正二：workflow 与 OA **各有一套** `ISysNoticeService`，职责不同

| 服务 | 接口方法 | 职责 |
| --- | --- | --- |
| workflow `ISysNoticeService` | 只有 `sendNotice()` 一个方法 | **只发不读**（发事件到 outbox） |
| OA `ISysNoticeService` | `sendNotice()` / `getMyNotices()` / `readNotice()` / `getUnreadCount()` / `getNoticeById()` / `deleteNotice()` 六个方法 | **落库 + 查询 + 已读**（表的实际拥有者） |

PRD 未区分这两套，改造时**必须分别处理**：
- workflow 侧：`sendNotice()` 改为调 `cloudflow-common-message` SDK（写 `outbox_event`，`aggregate_type='MESSAGE'`），接口可保留或直接下线
- OA 侧：六个方法全部收口到新的 `sys_message_record` 模型

### 修正三：`NotificationConfigDTO` 与 `wf_notification_config` **完全无关**，不在收口范围

**PRD 原判断**（AC-10D）：
> "workflow 的通知发送与配置管理改由新模型承载，`NotificationConfigDTO` 相关逻辑已迁移"

**实测**：

| 对象 | 字段 | 服务的表 | 用途 |
| --- | --- | --- | --- |
| `NotificationConfigDTO` | `notificationType, recipientType, recipientIds, notificationTitle, notificationContent` | **`wf_deploy_notification`**（独立表，在 `02` 脚本中存在） | **流程发布通知**（`DeployEnhancementController` 的 `/deploy/notification/*` 接口） |
| `WfNotificationConfig` | `configId, eventType, notifyChannel, templateId, recipientType, recipientValue, enabled` | `wf_notification_config` | 通知规则配置 |

**结论**：`NotificationConfigDTO` 服务于发布通知（`wf_deploy_notification` 表不在删除清单内），**不属于本次收口范围**。AC-10D 的措辞需修正，否则会误导开发去改发布通知功能。

### 修正四：前端铃铛收口**已经完成**，AC-12 已满足

**PRD 原判断**（§3.2 第 7 条 + AC-12）：
> "前端 3 个铃铛：`AnnouncementBell` / `NoticeBell` / `UnifiedMessageBell` 收口到 `UnifiedMessageBell` 单一入口，前两个下线"

**实测**：
- `MainLayout.tsx:573` 只用 `<HeaderAnnouncementBell />`
- `HeaderAnnouncementBell.tsx` 源码注释写明"**兼容层：保留旧组件路径和入参，内部切到统一消息铃铛**"，内部直接渲染 `<UnifiedMessageBell>`
- `AnnouncementBell` 与 `NoticeBell` **仅在 `components/common/index.ts` 导出，无任何实际使用点**

**结论**：收口已完成。本期只需**删除两个未使用组件与其 index 导出**（纯清理，零风险）。AC-12 实际已满足。

## 4. 修正后的工作量评估

| 改造对象 | 数量 | PRD 原估 | 实测 |
| --- | --- | --- | --- |
| 需改调用方的业务类 | **21 个**（OA 9 + workflow 12） | 未量化 | **这是主要工作量**，每个都要把 `sendNotice()` 改为 SDK 调用 |
| 需删除的实体/Mapper | 8 个 | 4 表 | 相符 |
| 需收口的 Controller | 3 个（`SysNoticeController`、`InnerNoticeController`、`HrEssPortalController` 部分） | 未量化 | — |

- **风险低于 PRD 预估**（无跨服务表耦合，现有链路已是 outbox 形态）

## 6. 建议的收口执行顺序

按"**先建新模型，再按服务逐个切换，最后删表**"推进，每步可独立验证：

| 步骤 | 动作 | 验证点 |
| --- | --- | --- |
| S1 | 建 5 张新表 + SDK + auth 消费者 + 站内渠道（PRD 的 M1-M2） | 新消息可发可查 |
| S2 | **workflow 侧 13 个调用方**改调 SDK（`ISysNoticeService` 保留为薄封装或下线） | 流程通知端到端可用 |
| S3 | **OA 侧 10 个调用方**改调 SDK | 印章/证照/风险/同步通知可用 |
| S4 | OA 的 `SysNoticeController` / `InnerNoticeController` 收口 + 前端 `notice.ts` 改端点 | 消息铃铛数据来自新模型 |
| S5 | HR 的 ESS 消息收口（3 个写入方 + 门户查询） | ESS 消息可用 |
| S6 | CRM 5 个 dispatch 改调 SDK | CRM 提醒可用 |
| S7 | 安全通知（`LoginRiskNoticeService` / `SecurityChangeNoticeService`）改调 SDK | 安全通知可用 |
| S8 | 删 4 张表 + 改 `02`/`03`/`06` 脚本 + **重新生成 `07`** + 删 2 个前端组件 | 全仓无残留引用 |
| S9 | 全量回归（五类场景） | PRD 的 AC-15 |

**注意**：S8 的删表必须在 S2-S7 全部完成后执行，否则会中断正在运行的功能。
