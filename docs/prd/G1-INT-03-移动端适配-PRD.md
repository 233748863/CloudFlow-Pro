## 1. 背景与目标

### 1.1 问题：适配程度不均，不是"大部分没适配"

> **2026-08-31 摸排修正**：本 PRD 初版说"只有 3 个移动端组件、大部分页面没适配"，**低估了现状**。

**实测已有的移动端基建**：

| 资产 | 说明 |
| --- | --- |
| `hooks/usePullToRefresh.ts` | **下拉刷新已实现** —— 本 PRD 原计划新建 `MobilePullRefresh` 组件 |
| `hooks/useGestures.ts` | 手势处理 |
| `hooks/useKeyboardHeight.ts` | 软键盘高度（输入框遮挡处理） |
| `hooks/useOffline.ts` | 离线状态 |
| `utils/device.ts` | `isMobileDevice()` 四重判断 |
| 响应式断点 | **已用 779 处** |
| `components/mobile/` | 3 个组件（表单渲染、流程轨迹、任务处理） |

**修正后的问题定位**：
- 移动端**基建已有**（hooks + 断点 + 设备判断），缺的是**布局壳**（底部导航、抽屉式侧栏）与**页面级适配的均匀度**
- `src/pages` 下 153 个 TSX 文件里，响应式覆盖不均 —— 需按 §3.1 的 8 个场景逐个核实哪些真的缺（**这是本 PRD 设计前的必查项**）
- PWA 已启用（`vite-plugin-pwa` 1.2.0），缺口已暴露给用户

**工作量 L → M**：6 个计划新建组件里，下拉刷新与手势已有 hook 支撑。

### 1.2 目标
1. 明确移动端**能力边界**（不是所有页面都要适配）
2. 覆盖高频移动场景
3. 补移动端专用组件（底部导航、下拉刷新、筛选抽屉等）
4. 现有约 70 个公共组件的响应式增强
5. 移动端专属能力：定位打卡、拍照上传

### 1.3 非目标
- **不适配全部 153 个页面**（管理配置类页面在手机上无意义）
- 不引入 Vant / NutUI（Vue 生态）或 Taro（独立跨端框架）
- 不做原生 App（已有 PWA + Tauri 双端）
- 不做微信小程序（第三套壳，收益低）

## 4. 功能需求

### FR-1 响应式断点策略
- FR-1.1 统一断点（对齐 Tailwind 默认）：
  ```
  移动端   < 640px   (sm 以下)
  平板     640-1024px (sm ~ lg)
  桌面端   >= 1024px  (lg 以上)
  ```
- FR-1.2 提供 `useBreakpoint()` hook 供组件判断当前形态
- FR-1.3 移动端与桌面端**共用路由**，由布局壳决定渲染形态（不做两套路由）
- FR-1.4 **两套判断并存，边界明确**（2026-08-31 已定决策）：

  | 判断方式 | 用于 | 实现 |
  | --- | --- | --- |
  | **视口宽度**（新建 `useBreakpoint()`） | **布局** —— 单列/多列、卡片/表格、弹窗/全屏、导航形态 | 新建 hook + 已有 779 处 Tailwind 断点 |
  | **UA 嗅探**（已有 `isMobileDevice()`） | **功能降级** —— 是否启用定位打卡、是否开相机、是否显示"请在电脑端使用"引导 | 保留 `utils/device.ts`，不改造现有 `router.tsx` / `ThemeContext.tsx` 用法 |

  **理由**：窗口拖窄的桌面浏览器应该变单列布局（视口判断），但不应该弹出相机（UA 判断）。两者回答的是不同问题。

  **禁止**：布局逻辑里用 `isMobileDevice()`，功能降级里用视口宽度。Code Review 检查项。

### FR-2 移动端布局壳
- FR-2.1 底部导航（`MobileTabBar`）：工作台 / 待办 / 消息 / 我的（4 个 tab）
  - 待办与消息带未读数徽标（消息未读数来自批次 A SYS-01）
- FR-2.2 顶部栏（`MobileHeader`）：返回 / 标题 / 操作按钮
- FR-2.3 现有 `side-nav.tsx` 在移动端形态改为抽屉式（左滑唤出）
- FR-2.4 安全区适配（iOS 刘海屏 `env(safe-area-inset-*)`）
- FR-2.5 桌面端布局不受影响

### FR-3 移动端专用组件（6 个）
| 组件 | 用途 |
| --- | --- |
| `MobileTabBar` | 底部导航 —— 新建 |
| `MobileHeader` | 顶部栏 —— 新建 |
| ~~`MobilePullRefresh`~~ | **已有 `usePullToRefresh` hook**，只需薄封装为组件或直接用 hook |
| `MobileFilterDrawer` | 筛选抽屉（替代桌面端筛选栏）—— 新建 |
| `MobileActionSheet` | 底部操作面板（替代下拉菜单）—— 新建 |
| `MobileListCard` | 列表卡片（替代表格行）—— 新建 |

- FR-3.1 上拉加载复用现有 `VirtualList.tsx`（已在依赖 `react-window`）
- FR-3.1B **下拉刷新直接用现有 `usePullToRefresh`**，不新建组件（摸排修正）
- FR-3.1C 输入框遮挡用现有 `useKeyboardHeight`
- FR-3.1D 手势（如左滑操作）用现有 `useGestures`
- FR-3.2 全部组件遵守触控目标 ≥ 44×44px

### FR-4 现有公共组件响应式增强
- FR-4.1 `table.tsx`：移动端降级为 `MobileListCard` 卡片列表（每行一卡）
- FR-4.2 `BaseDialog` / `ModalOverlay`：移动端全屏展示（而非居中弹窗）
- FR-4.3 各类 Selector（`EmployeeSelector` / `DeptSelector` / `UserSelector` 等）：移动端全屏选择页
- FR-4.4 `DateRangePicker`：移动端改为分步选择（先开始后结束）
- FR-4.5 `tabs.tsx`：移动端支持横向滚动
- FR-4.6 表单（批次 C 的 `FormRenderer`）：`GRID` 降单列（C1 已要求），本期确认落实

### FR-5 场景适配（8 个）
- FR-5.1 每个场景的适配要求：单列布局、卡片式列表、底部固定主操作按钮、筛选走抽屉
- FR-5.2 **考勤打卡（移动端专属重点）**：
  - 独立移动页面（桌面端不需要）
  - 获取地理定位（`navigator.geolocation`），传经纬度到后端（批次 D 的 D2 已定义 `latitude` / `longitude` 字段）
  - 位置围栏校验结果展示（D2 FR-6）
  - 可选拍照（`input[capture]`），上传到 `sys_file`
  - 显示当日打卡记录与班次信息
  - **定位权限被拒时的降级**：提示用户开启，或允许无位置打卡但标记 `location_valid_flag=0`
- FR-5.3 客户跟进录入（CRM-01 活动）：快速录入表单，支持语音转文字（浏览器原生 API，可选）
- FR-5.4 工作台：卡片式指标 + 图表（ECharts 移动端配置：简化图例、增大触控区）

### FR-6 不适配页面的引导
- FR-6.1 移动端访问不适配页面时，展示引导页："此功能建议在电脑端使用"，提供返回工作台按钮
- FR-6.2 引导页不是硬阻止 —— 提供"仍要继续"选项（桌面版布局横向滚动）
- FR-6.3 不适配页面清单集中配置（一处维护）

### FR-7 PWA 增强
- FR-7.1 检查现有 PWA 配置：图标、启动画面、`display: standalone`
- FR-7.2 离线可访问页面：工作台、待办列表（配合现有离线同步能力）
- FR-7.3 新版本提示更新

## 5. 非功能需求

| 项 | 要求 |
| --- | --- |
| 触控目标 | ≥ 44×44px（WCAG 2.1 AAA 建议 44px） |
| 性能 | 移动端首屏 < 3s（4G 网络）；列表滚动 60fps |
| 包体积 | 移动端组件按需加载，不增加桌面端包体积 |
| 无障碍 | 触控目标间距 ≥ 8px；表单字段有 label；对比度符合 WCAG AA |
| 定位隐私 | 打卡定位仅在用户主动打卡时获取；不后台追踪；获取前需用户授权 |
| 拍照隐私 | 仅打卡场景使用，图片存 `sys_file` 并受权限控制 |
| 主题 | 移动端支持亮暗主题（复用现有体系） |
| 安全区 | iOS 刘海与底部手势区适配 |
| 桌面端零影响 | 所有改动不得影响桌面端现有布局与行为 |

### 7.2 风险

| --- | --- |
| **工作量随页面数线性增长，易失控** | §3.1 明确只覆盖 8 个场景并列出不适配清单。这是本 PRD 最重要的范围控制 |

| 移动端组件与桌面端组件双份维护成本 | 优先"同一组件响应式"而非"两套组件"；只在交互形态差异大时才做移动专用组件（6 个已是最小集） |
| 8 个场景涉及多个批次的功能，依赖多 | 依赖已列；建议本 PRD 在批次 C/D/E 之后执行，或按场景分批（先适配已有功能的场景 1/3/4/5/8） |

## 9. 待确认

| # | 问题 | 建议默认 |
| --- | --- | --- |
| 1 | 8 个场景的优先级与是否需要增减 | 建议按 §3.1 顺序；实际应由业务确认哪些场景移动使用频率最高。**打卡与待办审批是最刚需的两个** |
| 2 | 是否需要移动端消息推送（Web Push） | 建议本期不做。Web Push 在 iOS 上限制多（需 16.4+ 且已安装 PWA）；批次 G 的 INT-02 企业 IM 待办推送是更实用的路径 |
| 3 | 语音转文字是否需要 | 建议可选（浏览器 `SpeechRecognition` API 兼容性一般），不作为验收项 |
| 4 | 平板（640-1024px）如何处理 | 建议按桌面端布局（平板横屏接近桌面）；竖屏平板可按移动端。以视口宽度为准 |
| 5 | 不适配页面是否硬阻止访问 | 建议不硬阻止（FR-6.2 提供"仍要继续"），避免用户在移动端完全无法应急处理 |
