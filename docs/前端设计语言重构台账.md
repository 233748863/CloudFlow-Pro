# CloudFlow 桌面前端设计语言重构台账

## 摘要
- 目标：让 `cloudflow-frontend` 桌面端整体设计语言尽量以 99% 相似度向 `.references/sub2api/frontend` 靠拢，优先统一布局骨架、信息架构、原子组件、主题模式、比例、状态反馈与页面密度。
- 硬要求：后续所有页面回炉都必须满足“代码和设计语言都往源码 `.references/sub2api` 上靠”，不能再出现“不是往源码靠，而是改成了另外一种设计语言”的情况；一旦出现，直接视为不符合要求，必须继续回炉。
- 范围：首期只覆盖桌面端路由页面与共享特性面；移动端本轮不实施，但保留 Phase 2 占位。
- 当前事实：参考项目为 Vue 3 + Tailwind，CloudFlow 为 React + Tailwind 4，因此本次采用“提炼设计合同 + 重建 React 设计系统”的方式，不复制参考项目实现。
- 台账纠偏：截至 2026-04-20，此前所有“已完成”均只代表第一轮收口，不代表最终达标；现统一回退到 `实施中`，当前无桌面页面和共享层达到最终完成标准。
- 当前基线：`ThemeProvider/useTheme`、`html.dark`、新 `MainLayout`、`TablePageLayout`、`components/ui`、`/login`、`/register`、`/dashboard`、`/workplace` 等已完成第一轮回炉，但仍未达到 99% 源码对齐标准。
- 执行纪律：从本条开始，后续每次进入任一页面或共享层改造前，必须重新读取本台账的强制规则与对应页面行，再开始动手。

## 参考设计合同
- 色板：主色统一为 `teal/cyan` 轴，主色使用 `#14b8a6 / #0d9488 / #0891b2`；禁用页面私有 `purple/pink/indigo` 作为主视觉。
- 字体：统一使用 system UI 中文优先栈，不额外引入与参考项目不一致的品牌字体。
- 间距：基于 4px 栅格，页面外边距默认 `16 / 24 / 32`，卡片内边距默认 `20 / 24`。
- 圆角：输入与按钮以 `12px` 为基础，卡片与弹窗以 `16px` 为基础，大模块保留 `24px`。
- 阴影：列表与卡片默认轻阴影，弹层与全局通知使用中高层级阴影；不再使用厚重拟物阴影。
- 表单密度：参考项目的紧凑 SaaS 密度，输入高度 `40-44px`，按钮高度 `36-48px`。
- 卡片比例：统计卡与工作台卡片优先采用“标题小、数值强、辅助说明弱”的信息层级。
- 表格样式：表头弱底色、轻边框、浅 hover；分页与筛选区与内容区明确分层。
- 玻璃态边界：只在主布局、顶部 Header、全局弹层等壳层使用，业务页内部不滥用。
- 暗色规则：统一由 `html.dark` 控制；所有共享层必须同时支持 `light | dark | system` 三种模式。

## 最终完成门槛（纠偏后）
- 只有布局骨架、信息架构、卡片比例、字体层级、间距节奏、组件状态、空态/加载态、Light/Dark 两套主题都与 `.references/sub2api/frontend` 基本 1:1 对齐，才允许标记为 `已完成`。
- “已接入 ThemeProvider / MainLayout / components/ui”、“已完成第一轮收口”、“构建通过”都不再视为完成，只能视为具备继续重做的基础。
- 任何页面只要仍保留明显的 CloudFlow 私有 Hero、工作台拼装语法、表格密度偏差、卡片比例偏差或独立视觉语言，就必须维持在 `设计中`、`实施中` 或 `联调中`。
- 完成日期只允许填写真正达到最终门槛的页面；非 `已完成` 条目统一使用 `-`。

## 强制执行规则
- 每次开始任何页面或共享层改造前，必须先重新阅读本台账的 `参考设计合同`、`最终完成门槛`、目标页面所在矩阵行，以及 `完成记录` 中该页最近一次回炉记录；不允许凭上一轮记忆继续改。
- 每次开始动手前，必须同时打开 `.references/sub2api/frontend` 中最接近的参考页面；如果没有直接对应页面，至少要回到后台标准页语法参考，如 `src/views/admin/UsersView.vue`、`ChannelsView.vue` 或其他最接近的后台列表页，禁止自行发明新设计语言。
- 参考语法 = 直接从 `.references/sub2api/frontend` 的真实源码页面或组件提取布局骨架、字段行、详情块、弹层、列表、时间线等表达；禁止就近抓取本项目现有页面作为“参考语法”，本项目代码只允许参考业务逻辑、接口字段和状态流转，不允许参考视觉结构与页面语法。
- 如果本轮没有先定位到对应的 `.references/sub2api/frontend` 参考文件路径，就视为“未完成参考抓取”，不得开始页面回炉；凡是以本项目现有实现充当视觉参考、结构参考或弹层参考，一律判定为违规并继续回炉。
- 本项目的硬约束不是“参考源码做一个更轻的 CloudFlow 风格”，而是“代码和设计语言都往源码 `.references/sub2api` 上靠”；如果改出来仍然是另外一种设计语言，即使比旧版更轻、更整洁，也一律判定为未达标。
- 台账中的“参考源码靠拢”定义，默认指向布局骨架、信息密度、筛选条形式、容器数量、卡片比例、列表/表格语法、弹层结构、字体层级、留白节奏和 Light/Dark 规则同时靠拢；不是只保留业务逻辑、再换一套“更轻”的 CloudFlow 风格。
- “代码往源码靠”包含：页面容器拆分方式、筛选条组织、主内容骨架、侧栏/弹层层级、组件组合关系和第三方控件皮肤策略都要优先向参考页看齐；不是只在业务逻辑不变的前提下重画一层皮。
- 如果用户明确指出“不像源码”“又起了一套设计语言”“页面太重”“卡片没有意义”“还在用原来的设计语言”等问题，必须视为该页未达标；该页不得标记为 `已完成`，并应继续维持在 `实施中` 或 `联调中`。
- 每次页面改造结束前，必须完成 4 项检查：`源码对照检查`、`Light/Dark 检查`、`构建检查`、`台账同步`。任一项未完成，只能算进行中，不能写完成结论。
- 每次页面回炉时，必须优先删除与源码语法冲突的旧壳层，包括但不限于私有 Hero、无意义统计卡、工作台拼装区、装饰性说明卡、过度皮肤化的第三方控件外观；原则固定为：`能删就删，能并就并，能扁平就扁平`。
- 后续每一轮实际动手前，都以本节为第一读取入口；若本节与旧完成记录、旧实现或口头默认习惯冲突，一律以本节和参考源码为准。
