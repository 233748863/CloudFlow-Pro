## 实测问题

A3管理页面R5已完成编辑、运行中改周期、手动执行、日志及电脑手机页面检查，但在直连auth的伪造调用检查失败：携带`X-Inner-Call: true`和`X-From-Service: cloudflow-auth`即可通过`@Inner`。后续使用未注册处理器的诊断请求也返回HTTP 200/业务码200，说明能到达执行服务；未知处理器自身会拒绝执行。已注册的零条日历处理器属于本次验证范围，不据此宣称发生业务数据变更。

当前`InnerAspect`仅校验上述标记及来源名称，没有服务身份凭据校验；网关会拒绝外部内部路径，实测网关伪造调用为403。随后五个实际服务的边界审计R2共15请求，缺标记或错误来源10次返回401/403，伪造auth来源5次均到达未注册处理器检查，接受执行0；结果保存在`a3-job-inner-boundary-20261002-r2.json`。原PRD AC-5F要求外部不能伪造内部任务执行。部署时是否暴露服务端口尚未验证，不能以网关通过替代直接服务入口保护，也不能将整个A3安全项标为通过。R5及独立审计失败证据完整保留。

## 建议的限定方案

仅保护`/inner/job/**`内部任务路径，包含执行、状态反查、处理器上报、完成回报及后台业务任务登记；不扩大到全部内部业务接口，也不修改公共`InnerAspect`的其他使用方。保留原来源服务白名单，在进入控制器之前增加真实身份校验。

| 项目 | 具体方案 |
| --- | --- |
| 服务凭据 | 每个逻辑服务生成独立32字节随机密钥；auth持有各调用方验证密钥，工作服务持有自己的发送密钥及auth验证密钥。实际密钥由部署安全配置提供，仓库只保存环境变量引用，自有验证环境使用新随机值 |
| 请求校验 | HMAC-SHA256；签名绑定来源服务、HTTP方法、请求路径及查询串、租户、原始请求体SHA256、UTC时间戳与16字节随机请求编号，常量时间比较 |
| 有效期与防重复使用 | 接收时间与签名时间相差最多300秒；验签后由现有Redis原子登记请求编号600秒，重复签名拒绝。正常业务重试生成新编号，既有执行编号继续保证业务去重 |
| 失败处理 | 无签名、未知服务、坏签名、内容/租户被改、超时及重复签名全部403；Redis不可用时拒绝执行并返回明确服务暂不可用，不能绕过校验；必需密钥缺失时阻止启用相关服务端点，不提供旧标记回退通道 |
| 改动范围 | `cloudflow-common-job`的请求签名、任务路径过滤及`JobReportClient`，auth五个任务Feign客户端专用配置，五个服务的配置引用与自有验证配置；无新数据库表、业务字段、菜单或员工权限，无新外部依赖 |

校验器仅处理任务路径；原始请求体在验签后仍供既有控制器正常读取，避免签名检查消耗请求体。Feign及RestClient都对实际发送的字节签名，失败重试重新签名。凭据、原始签名及完整请求不打印；正式凭据不由开发环境代填。

## 实施细节补充

签名同时绑定接收服务、用户编号及Authorization/Cookie摘要，防止合法请求被重定向或替换用户上下文；请求编号使用SecureRandom生成完整16字节随机值。Redis保存601秒，在原600秒双向时间窗外补足时间戳取整的一秒边界；正常重试仍使用新编号。任务模块显式声明仓库已使用的jakarta.servlet-api为provided，版本仍由现有平台管理、由各服务网页容器提供，没有引入新的第三方库或版本。

自有环境的五个随机凭据主副本用当前Windows账户加密保存，运行配置仅允许当前账户和SYSTEM读取。正式配置只保存环境变量引用，缺少所需凭据直接阻止服务启动。新代码验证与实际服务验收结果另记，原R5和五服务审计失败证据不覆盖。
