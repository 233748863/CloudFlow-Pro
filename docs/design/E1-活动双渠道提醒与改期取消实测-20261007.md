# E1 活动双渠道提醒与改期取消实测

本专项接续 B118/F79，核对 E1 AC-5、AC-6 及消息持久提交链路。R2 发现活动邮件未接入来源核验后，已完成 B119/F79 修复与实际提醒 R3；164 项检查、37 次脚本请求、7 次真实任务执行及 6 封本机邮件通过。原核心与工作台 R7、关联 R166 和阶段汇总 R1 均退出 0；E1 全 15 条仍未完成统一核定。

仅使用原本机隔离环境。邮件接收器监听 `127.0.0.1`，当前 auth 启动参数没有测试证书信任及邮件端点允许配置；验证包装保存两份原配置，临时启用仅指向该接收器的连接，重启原本机 auth，结束后按原字节恢复配置并再次验证服务健康。原消息渠道、用户联系方式、订阅、模板及权限保持。通过业务接口创建专属邮件渠道，结束后通过业务接口软删除；不配置正式邮箱、不向外部发送。

使用管理员创建的专属活动及既有用户 1、3，以负责人同时是参与人的场景核验去重，由实际销售账号拒绝参与后核验不收提醒。提前 30 分钟与提前 0 分钟分别核对已到期和未到期，随后验证同时间编辑、改期推迟、重新提前、取消及完成。每次调用原暂停中的 `crmActivityReminder` 手动入口，按返回的执行编号核对任务终态、消息记录、持久事件和本机邮件接收结果；原任务暂停状态及配置保持，手动执行产生的时间与日志作为实际运行事实保留。

原始活动、参与人、提醒、客户、跟进、消息渠道、模板、订阅、用户联系方式及角色权限按执行前摘要复核。执行日志仅输出检查数量和状态，邮件正文和地址仅在本机接收器的私有目录中读取；正式结果记录消息编号、投递状态及内容摘要，不输出原始邮件与凭据。

首轮 R1 在本机 auth 已健康后，父包装仍阻塞在原生子进程调用，业务验证尚未开始。核对原包装身份后停止该包装（原句柄 6079，退出 -1），保留原脚本、配置清单及中断说明；恢复两份原配置并通过原服务重启句柄 96134（退出 0）确认健康。未创建业务活动、未发测试邮件。包装改用隐藏启动并明确等待所创建的进程，再继续验证；产品未修改。

本专项对取消的初步范围为扫描前未提交的提醒，以及已投递后剩余未提交提醒；已进入消息队列但尚未投递时发生改期/取消，仍需后续独立验证，不能由本专项常规投递结果推定通过。

R2（原句柄 70026）退出 1，56 项已通过检查、17 次脚本请求及 1 次真实任务执行。活动 30 分钟提醒已入队，站内两名用户投递成功，但邮件两条均为 `SKIPPED / SOURCE_NOT_CONFIGURED`，实际邮件尝试为零；原有邮件来源核验只接入营销、商机阶段与邮件归档，活动邮件缺少接入。原八类业务/配置表、用户联系方式、角色授权及提醒任务配置保持；验证码 1452→1457，未修改计数且配置已恢复，两份本机邮件连接配置与 auth 健康亦恢复。

修复采用既有消息来源核验接口和持久事件，不增加表、字段或依赖：活动站内及邮件均纳入现有投递记录，核对原事件与收件人，再检查活动有效状态、当前提醒及参与人接受状态。普通编辑保留未改变设置的提醒编号，改期或移除设置使旧编号失效；取消、完成、删除或拒绝参与会拒绝对应的待投递消息。产品仅修改 `CrmMessageDeliverySourceGuard.java`、`MessageDispatchService.java`、`InnerMessageSourceController.java`、`CrmActivityService.java`，新增 `CrmActivityMessageSourceService.java`；前端保持 F79。
