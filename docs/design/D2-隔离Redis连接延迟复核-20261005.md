# D2隔离Redis连接延迟复核

## 实测原因

B83/F52整月性能R1的四次无分析采样请求为1264.59、1183.11、1257.39、1154.24毫秒；对应人事操作日志为356、340、340、306毫秒。后续独立分析采样显示排班SQL解析与多处Redis调用等待，未用分析期间耗时替代普通请求基线。

本机隔离Redis为8.10.1，使用MSYS运行时与select网络事件处理，共132个连接。服务端GET历史平均执行7.87微秒，独立原生TCP连接的连续/间隔PING中位数却为61.431/62.458毫秒；测量不经过Java业务代码。临时将hz从10提高至100，连续PING中位数仍为61.308毫秒；原10设置已恢复，未写入持久配置或删除任何键。

同一Redis程序另启空白实例，每组24次PING，除AUTH和只读命令外不创建业务数据：

| 已建立测试连接数 | 往返中位数（毫秒） |
| --- | --- |
| 2 | 0.124 |
| 60 | 0.507 |
| 70 | 46.756 |
| 132 | 62.194 |
| 降回2 | 0.125 |

空白实例原进程退出0，DBSIZE始终0，共享隔离实例未变更。该对照确认延迟随此Windows兼容程序的连接数量出现并消失。MSYS上游select实现的thread_socket在等待对象超过MAXIMUM_WAIT_OBJECTS时分组等待，提供了实现线索；上游源码不当作当前二进制完全相同的证明，具体连接数仍以上述实测为准。

## 隔离环境调整

使用现有Redisson配置能力，将六服务的最小空闲连接统一为4；原普通池上限64、订阅池最小1/上限50保持，HR原本已经为4。各服务继续使用原隔离Redis地址、凭据、0号库；命令超时分别保留认证/网关/办公3000毫秒、工作流5000毫秒、人事/CRM10000毫秒。

此调整仅写入当前隔离实例的integration.properties及private目录中的Redisson配置文件，不新增项目依赖或修改产品连接池默认值。原Redis服务保持运行，不清键、不重建登录态、不迁移数据。原六份配置保存备份和哈希；逐服务重载后再核对连接数与实际整月耗时。当前实施状态以d2-redis-pools-20261005-r1/manifest.json的Applied和Loaded字段为准。

D2规则和整月性能运行器新增引用配置的哈希冻结。旧R4规则与R1性能的runner-source.ps1均已保留，逐一与各自原inputs.json的哈希匹配，不将变化后的运行器归入旧证据。

## 加载与复测结果

六服务逐一重载原进程22358终态0，随后核对全部配置/原备份/私有YAML哈希与六服务健康。manifest.json已记录Loaded=true、实际PID和核验时间；Redis原进程23768保持，未清键。只读INFO实测连接数由132降至37；独立TCP探测R3每组20次，连续PING中位数0.431毫秒、间隔PING中位数0.817毫秒，分别为0.316至0.646及0.588至2.933毫秒。

B84/F52性能R2四次普通基线为206.17、123.39、149.92、164.62毫秒，均满足小于500毫秒；106项/77请求与5332份冻结输入通过。规则R5的476项/231请求、5332份输入保持，整月94.85毫秒；两轮原进程均退出0，原业务保持、敏感明文0，验证码532且原配置恢复。详细场景与尚未覆盖范围见《D2-整月重算性能与事务复核-20261005.md》；本机配置改善不构成正式部署容量结论。
