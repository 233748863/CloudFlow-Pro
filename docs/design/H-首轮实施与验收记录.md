## 2. 实现与发现的问题

菜单搜索复用后端身份化菜单缓存和现有组件，支持名称、拼音、路径、键盘及仅含菜单编号和时间的本地历史。真实手机路由使用独立MobileShell，已补充该布局中的搜索入口，不把桌面布局的窄屏分支测试当作手机路由通过。

草稿实现本人/租户隔离、配置摘要、版本竞争、无变化不续期、30天保留、提交事务及业务键重放。选人流程保存错误要求固定审批人已修；未指定选人范围仍沿既有“本租户有效用户”语义，指定范围时校验角色/部门ID。配置和表单写入使用同一加锁顺序。

真实员工界面发现两处基础资料读取误接管理接口。发起页现使用`GET /wf/startable-definitions`，沿用`workflow:process:start`权限，只列当前租户、最新已发布且本人可发起的定义，不返回模型和审批配置；先选最新版再过滤权限，避免撤权后退回旧版本。草稿四类参考字段使用`GET /wf/draft/context/{definitionId}/references/{fieldId}`，重新检查可发起上下文与字段可见性，仅返回编号、名称和部门编号；不放宽员工、部门、岗位和职位管理权限。当前`hr_position`没有部门列，职位沿原公共职位语义返回空部门。两个目录均按每页最多100条分页读取。

当前依赖JSQLParser 4.9实测会把`ORDER BY ... FOR UPDATE`输出为`FOR UPDATE ORDER BY ...`，`LIMIT`亦存在同类问题。本轮工作流五处、OA三处、HR一处已有显式`tenant_id = #{tenantId}`的锁查询使用方法级`@InterceptorIgnore(tenantLine="true")`，避免二次改写；没有类级豁免或全局关闭租户插件。回归用真实MyBatis映射与租户拦截器检查租户参数仍存在、SQL保持原样；真实双租户越权验证独立记录。

共享H审批守卫冻结模型、申请人和参与人名单，禁止覆盖审批人、转派/代理/加减签绕过及自审；HR后续节点与终审校验前序审批记录。带H标记的工资补正复用冻结财务名单，无H标记的D补正保持原行为。启动冻结接线与HR快照三字段透传已补齐。

OA完成台账成本、领用与采购接线、规则、发料/退回/冲正、重算和预警。真实错误重放原返回500，已增加耗材控制器限定的业务错误映射：冲突409、非法请求400，未知异常参数使用固定安全文案，不直接回显异常正文。

HR完成加班类型/申请、核定核价、调休/工资结算、调班与相关工作流接线。预览工时分段使用DTO直接复制，避免不兼容时间格式的二次转换导致500。HR直接使用的fastexcel-core补为显式依赖，未引入新版本。

工资关联补正发现处置快照的内部时间可包含小数秒，原返回对象的整秒解析触发异常并使处置事务回滚。现由结算服务独立读取该内部时间，保留小数秒精度与既有接口格式；无效时间返回固定业务错误，不修改全局时间规则。新增离线检查覆盖不同时间精度及异常边界，部署后关联补正已通过真实审批、应用、发放、防重复及日志隐私验证。

日历批量保存及导入服务原先把HOLIDAY日期的显式三倍标记0覆盖为1，现保留明确提交的0/1，未提供标记时沿用原默认，越界值拒绝。真实日历已覆盖WORKDAY/0、REST/0、HOLIDAY/0和HOLIDAY/1，加班分类、整分钟边界及阈值核算均通过。

假期周期修改日期或状态前，先拒绝未结算加班，再拒绝已有台账；日期和状态不变时仍允许元数据编辑。原管理关闭缺口形成的三笔真实待处置申请保留原审批结果，其中两笔明确补入开放目标、一笔终止自动结算，随后真实验证管理接口不能关闭仍有待结算加班的周期。验收经办改用既有且具备员工范围的人事身份，按`TARGET_PERIOD_CLOSED`及既有`leave_days`列核对；脚本中断后复用已提交结果继续查账，不扩大生产权限或重复入账。

H配置在07生成50租户后暴露原参数唯一性检查只比较config_key的问题，已按正式唯一键(config_key,tenant_id)检查；更新从原记录取得tenant_id，禁止借输入变更所属租户。

HR和OA原规则调用同样误接外部管理接口，现分别使用仅允许`cloudflow-service-hr`和`cloudflow-service-oa`调用的内部规则接口。HR仅允许`hr.overtime.hours.limit`，保留既有默认规则回退，但当前租户显式停用不得穿透；OA仅允许当前租户的`oa.consumable.request.limit`，不跨租户回退。命中记录限制业务类型、处理结果和本租户，并在记录前加锁去重；原外部规则管理权限不变。

独立数据库故障验证发现站内消息将重试次数强制为零，现统一沿实际渠道配置安排重试；首次失败、重试成功、重复事件不再次推送已通过真实消息状态表验证。外部推送仍为替身，不把该结果表述为真实网络投递成功。

真实预警还发现模板窗口仅按耗材业务编号抑制消息，补货恢复后再次缺货的新风险轮次被错误跳过。现核对来源服务、租户和显式去重键派生的稳定事件编号，匹配时沿既有事件及接收人身份去重；无显式键或事件编号不匹配时仍执行原模板窗口，订阅、免打扰、额度和自动重试边界不变。新增真实数据库用例在600秒窗口下先复现失败，修复后验证两轮各发一次、同轮不重发、任意身份不能绕过窗口及原强制重发语义。其它租户未配置仓管时，全局任务继续汇总失败，不为验收改成静默跳过或擅自补正式接收人。

审批通知仅补充白名单字段`oaRequestToken`，不复制完整流程变量或表单。处理中租约和完成标记分离，以租户及实例编号隔离，当前持有者才能续租、确认或释放；重领默认每10秒扫描最多100条，服务端再次检查至少60秒空闲，累计5次失败后先持久转存再确认原消息。线上实际使用Redisson 3.27.0，其`XClaimOptions`转换会因空闲选项为空抛异常；现使用显式`XCLAIM`脚本，保持原子空闲门槛与投递计数，两种连接实现均有真实Redis验证。

原耗材申请102保留原真实终审流程，经后台自然重试进入死信后，由真实管理员调用重放接口恢复为已批准。重放重新校验数据库中的租户、业务、终态及通知通道，只从原持久化实例补齐缺失令牌，不接受错误的既有令牌；12项核对确认原审批实例及历史均未增加，批准量正常回写，库存和台账未改变，也未提前发料。

当前开发启动默认关闭工资加密且未配置密钥，PAY核价正确拒绝明文写入。`scripts/verify-batch-h-encryption.ps1`只为本轮HR验收临时启用现有加密模块，测试密钥由Windows当前用户保护、留存在私有忽略目录，不输出或加入仓库；恢复原启动配置单独记录。保留该密钥用于后续复核合成PAY数据，不能把临时测试密钥当成正式上线密钥。

加密验收发现薪资组成及个税配置列采用MySQL JSON类型，裸密文不能合法写入。`@EncryptField(jsonStorage=true)`仅作用于这两列，将既有算法产生的密文封装为JSON字符串；其余文本列格式及算法不变，不修改表结构。读取严格验证封装与密文，失败统一隐藏，不返回原JSON或历史明文；写入失败中止操作，并拒绝解密失败占位值。参数按对象身份去重，执行完成或失败后恢复暂改的对象字段，避免重复加密或污染调用方对象。未增加明文迁移开关，在线验收只重写本轮自有且已知的合成薪资依据。
