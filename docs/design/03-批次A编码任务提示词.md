## 二、硬性约束（违反即返工）

这些是项目已有的强制规范，**不是建议**：

### 2.1 禁止 Java 拼接 SQL

```java
// ❌ 绝对禁止
String sql = "SELECT * FROM sys_job WHERE status = '" + status + "'";

// ✅ 标准 CRUD 用 MyBatis-Plus
LambdaQueryWrapper<SysJob> w = new LambdaQueryWrapper<>();
w.eq(SysJob::getStatus, status);

// ✅ 复杂查询写 XML mapper（resources/mapper/ 下）
```

### 2.2 权限码格式固定

`{module}:{resource}:{action}`，模块前缀**只允许** `system` / `oa` / `crm` / `hr` / `workflow` 五类。本批全部落在 `system`。

```java
@SaCheckPermission("system:job:list")     // ✅
@SaCheckPermission("job:list")            // ❌ 缺模块前缀
@SaCheckPermission("sys:job:list")        // ❌ sys 不在五类内
```

### 2.3 构建期静态扫描（10 条规则，违反直接构建失败）

`cloudflow-common-static-rules` 的 `StaticRuleScanner` 绑在 maven **`validate`** 阶段，发现任何 finding 就抛 `IllegalStateException`，**构建直接失败**。它不是 lint 建议。

（注：`scripts/security-audit.mjs` 是另一套独立规则，其中 `@SaCheckLogin` 被当作合法保护 —— 与扫描器结论相反。**以扫描器为准**。）

**`PERMISSION_GUARD`**：每个 Controller 里带 Mapping 注解的方法必须是以下四类之一：
- 带 `@SaCheckPermission("...")`
- 带 `@Inner`（内部接口，路径前缀 `/inner/{module}/{business}`）
- 带 `@SaIgnore`（真正的匿名接口，现仓仅 3 处：`LegalAgreementController` 2 个、`SysAnnouncementController` 1 个）
- `@SaCheckRole("admin")`（平台运维级，极少）

**`@SaCheckLogin` 不算保护** —— 只写它会被阻断。

其余 9 条规则里，这几条最容易被无意触发，写代码时就要避开：

| 规则 | 触发条件 | 怎么避开 |
| --- | --- | --- |
| `SQL_CONCAT` | 行内同时出现 `SELECT `/`UPDATE `/`DELETE `/`INSERT `（**带尾空格**）与 `+` | **这条无白名单豁免，且不判断是否真在拼 SQL**。`log.info("DELETE 完成 " + n)` 会误报。日志文案避免用这四个大写词，或改用 `{}` 占位符 |
| `POST_NO_REPEAT` | `@PostMapping` + 方法名含写语义词（`add`/`create`/`save`/`update`/`delete`/`remove`/`submit`/`approve`/`reject`/`publish`/`cancel`/`deploy`/`record`/`bind`/`unbind`/`void`/`archive`/`restore`/`rollback`/`replay`/`ignore` 等 29 个）+ 无 `@RepeatSubmit` | 写接口一律加 `@RepeatSubmit`；确实不需要的加 `@RepeatSubmit.Disabled`。注意方法名带 `record` 的查询接口也会命中 |
| `MP_SQL_LAST` / `MP_SQL_APPLY` | 出现 `.last(` 或 `.apply("` | MyBatis-Plus 这两个方法一律禁用，改写 XML |
| `MYBATIS_ANNOTATION_SQL` | 行首是 `@Select(`/`@Update(`/`@Insert(`/`@Delete(` 及对应 4 个 `*Provider` | 注解式 SQL 全禁，只能 XML |
| `TXN_WORKFLOW` | `@Transactional` 方法内调 `.startProcess(`/`.completeTask(`/`.cancelProcess(`/`.recallProcess(`/`startWorkflow(`（非 workflow 服务内） | 工作流调用移出事务 |
| `AUTH_NO_RATE` | 认证敏感 Controller 的 POST 或公开读接口无 `@RateLimiter` | 本批不涉及 |
| `HIGH_RISK_AUDIT_REQUIRED` | `@HighRiskAction` 无配套 `@Audit`/`@Auditable` | 成对使用 |
| `AUDIT_LOG_DELETE_CALL` | 对不可变日志表做删除 | 本批 `jobLogClean` 清理任务要注意：`sys_job_log` 是新表，不在不可变日志清单内，但清理逻辑要走 XML 而非拼接 |

⚠️ **白名单是 `文件路径:行号` 精确匹配**（源码里拼 `path + ":" + line` 后 `contains`）。`static-rules-whitelist.txt` 现有 14 行，其中 5 条指向 `AuthController.java:46` 与 `CaptchaController.java:33/44`。**你若在这两个文件里增删行，白名单会错位**，构建失败且报错指向无关代码。改动这两个文件后必须同步更新白名单行号。

### A2 统一消息中心

**发送链路（已定，不要改）**：

⚠️ **关键细节**：`event_type = "MESSAGE_SEND"`，`aggregate_type` 保持来源模块（**不要写成 `"MESSAGE"`** —— 现有 `OutboxPublisher.publish()` 是 `outbox.setAggregateType(envelope.getSourceModule())`，改了会破坏现有约定）。

### A3 定时任务平台

**3 张表**：`sys_job` / `sys_job_log` / `sys_job_handler`

**架构（已定）**：auth 集中调度 + Feign 调各服务 `@Inner` 执行接口。

**执行协议必须异步**（关键）：
```
auth 到点 → 抢 Redisson 锁（防 auth 多实例重复触发）→ 写 sys_job_log(RUNNING)
  → Feign 调 POST /inner/job/execute（连接超时 3s / 读超时 10s）
    → 被调服务抢 @DistributedJob 锁 → 立即返回 {accepted:true} → 本地线程池异步跑
  → auth 侧线程释放（长任务不占 HTTP 连接）
    → 执行完成 → 被调服务调 POST /inner/job/report 回传结果
  → auth 按 executeNo 幂等更新日志
```

**四类失败必须区分**：
| 情况 | 状态 | 告警文案 |
| --- | --- | --- |
| Feign 调用失败 | `DISPATCH_FAILED` | 「网络调度失败」 |
| 目标服务全不可用 | `DISPATCH_FAILED` + 按 `misfire_strategy` | 同上 |
| handler 抛异常 | `FAILED` | 「任务执行失败」 |
| **回报丢失** | 巡检先反查 `/inner/job/status/{executeNo}`，反查也失败才置 `TIMEOUT` | **「结果未知」不是「执行失败」** |

最后一条很重要：任务实际可能已成功，误报会让运维做错决策。

**已有资产必须复用**：`cloudflow-common-job` 模块的 `@DistributedJob`（Redisson 锁）已存在且用在 **26** 处。**不要重造分布式锁**，锁留在业务服务侧。

**两个服务侧接口放 `cloudflow-common-job` 统一实现**（`/inner/job/execute` 与 `/inner/job/status/{executeNo}`），五个服务共用，避免五处重复。

**24 个存量任务迁移**（不是 16 个 —— 设计文档 A-04 原清单漏了 8 个，已补，见该文档 §2 修正框），cron 与现状完全一致。

实测全仓方法级 `@Scheduled` 共 **25 个**，减去不迁移的 `OutboxScheduler` 后应迁 **24 个**。开工前先自己跑一遍确认基数：

```bash
grep -rn "@Scheduled" --include=*.java cloudflow-backend/ | grep -v /target/ | grep -v "^\s*\*"
```

补齐的 8 个都在 workflow，且 6 个位于 `*ServiceImpl`/`*Service` 而非 `*Job` 类：
`TaskTimeoutJob.cleanupExpiredKeys`(`0 0 2 * * ?`)、`TimerScanJob.cleanupExpiredTimerKeys`(`0 0 3 * * ?`)、`AnomalyDetectionServiceImpl`×2(`0 */10 * * * ?` / `0 0 */6 * * ?`)、`TimeoutDetectionServiceImpl`×2(均 `0 */5 * * * ?`)、`TransactionConsistencyService`×2(`fixedDelay=60000` / `0 0 2 * * ?`)。

迁移这 6 个时**方法要保留**（改为普通 public 方法供 `/inner/job/execute` 调用），只摘掉 `@Scheduled`，`@DistributedJob` 留在原处。

⚠️ 两个 `TimeoutDetectionServiceImpl` 的 cron 完全相同（都是 `0 */5 * * * ?`）。迁移前先读源码确认两者职责是否重复 —— **若确为重复实现，这属于本批范围外的现存缺陷，按第七节报告，不要顺手合并**。

其中四个高频任务按已定间隔调整：
| handler | 原 | 新 `interval_ms` | `log_success_flag` |
| --- | --- | --- | --- |
| `taskReminder` | 30s | 300000（5min） | 0 |
| `taskTimeout` | 60s | 300000（5min） | 0 |
| `timerScan` | 60s | 180000（3min） | 0 |
| `deadlockDetection` | 30s | 600000（10min） | 0 |

**两个任务不迁移**：`OutboxScheduler`（5s 高频 + DB 行级 claim）与 `TimerSchedulerService`（源码注释明确要求由 `TimerScanJob` 单点调度，避免两个调度器并发消费同一 Redis ZSet）。**`TimerScanJob` 本身迁移**，但它内部调用 `TimerSchedulerService` 的方式不变。

`handler_name` 只能是已上报白名单，**不接受反射类名或表达式**。`/inner/job/execute` 必须走 `@Inner` 校验，防外部伪造触发。

### A4 节假日日历

**2 张表**：`sys_holiday_calendar` / `sys_holiday_date` + `sys_dept` 增 `holiday_calendar_id` 列

新建 `cloudflow-common-holiday` 模块（已定），直接读 HR 表（各服务连同一库）。

**明细表只存例外日期**（法定节假日 + 调休上班日），普通周末由 `weekly_rest_days` 表达 —— 一年约 30 条而非 365 条。

**三级回退解析（已定）**：
```
① 员工当日排班的班次绑定日历（hr_shift.holiday_calendar_id）
② 员工所在部门的日历（sys_dept.holiday_calendar_id）
③ 租户默认日历（default_flag=1）
④ 三级全空 → 抛明确异常，绝不静默按自然日计算
```

**6 个计算方法**：`isWorkday` / `countWorkdays` / `calcLeaveDays` / `calcWorkMinutes` / `nextWorkday` / `getDateType`

⚠️ **`triple_pay_flag` 的语义不能填错**：法定节假日当天=1（三倍工资），调休日=0（两倍）。批次 H 的加班倍率依赖它。

## 四、种子数据要点

### 🛑 menu_id 段位（这一项最容易造成静默事故，先读完再动手）

**批次 A 用 1300-1349**。全局现有最大 `menu_id` 是 **1210**（不是 884 —— 884 只是 CRM 某个连续块的末尾）。后续批次：B=1350-1399、C=1400-1449、D=1450-1549、E=1550-1649、F=1650-1749、G=1750-1799、H=1800+。

设计文档早期版本写的 900-939 段位**是错的，已作废**。那个段位在现库里 40 个 ID 全被占用，其中 5 个是真实的 HR 权限：

```
925 → hr:employees:view      937 → hr:lifecycle:edit
936 → hr:lifecycle:add       938 → hr:attendance:add     939 → hr:attendance:edit
```

若照旧段位执行下面那条 `CROSS JOIN`，因为是 `INSERT IGNORE`，**不会报任何错**，但会把人事异动与考勤的新增/编辑权限静默授予全部 10 个角色（含 EMPLOYEE）。**静默越权比构建失败危险得多**，所以务必用新段位。

**落库前必须先跑冲突校验**（返回非 0 行就停下报告，不要自行改段位）：
```sql
SELECT menu_id, menu_name, perms FROM cloud_flow_db.sys_menu WHERE menu_id BETWEEN 1300 AND 1349;
```

**32 个权限码的角色授权**：
- ADMIN(role_id=1)：走现有 `SELECT 1, menu_id FROM sys_menu` 全量语句，自动含新菜单，无需改
- MANAGER(2)：除 `system:codegen:*` 与 `system:job:*` 外
- ⚠️ **全部 10 个角色都必须有的 5 个权限**（漏了普通员工登录后消息铃铛报 403）：
```sql
INSERT IGNORE INTO cloud_flow_db.sys_role_menu (role_id, menu_id, tenant_id)
SELECT role_id, m.menu_id, 100000
FROM sys_role r CROSS JOIN (SELECT 1336 AS menu_id UNION SELECT 1337 UNION SELECT 1338
                            UNION SELECT 1339 UNION SELECT 1325) m
WHERE r.tenant_id = 100000;
```

**执行后必须验证没有误授权**：
```sql
-- 必须返回 0 行：EMPLOYEE 不应有任何 hr 写权限
SELECT m.perms FROM cloud_flow_db.sys_role_menu rm
  JOIN cloud_flow_db.sys_menu m ON m.menu_id = rm.menu_id
 WHERE rm.role_id = 5 AND m.perms LIKE 'hr:%:add';
```
