## 1. 当前基线和取值对齐

`oa_meeting_room`已有capacity/location/equipment；仅补结构化设备标签和可预约规则。`oa_schedule_event`已有room_id，继续使用它，不重复新增meeting_room_id。`oa_meeting_attendance`现有minutes_id必填，meeting_id可空；新增明确schedule_event_id，允许会前邀请在无纪要时记录。原attend_status/check_in_time仍表示实际出席。

| 字段 | E1 CRM值/含义 | H4 OA采用值/含义 |
| --- | --- | --- |
| status | PLANNED/IN_PROGRESS/COMPLETED/CANCELLED/NOT_HELD | 完全一致，不混入审批状态 |
| acceptance_status | NONE/ACCEPTED/DECLINED/TENTATIVE | 完全一致，与签到独立 |
| remind_minutes_before/channel_type | 提前分钟数/统一消息渠道 | 同名同义 |
| sent_flag/send_time/message_record_id | 实际发送标志/时间/消息记录 | 同名同义，排队不等于已发送 |

会议审批独立`approval_status`，周期主记录独立`recurrence_role`，均不扩充会议五态。OA/CRM继续两套业务实体，只复用枚举/提醒配置及冲突接口，不合并表。

## 2. 房间规则、审批与并发

单次预约校验会议室启用、预计人数≤capacity、开始早于结束、最短/最长时长、提前天数、开放星期、开放时间和绑定节假日日历。原会议室未配置限制时保留原行为；前端新建房间时显式填写规则，不能通过给旧表加默认工作时间悄悄取消历史预约。capacity/location不新增同义列，equipment原文保留，equipment_tags从页面显式选择。

日历判断复用A4按日期返回的工作日/休息日/法定假及调休事实；`holiday_bookable_flag=0`拒绝法定假，开放星期限制仍适用。已绑定日历的日期尚未核定时返回缺配置原因，不把未知日历当普通工作日。跨天预约逐天检查开放区间。

房间互斥在数据库内实现：锁本租户会议室行，再查并写所有有效预约；换房时按房间ID顺序同时锁旧/新房间。冲突比较半开区间`[start,end+buffer)`，buffer表示会后间隔，10分钟配置就需10分钟间隔，不能两端各扩10分钟变20分钟。既有预约按保存的buffer快照校验，新规则不篡改历史；开启更严格规则时先显示存量冲突，确认后仅约束新预约。独立事件编辑同样检查版本和冲突，不允许走旧createEvent/updateEvent绕过。

需要审批的房间：草稿不占位，提交时锁房间并占位、PENDING等待审批；提交事务后启动工作流，失败保留可重试记录。审批拒绝/撤回将事件CANCELLED并释放占位；未经审批不能IN_PROGRESS。审批人为自己且无合法替代审批人时提示配置冲突，不能自批。过了预约结束仍PENDING的会议由任务标NOT_HELD并审计，不让逾期未批占位永久阻塞。已有需纪要/签到功能只对真实发生的单次会议使用。

参会人冲突是提示：查询OA会议和CRM本人参与的活动，返回授权可见标题或仅“忙碌时段”，不能泄漏客户名称。CRM暂不可达显示“客户活动冲突未核实”，用户确认后允许继续；房间冲突或房间数据不可核实必须拒绝预约。

## 3. 邀请、五态与提醒

有效预约形成邀请名单，`oa_meeting_attendance`按日程+用户唯一；会前minutes_id可空，纪要创建后关联同一行，不重复签到记录。只有受邀本人可回应ACCEPTED/DECLINED/TENTATIVE；不允许修改签到。改期/换房/重要参会信息变化增加schedule_version，受影响人接受状态重置NONE并通知；移除参会人保留历史，不能再回应旧邀请。回应请求带invitationVersion，过期邀请返回冲突。

状态流转：PLANNED→IN_PROGRESS→COMPLETED；PLANNED可CANCELLED/NOT_HELD，未实际开始不能直接自动COMPLETED。取消、未举行释放房间且取消提醒；已实际开始取消须管理权限和原因，保留出席事实，不回写成从未举行。主持人/管理者才能修改会议状态，受邀普通员工仅能回应本人邀请。

`oa_meeting_reminder`存0—43200提前分钟数及渠道，与CRM配置结构一致；一场最多10组互异提醒。改期取消旧版本PENDING/DISPATCHED提醒，新增新版本。定时任务使用A3，不另写散落@Scheduled；发送经SYS-01，业务源键包含会议ID、版本、提前分钟和渠道。每次真正投递前再次核验会议仍有效和版本未过期，收件人排除已DECLINED或被移除用户；外发已开始的旧消息保留事实并发更正通知，不能撤销实际已发送邮件。未配置外部渠道显示原因，站内渠道和预约仍可用。

## 4. 周期规则与看板

采用RFC5545 RRULE，服务端拟锁定`org.mnode.ical4j:ical4j:4.3.0`解析；Maven发布源码已核验BSD三条款，625个基础class最大主版本55，Java17可加载的主版本上限61。完整工程及传递依赖兼容性待批准后构建验证，记录见总确认稿；不使用浏览器提交的展开列表作为权威。DTSTART来自会议开始，DTEND按原持续时间推导，时区使用明确timezone_id，当前部署Asia/Shanghai。COUNT/UNTIL与recurrence_end_date共同取较早上限；没有任何结束条件时拒绝，最多500个实例、从首次开始最多3660天，超过上限明确拒绝而非静默截断。

SERIES行只作规则主记录，不占房间、不发邀请；INSTANCE行保存实际会议与original_start_time，主记录和首个实例不能双占位。一次提交在同一锁定房间的事务中校验全部展开实例，与已有预约及同系列实例两两不重叠；其中一项失败则全部不创建，返回具体冲突日期。唯一键`tenant_id,parent_event_id,original_start_time`保证重试不重复展开。单实例改期不改original_start_time，取消保留CANCELLED记录，重新展开不能复活它。修改整系列仅重算未开始、未独立编辑的未来实例，先显示影响清单并二次确认，已发生实例不可重写。

前端保留已安装FullCalendar普通月/周/日历，用现有React和CSS Grid实现“横轴时间、纵轴房间”的资源看板。当前项目没有商业resource-timeline授权，本提案不安装试用版、不伪造licenseKey；该实现方式需随总设计确认，业务呈现仍覆盖占用、空闲、点击预约与冲突提示。查询时间窗最多31天、每页50间会议室，保证结果不是只截前几间而无提示。

空闲查询复用提交同一个房间规则计算器，参数为start/end/人数/设备；临近提交再锁行复查。使用率=报告期内已实际使用的IN_PROGRESS/COMPLETED会议时长与开放窗口交集÷同房间同期可预约窗口分钟数；排除CANCELLED/NOT_HELD和缓冲分钟，分母0显示“不适用”。另列PLANNED/PENDING的预订占用率，不能当实际使用率。

## 5. 接口与权限

所有接口返回`R<T>`或分页类型，更新携带version；写接口带重复提交保护、审计。既有日程入口转调相同服务并保留旧权限，不能形成新旧两套规则。

| `GET /oa/meeting/board` | `oa:meeting:board` | start/end、房间分页→占用、审批标识，隐藏无权会议详情 |
| `GET /oa/meeting/room/available` | `oa:meeting:board` | 时段、人数、设备→可预约房间及规则 |
| `PUT /oa/meeting-room/{id}/booking-rule` | `oa:meeting:room-manage` | 开放/时长/提前天数/日历/审批/缓冲及version |
| `POST /oa/meeting/booking`、`POST /oa/meeting/booking/{id}/submit` | `oa:meeting:book` | 本人发起、标题/时段/roomId/邀请人/提醒/线上链接 |
| `PUT /oa/meeting/booking/{id}` | `oa:meeting:edit-own` | 本人尚未开始会议；变更规则全部重校验 |
