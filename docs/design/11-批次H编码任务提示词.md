## 一、这批和前七批不一样，先读这节

批次 H 是 **19 个独立增强条目的菜单**，不是一个固定范围的批次。已明确定位：**按需挑选，不建议整批执行**（全做是 36 张表、320 → 355）。

所以 `H-批次H技术设计要点.md` 只有 163 行，给的是**要点而非完整设计** —— DDL、接口签名、业务逻辑都没写。理由：19 个条目大概率有一半不会执行，现在做完整设计等于浪费，而且摸排结果会过期（前六批的经验是**设计前必须摸排，摸排后有 5 个条目工作量下降**）。

**因此你的任务分两种情况：**

| 情况 | 你要做的 |
| --- | --- |
| **用户已指定要做哪几项** | 按第二节的补设计流程，先补完整设计，**给出设计后等确认再编码** |
| **用户没指定** | 不要自己挑。列出第四节的优先级建议，问清楚做哪几项 |

🔴 **不要在没有完整设计的情况下直接编码 H 的任何条目。** 前七批都是"设计 → 确认 → 编码"，H 不能跳过设计。

## 二、执行某项时的补设计清单（六步）

确定要做某条目后，按顺序补：

1. **重新摸排该条目** —— 前六批经验：摸排必有发现。`H-批次H技术设计要点.md` §1 的摸排结论是 2026-08-31 的，先验证是否仍然成立
2. **完整 DDL** —— 遵循对应模块规范：workflow 用 `VARCHAR(64)` 主键且普遍不加 `deleted`；HR/OA/CRM 用 `BIGINT(20)` 自增（详见通用约束 §3.5）
3. **接口签名 + 权限码** —— 模块前缀限 `system`/`oa`/`crm`/`hr`/`workflow` 五类
4. **与已铺地基的接线点** —— 见第三节，不要重复建设
5. **跨模块取值对齐** —— 若涉及（如 OA-07 与 E1），先确认对齐标准
6. **更新表数与 `06` 种子数据** —— menu_id 段位 **1800+**（⚠️ 2026-09-01 全批次段位重排，文档早期版本写的"H 建议用 1100+"会撞现有菜单，见 `01-决策汇总.md` §11.1）

## 五、五个已定的关键决策（执行对应条目时必须遵守）

### 5.1 OA-07 必须与 E1 对齐（强约束）

会议的 `status` 五值与 `acceptance_status` 四值**必须与 `crm_activity` 完全一致**。这是 H4 的第一验收项。

已定决策是"CRM 活动与 OA 日程**不合并，只对齐取值**" —— 所以不要试图合并两张表，也不要自己定义一套取值。

### 5.2 OA-08 台账用新表而非扩展 `oa_asset_log`

已定决策：**新建 `oa_consumable_ledger`**（含 `balance_after` 结存快照、`unit_price`、`amount`），原 `oa_asset_log` 保留作通用变更历史。

⚠️ 摸排修正：耗材出入库**已实现**（`ConsumableServiceImpl.addStock` + `getLowStockList`）**且已写 `oa_asset_log`**（`refType="2"` + `quantity_change`）。**缺的只是结存快照与领用单**，不是整个出入库。PRD 原写"无出入库流水"是错的。

理由：往共用日志表加 `balance_after` 对资产无意义，两种语义混在一表难维护。

### 5.3 CRM-07 的业绩口径变更影响面

`CrmPerformanceQueryServiceImpl` 实测有 **4 个聚合方法**（`summarizeByOwner` / `summarizeByDept` / `topOwners` / `topDepartments`），**全按单一 owner/dept 维度**。

改团队分成会改变业绩口径 —— 这 4 个方法全部受影响。改造前先确认历史报表数据是否需要保持可比。

### 5.4 HR-13 得分公式复用 C3 的解析器

不要新写表达式解析器。C 批已有受限解析器（Aviator + 4 项加固配置），改 `evalNumeric` 即可。

🔴 **必须沿用 C 批那套加固配置**（`ENABLE_PROPERTY_SYNTAX_SUGAR=false` + 移除 123 个内置函数 + 类白名单置空 + `FEATURE_SET`），详见 `02-安全验证报告.md` §2.4。**不要因为"绩效公式是内部人写的"就放宽配置。**

### 5.5 INT-06 一期可提前

菜单搜索几乎零成本（`useBackendMenus.ts` 已有数据源），不必等 H 批，可插入任意批次。

## 七、验收要求

H 批没有统一验收清单（范围不固定）。每个挑中的条目，补设计时**必须一并写出该条目的验收标准**，标准要满足：

1. 可自测（不是"功能正常"这种无法验证的表述）
2. 覆盖"现有行为不变"（H 的条目大多是改造现有功能）
3. 若涉及第五节的决策，验收项里要有对应的检查

通用约束第五节的自检清单**全部适用**（构建、类型检查、静态规则、menu_id 冲突校验、越权校验等）。
