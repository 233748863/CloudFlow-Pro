## P0-1：批量安全检查接口请求体不匹配（已修复）

### 现象
- 前端 `checkOperationSafety` 发送：`{ workflowIds: [...] }`
- 后端 `POST /api/workflow/batch/check-safety` 接收：`@RequestBody List<String> workflowIds`
- 结果：反序列化失败或参数为空，归档前安全检查流程异常

### 影响
- 批量归档前置检查不可用，影响需求 7.5、10.6
- 可能导致前端误判风险状态，降低操作可靠性

### 方案 A（推荐）：统一后端为 DTO 入参
- 后端改为接收 `BatchIdsRequest { List<String> workflowIds }`
- 与前端现有调用保持一致，避免影响前端多个调用点
- 优点：可扩展（后续可加 `operationType`、`force`）

### 方案 B：调整前端直传数组
- 前端将请求体改为 `["id1","id2"]`
- 优点：后端改动小
- 缺点：语义不清晰，可扩展性差，后续加参数需再次破坏协议

**推荐：方案 A**

### 修复状态
- **状态：已修复**
- **后端修复**：`/api/workflow/batch/check-safety` 入参已从裸数组统一为 DTO（`BatchIdsRequest`）
- **前端修复**：`checkOperationSafety` 继续按 `{ workflowIds }` 协议调用，无需改动业务层调用方式
- **结果**：安全检查请求体协议已一致，归档前安全检查链路恢复可用

## P0-2：永久删除“确认字段”前后端不一致（已修复）

### 现象
- 后端 `DELETE /api/workflow/batch/permanent` 强制校验 `confirmed=true`
- 前端 `permanentDeleteWorkflows` 仅发送 `{ workflowIds }`，未发送 `confirmed`
- 结果：接口稳定返回失败，永久删除无法执行

### 影响
- 需求 8.5~8.7 无法完成
- 管理端清理闭环中断，归档数据长期堆积

### 方案 A（推荐）：前端补充 `confirmed: true`
- 在确认弹窗点击“确认删除”后发送 `{ workflowIds, confirmed: true }`
- 保持后端安全设计不变，符合“二次确认”审计思路

### 方案 B：后端移除 `confirmed` 强校验
- 仅依赖前端 UI 弹窗确认
- 缺点：安全性下降，后端无法证明“已确认”语义

**推荐：方案 A**

### 修复状态
- **状态：已修复**
- **前端修复**：`permanentDeleteWorkflows` 请求体已补充 `confirmed: true`
- **后端现状**：保留 `confirmed=true` 强校验逻辑（安全策略未降级）
- **结果**：永久删除接口不再因确认字段缺失而失败

## P0-3：模板来源字段与引用统计链路未闭环（已修复）

### 现象
- `WorkflowTemplateMapper.xml` 用 `wf_process_definition.template_id` 统计使用数
- `TemplateServiceImpl.createWorkflowFromTemplate` 注释明确“需要在 `WfProcessDefinition` 增加 templateId 字段”，当前仅拼接到描述文本
- `WfProcessDefinition` 实体未见 `templateId/currentVersion` 等字段闭环

### 影响
- 模板删除前“是否被引用”检查不可靠（可能始终 0 或映射异常）
- 需求 2.5“记录来源模板信息”无法结构化查询
- 需求 10.1 引用完整性存在缺口

### 方案 A（推荐）：补齐实体/DDL/Mapper 全链路
- `wf_process_definition` 增加并映射 `template_id`
- 创建流程时写入 `template_id`
- 删除校验与统计基于结构化字段
- 同步补齐必要索引

### 方案 B：建立独立映射表 `workflow_template_usage`
- 每次“从模板创建流程”写一条关系记录
- 删除校验与统计走关系表
- 优点：可保留历史关系
- 缺点：改造面大于方案 A

**推荐：方案 A（简单直接，落地快）**

### 修复状态
- **状态：已修复**
- **后端修复（实体）**：`WfProcessDefinition` 已补齐 `templateId`（并补齐 `currentVersion` 字段映射）
- **后端修复（业务）**：`createWorkflowFromTemplate` 已改为结构化写入 `templateId`，移除“描述文本拼接来源模板”的临时方案
- **后端修复（SQL）**：模板使用统计条件已修正为 `del_flag = '0'`，避免删除标记字段不一致导致统计失真
- **结果**：模板来源追溯与引用计数链路已闭环，删除前引用检查可靠性恢复

## P1-1：版本历史/详情/对比接口权限控制未完成（安全高风险）

### 现象
`VersionController` 中多处保留：
- `// TODO: 权限验证 - 只有流程创建者和管理员可以查看`

### 影响
- 违反需求 9.3/9.4
- 可能导致普通用户读取非本人流程版本信息（敏感配置、流程规则暴露）

### 方案 A（推荐）：控制器层 + 服务层双重校验
- 控制器增加注解与显式校验（当前用户是否管理员/创建者）
- 服务层再做数据级校验，防止绕过

### 方案 B：AOP 统一鉴权切面
- 对版本查询接口统一切面拦截
- 优点：集中化
- 缺点：初期排查复杂、上下文传参要求高

**推荐：方案 A（快速、清晰、可审计）**

## P1-2：安全检查核心能力仍为 TODO（运行实例/依赖检查缺失）

### 现象
`SafetyChecker` 中：
- 运行实例检查 TODO（当前“假设没有运行实例”）
- 依赖关系检查 TODO（未检查流程引用/定时任务关联）

### 影响
- 需求 7.5、10.6、设计“安全检查机制”未达标
- 归档/删除时高风险流程无法被有效拦截或警告

### 方案 A（推荐）：接入真实数据源完成检查
- 注入实例服务/Mapper，查询 RUNNING/SUSPENDED 实例
- 增加依赖检测（子流程引用、任务计划引用）
- 将结果写入 `SafetyCheckResultDTO` 详细字段

### 方案 B：先做“最小可用”策略
- 仅实现运行实例检查，依赖检查先降级为 warning
- 快速恢复关键风险防护，再二期补依赖图谱

**推荐：方案 A（一次到位，避免重复返工）**

## P1-3：归档时间筛选参数格式不一致（筛选失效）

### 现象
- 前端传参：`params[archivedAfter]=yyyy-MM-dd`、`params[archivedBefore]=yyyy-MM-dd`
- 后端接参：`@RequestParam archivedAfter/archivedBefore` 且格式 `yyyy-MM-dd HH:mm:ss`
- 同时前端使用 `params[...]` Map 风格，后端并未按 Map 接收

### 影响
- 需求 8.3“按归档时间搜索”无法稳定生效
- 管理端筛选结果与预期偏差

### 方案 A（推荐）：统一为标准 query 参数 + LocalDate
- 前端传 `archivedAfter=yyyy-MM-dd` / `archivedBefore=yyyy-MM-dd`
- 后端改 `LocalDate`（或支持多格式解析）

### 方案 B：保持后端现状，前端改为完整时间
- 前端提交 `yyyy-MM-dd 00:00:00 / 23:59:59`
- 缺点：前端逻辑复杂且易出时区边界问题

**推荐：方案 A**

## P2-2：模板预览仅占位，未展示流程图与节点配置

### 现象
`TemplateLibrary` 预览弹窗显示“流程图预览功能开发中...”

### 影响

## P2-3：导入页面权限变量已声明但未实际生效

### 现象
`WorkflowImport` 获取了 `canImport/canImportBatch`，但文件选择、`multiple`、批量导入流程未按权限限制

### 影响
- 需求 6.6、9.6 可能被绕过（至少前端侧）
- 非管理员可在 UI 发起批量导入（最终可能被后端拦截，但体验与预期冲突）

### 方案 A（推荐）：前端显式权限门控 + 行为降级
- 非管理员：禁用多文件上传、只允许单文件导入
- 页面提示权限说明，减少无效请求

### 方案 B：仅保留后端拦截
- 前端不做限制
- 缺点：用户体验差，产生大量 403/失败提示

**推荐：方案 A**

## P3-1：标签筛选采用字符串 LIKE，准确性与性能可优化

### 现象
模板标签存储为 JSON 字符串，筛选为 `LIKE` 循环匹配

### 影响
- 可能误匹配（如 “财” 命中 “财务/理财”）
- 多标签条件性能与精确度受限

### 方案 A（推荐）：MySQL JSON 查询能力
- 使用 `JSON_CONTAINS(tags, '\"报销\"')` 等表达式
- 提升语义准确性

### 方案 B：标签关系拆表
- `template_tag(template_id, tag)` 结构化建模
- 优点：查询最标准；缺点：改造量较大

**推荐：方案 A（中短期）**
