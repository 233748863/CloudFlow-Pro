## 四、可移植条目

### [HR-01] 假期流水台账（余额从快照改为可追溯）
- **参考来源**：`frappe/hrms` → `hrms/hr/doctype/leave_ledger_entry/leave_ledger_entry.json`（GPL-3.0，仅借鉴设计）
- **参考实现怎么做的**：实测 13 字段：`employee, leave_type, transaction_type(Link DocType), transaction_name(Dynamic Link), leaves(Float 可正可负), from_date, to_date, is_carry_forward(Check), is_expired(Check), is_lwp(Check), holiday_list`。
  核心设计：**余额不落库，由台账 sum 得出**。每次分配（+）、请假（-）、结转（+ 带 is_carry_forward）、过期（- 带 is_expired）都写一条流水，`transaction_type` + `transaction_name` 指回来源单据。任何余额争议都能逐笔还原。
- **我们现状**：`hr_leave_quota`（15 列）是余额快照：`total_quota, used_quota, frozen_quota, available_quota, expiry_date`。请假审批通过后直接改 used_quota。问题：① 余额算错无法追溯；② 结转、过期、冻结释放都是就地改数；③ 跨年结转规则无处表达。
- **落地改动**：
  - 新增 `hr_leave_ledger`：`ledger_id, tenant_id, employee_id, leave_type_id, leave_period_id, transaction_type(ALLOCATION/APPLICATION/CARRY_FORWARD/EXPIRY/ENCASHMENT/ADJUSTMENT/COMPENSATORY), source_biz_type, source_biz_id, leave_days DECIMAL(8,2)（正为增负为减）, from_date, to_date, carry_forward_flag, expired_flag, lwp_flag, remark` + 审计列
  - `hr_leave_quota` 保留为**读模型/物化视图**（查询性能考虑），由台账重算刷新，增 `last_calc_time`
  - 项目未上线，直接改 `03.cloudflow-hr.sql`，不做旧数据迁移
  - API：`GET /hr/leave/ledger`（按员工按假期类型查流水）、`POST /hr/leave/ledger/recalc`（重算余额）
- **工作量**：M（1 新表 + 请假审批链路改写 + 余额重算）
- **优先级**：P0 —— 假期余额是 HR 最容易起争议的数据，无台账等于不可审计

### [HR-02] 假期类型规则字段补齐（12 → 20+）
- **参考来源**：`frappe/hrms` → `hr/doctype/leave_type/leave_type.json`（GPL-3.0，仅借鉴）
- **参考实现怎么做的**：实测 20 个规则字段，逐个都是真实业务规则：
  - `max_leaves_allowed`（年度上限）、`applicable_after`（入职满 N 天才可用）、`max_continuous_days_allowed`（单次连续上限）
  - `is_carry_forward` + `maximum_carry_forwarded_leaves` + `expire_carry_forwarded_leaves_after_days`（结转三件套）
  - `is_earned_leave` + `earned_leave_frequency` + `rounding`（按月累积型年假，如每月 +1.25 天）
  - `allow_encashment` + `earning_component`（可折现，折现走哪个薪酬项）
  - `is_lwp`（无薪假，影响薪资计算）、`is_ppl` + `fraction_of_daily_salary_per_leave`（部分带薪，如病假 60% 工资）
  - `is_compensatory`（调休假，来源于加班）、`is_optional_leave`（可选节假日）
  - `include_holiday`（请假天数是否含节假日）、`allow_negative`（允许负余额）、`allow_over_allocation`
- **我们现状**：`hr_leave_type` 12 列，规则只有 `need_quota, is_paid, unit, quota_rule(JSON)`。所有精细规则挤在 `quota_rule` JSON 里 —— 无法在 SQL 层校验、无法在前端做配置表单、无法做规则报表。
- **落地改动**：
  - `hr_leave_type` 增结构化字段：`max_days_per_year, applicable_after_days, max_continuous_days, carry_forward_flag, max_carry_forward_days, carry_forward_expire_days, earned_leave_flag, earned_leave_frequency(MONTHLY/QUARTERLY/HALF_YEARLY/YEARLY), rounding_mode(NONE/HALF_DAY/FULL_DAY), encashment_flag, encashment_component_id, lwp_flag, partial_paid_flag, salary_fraction_per_day DECIMAL(5,4), compensatory_flag, optional_leave_flag, include_holiday_flag, allow_negative_flag`
  - `quota_rule` JSON 保留做扩展位，但上述规则全部提取为列
  - 请假校验器读结构化字段；命中规则冲突走 `sys_business_rule`（已有 `hr.leave.quota.limit` 规则码，扩展为多规则）
- **工作量**：M（表改 + 校验器 + 前端配置表单）
- **优先级**：P0 —— 与 HR-01 同批做，两者共同构成假期规则地基

### [HR-03] 假期政策与假期周期
- **参考来源**：`frappe/hrms` → `hr/doctype/{leave_policy,leave_policy_detail,leave_policy_assignment,leave_period,earned_leave_schedule,leave_allocation}`（GPL-3.0，仅借鉴）
- **参考实现怎么做的**：
  - `leave_policy` + `leave_policy_detail`：一个政策打包多个假期类型及各自额度（如"P5 及以上：年假 15 天 + 病假 10 天"）
  - `leave_policy_assignment`（实测 11 字段）：`employee, leave_policy, assignment_based_on(Select 按周期/按入职日), leave_period, effective_from, effective_to, carry_forward(Check), leaves_allocated(Check)` —— 政策与员工的绑定关系，支持按职级批量分配
  - `leave_period`：假期年度周期（可以不是自然年，如 4月-次年3月）
  - `earned_leave_schedule`：按月累积的执行记录
- **我们现状**：`hr_leave_quota` 直接挂 `employee_id + leave_type_id + year`。政策概念不存在——给 200 人调整年假额度只能逐条改；假期年度固定按自然年（`year` 字段）；无按职级/入职年限自动套政策的能力。
- **落地改动**：
  - 新增 `hr_leave_period`：`period_name, start_date, end_date, status`（替换 `hr_leave_quota.year` 的语义）
  - 新增 `hr_leave_policy` + `hr_leave_policy_detail`（policy_id, leave_type_id, annual_days）
  - 新增 `hr_leave_policy_assignment`：`employee_id, policy_id, leave_period_id, assignment_basis(PERIOD/JOINING_DATE), effective_from, effective_to, carry_forward_flag, allocated_flag`
  - 新增 `hr_earned_leave_schedule`：按月累积执行台账（写入 `hr_leave_ledger`）
  - 批量分配 API：`POST /hr/leave/policy/{id}/assign`（按部门/职级/员工类型批量）
- **工作量**：L（4 表 + 批量分配 + 与 HR-01 台账联动）
- **优先级**：P0（与 HR-01/HR-02 同批，构成完整假期体系）

### [HR-04] 考勤自动判定规则（班次判定字段补齐）
- **参考来源**：`frappe/hrms` → `hr/doctype/shift_type/shift_type.json`（GPL-3.0，仅借鉴）
- **参考实现怎么做的**：实测班次上直接挂**自动判定规则**：
  - `determine_check_in_and_check_out`（Select：按班次时间最早最晚 / 交替进出）
  - `working_hours_calculation_based_on`（Select：首末打卡 / 每次进出配对）
  - `working_hours_threshold_for_half_day` + `working_hours_threshold_for_absent`（工时不足 X 判半天、不足 Y 判缺勤）
  - `begin_check_in_before_shift_start_time` + `allow_check_out_after_shift_end_time`（打卡有效窗口，分钟）
  - `late_entry_grace_period` + `early_exit_grace_period`（迟到/早退宽容期）
  - `enable_auto_attendance` + `process_attendance_after` + `last_sync_of_checkin`（自动生成考勤的开关与水位线）
  - `mark_auto_attendance_on_holidays`、`enable_late_entry_marking`
  - `holiday_list`（班次绑节假日表）
- **我们现状**：`hr_shift`（13 列）只有 `start_time, end_time, break_minutes, work_minutes`；判定规则在 `hr_attendance_rule.config_json` 里。`hr_attendance_record` 已有 `deviation_minutes`（说明有偏差计算）但半天/缺勤阈值、宽容期、有效打卡窗口都不可配。
- **落地改动**：
  - `hr_shift` 增：`checkin_window_before_minutes, checkout_window_after_minutes, late_grace_minutes, early_exit_grace_minutes, half_day_hours_threshold, absent_hours_threshold, working_hours_calc_mode(FIRST_LAST/PAIRED), checkin_determine_mode, holiday_calendar_id, auto_attendance_flag, mark_on_holiday_flag`
  - `hr_attendance_rule.config_json` 中相应规则提取为 `hr_shift` 列（规则应挂班次，不挂规则表）
  - 新增节假日表 `hr_holiday_calendar` + `hr_holiday_date`（假期天数计算、SLA 工作日计算都要用，CRM-03 也依赖，建议做成公共表放 `01.cloudflow-common.sql`）
  - 自动考勤生成器读班次规则；结果写 `hr_attendance_record.status`
- **工作量**：M
- **优先级**：P0 —— 节假日表是 HR 假期、考勤、CRM SLA 三处的公共前置

### [HR-05] 原始打卡与考勤记录分离
- **参考来源**：`frappe/hrms` → `hr/doctype/employee_checkin/employee_checkin.json`（GPL-3.0，仅借鉴）
- **参考实现怎么做的**：实测 18 字段：`employee, log_type(IN/OUT), shift, time, device_id, skip_auto_attendance(Check), attendance(Link 回指生成的考勤单), shift_start, shift_end, shift_actual_start, shift_actual_end, geolocation, latitude, longitude, offshift(Check), overtime_type`。
  关键设计：**原始打卡（checkin）与考勤结论（attendance）是两张表**。打卡是不可变事实，考勤是可重算结论，`attendance` 字段建立回指关系。重算考勤不丢原始数据。
- **我们现状**：`hr_attendance_record`（19 列）一张表同时承担打卡与结论：有 `check_type, check_time, check_method, location, status, deviation_minutes`。改考勤规则后无法重算历史（原始时间被结论污染的风险）。已有 `location` 但无经纬度、无设备 ID。
- **落地改动**：
  - 新增 `hr_attendance_checkin`（原始打卡）：`checkin_id, employee_id, log_type(IN/OUT), check_time, shift_id, device_id, check_method(APP/FACE/CARD/WIFI/GPS/MANUAL), latitude DECIMAL(10,7), longitude DECIMAL(10,7), location_name, offshift_flag, overtime_type_id, skip_auto_flag, attendance_record_id`
  - `hr_attendance_record` 收敛为**日考勤结论**：一员工一天一条，`status, work_minutes, late_minutes, early_exit_minutes, overtime_minutes, half_day_flag, absent_flag, recalc_time`
  - 支持按日期范围重算：`POST /hr/attendance/recalculate`
  - 现有 `hr_attendance_appeal`（申诉）挂到日结论上
- **工作量**：M
- **优先级**：P1

### [HR-06] 薪资批量运算（Payroll Entry）
- **参考来源**：`frappe/hrms` → `hrms/payroll/doctype/payroll_entry/payroll_entry.json`（GPL-3.0，仅借鉴），配套 `payroll_period`、`payroll_employee_detail`、`bulk_salary_structure_assignment`、`payroll_correction`
- **参考实现怎么做的**：实测 `payroll_entry` 关键字段：`posting_date, payroll_frequency, department, designation, grade, branch, number_of_employees, employees(Table), validate_attendance(Check), start_date, end_date, salary_slip_based_on_timesheet, deduct_tax_for_unsubmitted_tax_exemption_proof, cost_center, project, payment_account, payroll_payable_account, salary_slips_created(Check), salary_slips_submitted(Check), error_message, status(Draft/...)`。
  核心设计：**批次是一等公民**。先建批次（筛选条件 + 员工清单），再由批次生成 N 张工资单，两阶段提交（created → submitted），失败信息落 `error_message` 可重跑；`validate_attendance` 决定是否强制考勤齐备才允许算薪；另有 `payroll_correction` 处理算错后的补正。
- **我们现状**：`hr_salary_slip`（21 列，含 `digest_sha256` 防篡改、`employee_confirmed` 确认态，这两点做得比参考项目细）但**没有批次概念**。算 500 人的薪只能逐条；算错无批次可回滚；无"考勤未齐不许算薪"的前置校验。
- **落地改动**：
  - 新增 `hr_payroll_period`：`period_name, start_date, end_date, frequency(MONTHLY/SEMI_MONTHLY/WEEKLY), status`
  - 新增 `hr_payroll_batch`：`batch_id, batch_no, payroll_period_id, posting_date, filter_dept_id, filter_position_id, filter_job_level_id, filter_employee_type, employee_count, validate_attendance_flag, status(DRAFT/CALCULATING/CALCULATED/SUBMITTED/PAID/FAILED/CANCELLED), slip_created_flag, slip_submitted_flag, error_message, total_gross, total_deduction, total_net` + 审计列
  - 新增 `hr_payroll_batch_employee`：`batch_id, employee_id, salary_slip_id, calc_status, error_message`
  - `hr_salary_slip` 增 `batch_id`
  - 新增 `hr_payroll_correction`：`original_slip_id, correction_slip_id, reason, corrected_by, correction_time`
  - API：`POST /hr/payroll/batch`（建批次+筛人）、`POST /hr/payroll/batch/{id}/calculate`、`POST /hr/payroll/batch/{id}/submit`、`POST /hr/payroll/batch/{id}/cancel`、`GET /hr/payroll/batch/{id}/errors`
- **工作量**：L（4 表 + 批量算薪引擎 + 幂等与失败重跑）
- **优先级**：P0 —— 薪资是 HR 最高频重活，无批量能力等于不可用于真实规模

### [HR-07] 个税税率表结构化
- **参考来源**：`frappe/hrms` → `payroll/doctype/{income_tax_slab,taxable_salary_slab,income_tax_slab_other_charges,employee_tax_exemption_declaration,employee_tax_exemption_proof_submission}`（GPL-3.0，仅借鉴）
- **参考实现怎么做的**：税率表是独立主数据（`income_tax_slab` + 分档明细 `taxable_salary_slab`），有生效期；专项扣除分两阶段——先"申报"（declaration）后"提交证明"（proof_submission），未提交证明的可选择在算薪时不予扣除（对应 payroll_entry 的 `deduct_tax_for_unsubmitted_tax_exemption_proof`）。
- **我们现状**：`hr_tax_profile`（10 列）用 `tax_config` JSON 存税率配置，`threshold` 存起征点；`hr_tax_deduction`（15 列）有 `deduction_type/amount/start_date/end_date` 但无"申报 vs 已举证"两态。个税税率改了要改每个人的 JSON。
- **落地改动**：
  - 新增 `hr_tax_slab`（税率表主数据：`slab_name, region, effective_from, effective_to, threshold_amount, status`）+ `hr_tax_slab_detail`（`from_amount, to_amount, tax_rate, quick_deduction`）—— 中国个税用「速算扣除数」，这个字段是本地化必需
  - `hr_tax_profile` 改为引用 `tax_slab_id`，`tax_config` JSON 降级为扩展位
  - `hr_tax_deduction` 增 `declare_status(DECLARED/PROOF_SUBMITTED/VERIFIED/REJECTED), proof_file_url, verify_by, verify_time`
  - 累计预扣预缴：算薪时需要年度累计值，`hr_salary_slip` 增 `cumulative_taxable_income, cumulative_tax_paid`（中国个税按累计预扣，这是与参考项目最大的本地化差异）
- **工作量**：M
- **优先级**：P1（与 HR-06 批量算薪同批更省事）

### [HR-08] 离职结算单与经济补偿
- **参考来源**：`frappe/hrms` → `hr/doctype/{full_and_final_statement,full_and_final_asset,full_and_final_outstanding_statement,exit_interview}` + `payroll/doctype/{gratuity,gratuity_rule,gratuity_rule_slab,gratuity_applicable_component}`（GPL-3.0，仅借鉴）
- **参考实现怎么做的**：
  - `full_and_final_statement`（实测）：`employee, status, assets_allocated(Table), relieving_date, date_of_joining, payables(Table), receivables(Table), total_payable_amount, total_receivable_amount, total_asset_recovery_cost` —— 一张单据同时结清「应付员工」「应收员工」「资产回收」三笔账
  - `gratuity_rule` + `gratuity_rule_slab`（实测）：`calculate_gratuity_amount_based_on(Current Slab/...), applicable_earnings_component, work_experience_calculation_function(Round off Work Experience/...), total_working_days_per_year, minimum_year_for_gratuity` —— 工龄分档算补偿，可配"按哪些薪酬项作为基数"
- **我们现状**：`hr_lifecycle_application/_detail/_task` 是通用生命周期流程（入职/转正/调岗/离职共用），离职时能跑流程和任务清单，但**没有结算单**：应付（未结工资、未休年假折现）、应收（借款、培训违约金）、资产回收（OA 有 `oa_asset` 但不与离职联动）三笔账都是线下处理。无经济补偿计算（N+1）。
- **落地改动**：
  - 新增 `hr_final_settlement`：`settlement_id, employee_id, lifecycle_application_id, join_date, relieving_date, work_years DECIMAL(5,2), total_payable, total_receivable, asset_recovery_cost, net_amount, status(DRAFT/CONFIRMED/PAID/CLOSED), instance_id` + 审计列
  - 新增 `hr_final_settlement_item`：`settlement_id, item_type(PAYABLE/RECEIVABLE/ASSET), item_name, source_biz_type, source_biz_id, amount, remark`
  - 新增 `hr_severance_rule` + `hr_severance_rule_slab`：工龄分档、计算基数（引用 `hr_comp_component`）、封顶月数（社平工资 3 倍封顶是中国法定要求）
  - 资产回收：调 OA 侧 `oa_asset`（按 `owner_id` 查未归还资产），走已有的服务间调用；OA 已有 `oa_borrow_reminder_log` 可复用提醒
  - 新增 `hr_exit_interview`：离职面谈（`hr_performance_interview` 结构可参照）
- **工作量**：L（4-5 表 + 跨服务资产查询 + 补偿计算）
- **优先级**：P1

### [HR-09] 加班与调班独立建模
- **参考来源**：`frappe/hrms` → `hr/doctype/{overtime_type,overtime_slip,overtime_details,overtime_salary_component,compensatory_leave_request,shift_request,shift_assignment_tool,shift_schedule}`（GPL-3.0，仅借鉴）
- **参考实现怎么做的**：加班有独立类型（`overtime_type`，可挂薪酬项 `overtime_salary_component` 决定加班费怎么算）与加班单（`overtime_slip` + 明细）；调休假通过 `compensatory_leave_request` 把加班转成假期额度（写 leave_ledger）；调班是独立申请（`shift_request`：`shift_type, employee, from_date, to_date, status, approver`）。
- **我们现状**：加班挤在 `hr_time_request`（`request_type` 区分请假/加班/出差），共用一套字段；加班费计算规则无处配；加班转调休无链路（`hr_leave_type` 也还没有 `is_compensatory`，见 HR-02）；调班无申请入口，只有 `hr_schedule_assignment` 由 HR 直接排。
- **落地改动**：
  - 新增 `hr_overtime_type`：`type_code, type_name, rate_multiplier DECIMAL(4,2)（1.5/2/3 倍）, salary_component_id, compensatory_flag(转调休), max_hours_per_month, applicable_day_type(WORKDAY/WEEKEND/HOLIDAY)`

  - 结算为调休时写 `hr_leave_ledger`（transaction_type=COMPENSATORY，依赖 HR-01）
  - 新增 `hr_shift_request`：`employee_id, from_shift_id, to_shift_id, from_date, to_date, reason, approver_id, status, instance_id`
- **工作量**：M
- **优先级**：P1（依赖 HR-01 台账）

### [HR-10] 员工申诉（轻量，区别于劳动争议）

### [HR-13] 绩效周期与最终得分公式
- **参考来源**：`frappe/hrms` → `hr/doctype/{appraisal_cycle,appraisal,appraisal_kra,appraisal_template,appraisal_template_goal,kra,employee_feedback_criteria,employee_performance_feedback}`（GPL-3.0，仅借鉴）。实测 `appraisal_cycle`：`cycle_name, start_date, end_date, branch, department, designation, appraisees(Table), kra_evaluation_method(Select), status, final_score_formula(Code), calculate_final_score_based_on_formula(Check)`
- **参考实现怎么做的**：周期是容器（一次性框定参评范围 branch/department/designation），KRA（关键结果领域）带权重，最终得分可用**公式**计算（`final_score_formula` 是代码字段），支持多种评估方法（`kra_evaluation_method`）。
- **我们现状**：`hr_performance_objective/_assignment/_result` + `hr_perf_evaluator/_response`（360 度）+ `hr_perf_distribution_rule`（强制分布）+ `hr_performance_interview` + `hr_performance_salary_adjustment` —— 覆盖面已经不错，缺的是：① 无"周期"实体统一框定参评范围；② 最终得分算法固定不可配；③ 无 KRA 层级（目标直接挂人，没有"关键结果领域"这一中间层做权重聚合）。
- **落地改动**：
  - 新增 `hr_appraisal_cycle`：`cycle_id, cycle_name, start_date, end_date, scope_dept_ids(JSON), scope_position_ids(JSON), scope_job_level_ids(JSON), evaluation_method(KRA_WEIGHTED/GOAL_BASED/MIXED), final_score_mode(WEIGHTED_AVG/FORMULA), final_score_formula VARCHAR(500), status(DRAFT/ONGOING/SCORING/CALIBRATING/COMPLETED)`
  - 新增 `hr_appraisal_kra`：`cycle_id, kra_name, weight, description`；`hr_performance_objective` 增 `kra_id`
  - `hr_performance_assignment` 增 `cycle_id`
  - 公式求值用受限表达式（**不要引入可执行代码字段**，改用白名单变量 + 四则运算的表达式解析，避免任意代码执行面）
  - 与现有 `hr_perf_distribution_rule`（强制分布）和 `hr_talent_calibration_session`（校准会）串联
- **工作量**：M
- **优先级**：P2

## 五、不建议移植

| 项 | 原因 |
| --- | --- |
| frappe/hrms 的 `vehicle_log` / `vehicle_service` | 我们 OA 侧已有更完整的车辆体系（`oa_vehicle` + 使用/费用/维保/违章/加油 5 张表），无需在 HR 重复 |
| `travel_request` / `travel_itinerary` / `travel_request_costing` | OA 已有 `biz_business_trip`；若要补行程明细应加在 OA，不在 HR（见 02 文档） |
| `expense_claim` 系列（7 个 doctype） | OA 已有 `biz_expense_claim` + `biz_expense_item` + `oa_expense_standard`，覆盖更贴合国内报销 |
| ERPNext 的会计科目联动（payroll_payable_account 等） | 我们无总账体系，薪资出账走 OA 付款申请即可 |
| OrangeHRM 整体架构 | PHP 技术栈，且功能广度已被我们超过（86 表 vs OrangeHRM 核心约 40 表）；仅个别字段命名可参考 |
| `daily_work_summary` 日报 | 与 OA `oa_work_task` 职能重叠 |
| Frappe 的 doctype 元数据驱动架构 | 与 MyBatis-Plus 固定表结构技术栈冲突，属重写 |
