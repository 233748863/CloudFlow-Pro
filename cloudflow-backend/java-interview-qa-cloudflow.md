# CloudFlow Pro 后端 Java 面试题聊天版

说明：这份题库按 CloudFlow 后端实际代码整理，适合面对面面试时自然表达。术语 = 具体含义，首次出现时尽量用项目里的做法解释。

项目技术亮点

问：这个后端项目整体可以怎么介绍？
答：它是一个 Java 17 + Spring Boot 3.2.6 的微服务后端，分为网关、认证、工作流、OA、HR 和 common 公共组件，公共能力包括认证、租户隔离、数据权限、日志审计、Redis、限流、防重复提交、Excel、OSS 和上下文传递。

问：你觉得项目里最值得讲的 2 个技术亮点是什么？
答：第 1 个是多租户和数据权限做成了公共拦截能力，业务代码不用每次手写 tenant_id 和部门过滤；第 2 个是工作流和 HR/OA 业务通过 Feign、回调处理器、本地消息表把审批链路串起来，业务状态和流程状态能保持最终一致。

问：项目为什么拆成多个 common 模块？
答：common 模块把通用能力沉到公共层，比如 core、security、redis、data、audit、log、idempotent、ratelimiter，业务服务只按需要引入，减少复制代码。

问：这个项目的实施步骤可以怎么讲？
答：先准备 MySQL、Redis、Nacos，再导入 DB 脚本和配置 Nacos；然后启动 cloudflow-gateway、cloudflow-auth、cloudflow-service-workflow、cloudflow-service-oa、cloudflow-service-hr；最后用前端登录验证认证、路由、流程发起、HR/OA 业务审批和回调。

问：上线或联调时最容易踩的点是什么？
答：Token、租户 ID、Redis、Nacos 配置、数据库初始化顺序、Feign 服务名和回调流 Key 要一致；这些地方错了，现象通常是 401、查不到数据、流程回调失败或服务调用失败。

问：面试时怎么把这个项目讲得不空？
答：按“请求进网关 → 校验 Token → 下游恢复用户和租户上下文 → MyBatis 自动加租户和数据权限 → 业务执行 → 日志审计/流程回调”这条链路讲，能把架构和代码连起来。

初级题 1-35

1. 问：这个项目用的 Java 版本是多少？
答：项目统一用 Java 17，根 POM 里通过 maven-compiler-plugin 把 source 和 target 都设置成 17。面试时可以顺带说一句：多模块项目统一 Java 版本很重要，否则不同服务编译和运行行为容易不一致。

2. 问：Spring Boot 在项目里主要负责什么？
答：Spring Boot 负责把 Web 接口、配置读取、依赖注入、AOP、事务、定时任务这些基础能力组装起来。CloudFlow 的 auth、workflow、HR、OA 都是基于它启动，业务开发主要集中在 Controller、Service、Mapper 和少量配置类。

3. 问：Controller、Service、Mapper 分别做什么？
答：Controller 负责接收前端请求和返回结果，Service 负责业务规则和事务边界，Mapper 负责和数据库交互。比如排班创建接口进 ScheduleController，核心校验和保存逻辑在 ScheduleServiceImpl，最终由 ShiftMapper、SchedulePlanMapper 落库。

4. 问：DTO、VO、Entity 分别是什么？
答：DTO = 前端传给后端的参数对象，VO = 后端返回前端的展示对象，Entity = 和数据库表结构对应的对象。项目里这样拆开后，前端不能随便传数据库内部字段，后端也可以在 VO 里补充 shiftName、targetName 这类展示字段。

5. 问：为什么项目里很多方法返回 R？
答：R 是统一响应对象，接口成功和失败都按 code、msg、data 返回。这样前端处理接口更稳定，后端遇到业务失败也能返回明确消息，比如流程定义不存在、排班重复、Token 过期。

6. 问：为什么 Service 方法上经常加 @Transactional？
答：@Transactional = 这个方法里的数据库操作作为一个整体提交或回滚。像批量排班、审批回调、用户角色保存这类操作，任意一步失败都不能留下半截数据，所以事务边界通常放在 Service 层。

7. 问：rollbackFor = Exception.class 是干什么的？
答：默认事务主要对运行时异常回滚，rollbackFor = Exception.class 会把普通 Exception 也纳入回滚范围。项目里很多业务方法这么写，是为了让业务异常、远程调用异常、数据处理异常都能触发回滚。

8. 问：MyBatis-Plus 在项目里解决了什么问题？
答：MyBatis-Plus 简化了常见增删改查、条件构造和分页，也方便接入拦截器。CloudFlow 还利用它的拦截器链实现了多租户、数据权限和分页，业务 Mapper 就不用每个 SQL 都手写这些公共条件。

9. 问：LambdaQueryWrapper 有什么好处？
答：LambdaQueryWrapper 用实体字段的方法引用来写查询条件，比如 Shift::getTenantId、SchedulePlan::getStatus。字段改名时编译器更容易发现问题，也比手写字符串字段名更稳。

10. 问：为什么项目里很多查询都要带 tenantId？
答：tenantId = 租户编号，用来区分不同公司或组织的数据。CloudFlow 是多租户系统，同一张员工表、排班表、流程表会存多个租户的数据，查询和写入都必须带租户边界。

11. 问：BeanUtils.copyProperties 是做什么的？
答：它把一个对象里的同名字段复制到另一个对象，减少大量重复 set 方法。项目里常用于 DTO 转 Entity、Entity 转 VO，但 id、tenantId、status 这类关键字段通常还要手动设置，避免被前端参数误覆盖。

12. 问：Lombok 在项目里主要用来干什么？
答：Lombok 主要减少样板代码，比如 @Data 生成 getter/setter，@RequiredArgsConstructor 生成构造器，@Slf4j 生成日志对象。它让 Entity、DTO、Service 更简洁，但业务逻辑仍然要写清楚。

13. 问：@RequiredArgsConstructor 有什么用？
答：它会给 final 字段生成构造器，Spring 可以通过这个构造器注入依赖。ScheduleServiceImpl 这种写法能清楚表达哪些 Mapper 和 Service 是必需依赖，也减少字段注入带来的隐藏问题。

14. 问：为什么接口里会做参数校验？
答：参数校验能把错误挡在业务入口，避免脏数据进入后面的业务和数据库。比如排班要检查日期范围、班次时间、目标类型，审批回调要检查 tenantId、businessId、approvalResult 是否完整。

15. 问：HrBusinessException 这种业务异常有什么意义？
答：业务异常能把“系统错误”和“业务不允许”区分开。比如班次被引用不能删除、同一天已经排班、审批结果非法，这些都应返回用户能理解的业务消息，而不是只返回 500。

16. 问：项目里的日志一般记录什么？
答：日志主要记录关键业务动作、核心标识、执行结果和异常原因。像创建班次要记 shiftCode，流程回调要记 businessType、businessId、processInstanceId，这样出问题时能快速定位。

17. 问：为什么不能把所有参数都打进日志？
答：日志里可能包含 Token、手机号、身份证、薪资、合同附件等敏感信息。项目有 common-sensitive 这类敏感处理能力，日志应该只打定位问题需要的字段，并对敏感内容做脱敏。

18. 问：Redis 在项目里用在哪些地方？
答：Redis 在项目里承担登录态存储、缓存、限流、防重复提交、分布式锁辅助和消息流转等能力。比如 Sa-Token 登录态放 Redis，RepeatSubmitAspect 和 RateLimiterAspect 也依赖 Redis 做控制。

19. 问：Redisson 是什么？
答：Redisson = 基于 Redis 的 Java 增强客户端，项目里主要用它做分布式锁。比如 workflow 的定时重试任务在多实例部署时需要抢锁，避免多台机器同时处理同一批消息。

20. 问：Nacos 是什么？
答：Nacos = 服务注册和配置中心。CloudFlow 的各个服务启动后会把自己注册到 Nacos，Feign 和网关通过服务名找到实例，同时服务也会从 Nacos 读取公共配置和专属配置。

21. 问：Gateway 在项目里做什么？
答：Gateway = 系统统一入口，前端请求先到网关，再转发到 auth、workflow、oa、hr 等服务。项目里的 AuthFilter 会先检查 Token，白名单接口放行，非法请求直接返回 401。

22. 问：网关白名单一般放什么接口？
答：白名单一般放登录、注册、验证码、租户选项和 WebSocket 握手这类未登录也要访问的入口。CloudFlow 里 /auth/login、/auth/captcha/**、/ws/** 就属于这类场景。

23. 问：Sa-Token 是什么？
答：Sa-Token = 登录认证框架，项目里用它管理 Token、Session、续期和登出。TokenService 对它做了一层封装，业务代码不用直接散落调用 Sa-Token API。

24. 问：项目为什么用 Authorization: Bearer token？
答：Authorization: Bearer token 是常见的 HTTP 认证格式，网关、Feign 和下游服务都容易统一处理。项目会把 Bearer 前缀剥掉后校验原始 Token，减少不同接口各自解析的混乱。

25. 问：UserContext 是什么？
答：UserContext = 当前请求的用户信息容器，保存 userId、username、roles、permissions、deptId、tenantId 和 authToken。Service 层需要当前用户或租户时可以统一从这里取。

26. 问：TenantContext 是什么？
答：TenantContext = 当前线程里的租户上下文，MyBatis 多租户插件会从这里读取 tenantId。它的作用是让 SQL 自动带上 tenant_id 条件，减少业务代码手写租户过滤。

27. 问：为什么请求结束要清理 UserContext 和 TenantContext？
答：这些上下文底层依赖 ThreadLocal，而 Web 容器线程会复用。请求结束不清理，下一次请求可能读到上一个用户或租户的信息，结果会出现权限和数据串用。

28. 问：ThreadLocal 是什么？
答：ThreadLocal = 每个线程独立保存一份变量。项目里用它保存一次请求里的用户、租户和权限信息，业务代码不需要层层传 userId、tenantId 参数。

29. 问：TransmittableThreadLocal 是什么？
答：TransmittableThreadLocal = 能把父线程上下文传递到线程池任务里的工具。CloudFlow 有异步审计、异步通知和工作流异步任务，使用它可以让异步线程继续拿到用户和租户信息。

30. 问：ContextTaskDecorator 的作用是什么？
答：ContextTaskDecorator 会在异步任务提交时捕获 UserContext、TenantContext 和请求信息，在线程池执行时恢复，执行结束后清理。它主要解决异步线程里审计日志拿不到真实用户、IP、租户的问题。

31. 问：OpenFeign 是什么？
答：OpenFeign = 微服务之间的声明式 HTTP 调用客户端。HR 服务调用 workflow 的 /start 接口时，只需要写 WorkflowServiceClient 接口，使用起来像本地方法调用。

32. 问：Feign fallback 是干什么的？
答：fallback = 远程服务调用失败时的降级处理。比如 HR 调 workflow 时，如果 workflow 不可用，fallback 可以返回“Workflow 服务无响应”这类明确错误，避免调用方出现空指针或长时间等待。

33. 问：application.yml 里为什么还要 import Nacos 配置？
答：本地 application.yml 放服务名、端口、Nacos 地址这类启动基础配置，Nacos 放更容易变化的公共配置和服务配置。这样部署后修改配置不一定要重新打包服务。

34. 问：Actuator 和 Prometheus 是做什么的？
答：Actuator 提供健康检查、运行状态和指标出口，Prometheus 负责采集和保存这些指标。上线后可以用它们观察接口、JVM、线程、服务健康状态，排查问题会更快。

35. 问：项目里为什么要统一异常处理？
答：统一异常处理能把业务异常、认证异常、参数异常和系统异常转成统一响应格式。前端不用适配各种 Java 异常结构，用户也能看到更清楚的错误提示。

中级题 36-75

36. 问：网关认证的流程可以怎么讲？
答：请求先进入 cloudflow-gateway 的 AuthFilter，白名单路径直接放行。其他接口必须带 Authorization: Bearer token，网关用 TokenService 校验有效后再转发到下游服务，失败就返回 401。

37. 问：网关为什么会删除 X-User-* 这类请求头？
答：X-User-* 这类头如果从客户端传进来，存在被伪造的风险。项目在网关删除这些头，下游统一从 Token 还原登录态，身份来源更可信。

38. 问：下游服务怎么恢复用户信息？
答：下游 MVC 服务通过 UserContextInterceptor 从 Authorization 或 token 参数里取 Token，再调用 TokenService 校验。校验成功后，把用户 ID、角色、权限、部门、租户和数据权限写入 UserContext，Service 层就能直接读取。

39. 问：TokenService 的核心逻辑是什么？
答：登录时 TokenService 用 Sa-Token 创建登录态，把用户信息放到 Session，并返回原始 Token。校验时根据 Token 找登录 ID 和 Session，Token 快过期时按配置自动续期。

40. 问：Token 自动续期有什么用？
答：自动续期能让用户持续操作时不频繁掉线。项目里当 Token 剩余时间低于 refreshTime，就把有效期续回 expiration；长期不操作时仍会过期。

41. 问：多租户 SQL 是怎么自动加上的？
答：MybatisPlusConfig 注册了 TenantLineInnerInterceptor，多租户插件会从 TenantContext 读取当前 tenantId。执行 SQL 时自动追加 tenant_id 条件，业务查询就能默认限制在当前租户内。

42. 问：哪些表可以跳过租户过滤？
答：租户无关的系统表或平台级查询表可以跳过租户过滤，具体由 cloudflow.tenant.ignoreTables 配置控制。代码里也支持通过 TenantContext.setTenantSkip 临时跳过，但必须严格限制调用场景。

43. 问：@TenantIgnore 这类能力适合什么场景？
答：它适合平台管理员查询、租户初始化、系统级统计这类需要跨租户的数据操作。使用后要恢复上下文，否则普通业务查询可能误查全量数据。

44. 问：数据权限和租户隔离有什么区别？
答：租户隔离解决“这个用户属于哪个公司或组织”的边界，数据权限解决“同一个租户里这个用户能看哪些部门或本人数据”的边界。先按租户隔开，再按用户的数据范围收窄。

45. 问：数据权限是怎么接进 MyBatis 的？
答：DataScopeInnerInterceptor 会在查询前检查 Mapper 参数里有没有 DataScope。存在 DataScope 时，它把原 SQL 包成子查询，再根据用户 ID、部门 ID 列表追加过滤条件。

46. 问：DataScope 为空时会怎样？
答：DataScope 为空时，拦截器不会追加数据权限条件。面试时可以补一句：这要求开发者在需要数据权限的 Mapper 参数里显式传 DataScope，避免漏控。

47. 问：为什么 MyBatis 插件顺序要注意？
答：插件顺序会影响最终 SQL 的含义。项目按多租户、数据权限、分页的顺序注册，先确定能查的数据范围，再分页，避免出现分页总数和实际列表不一致。

48. 问：防重复提交怎么实现？
答：RepeatSubmitAspect 会根据用户 ID、请求 URI 和参数摘要生成 Redis Key。第一次请求用 setIfAbsent 写入短期标记，间隔内重复提交时 Key 已存在，就直接拒绝。

49. 问：setIfAbsent 为什么适合做防重复提交？
答：setIfAbsent = Redis 的“Key 不存在才写入”操作，并且可以带过期时间。并发请求同时进来时，只有第一个能写成功，后续请求会识别为重复提交。

50. 问：接口限流怎么实现？
答：RateLimiterAspect 会根据接口名、自定义 Key、IP 或用户 ID 生成限流 Key，再执行 Redis Lua 脚本做计数。超过注解配置的 time 和 count 后，就抛出限流异常。

51. 问：Lua 脚本在限流里有什么用？
答：Lua 脚本能把读取计数、增加计数、设置过期时间放在 Redis 内部一次执行完成。这样高并发下不会出现多个请求同时读到旧计数导致限流失效。

52. 问：项目里的限流是滑动窗口吗？
答：当前脚本更接近固定时间窗口计数：Key 第一次出现时设置过期时间，窗口内不断累加请求次数。回答时可以说明它实现简单、性能好，但窗口边界会有瞬时流量偏大的可能。

53. 问：审计日志是怎么做的？
答：项目通过 @Audit 标记需要审计的方法，AuditAspect 在方法执行前用 SpEL 取旧值，执行后比较新旧值差异并记录。这样能知道谁在什么时候改了哪个业务对象、改了哪些字段。

54. 问：AOP 是什么？
答：AOP = 面向切面编程，具体说就是在不改业务方法主体的情况下，统一插入一些公共逻辑。CloudFlow 的审计、限流、防重复提交、内部接口保护都适合用 AOP 做。

55. 问：为什么日志、限流、防重适合用 AOP？
答：这些能力属于横向能力，很多接口都需要，逻辑也比较固定。用 AOP 后，业务方法可以专注排班、审批、员工这些规则，公共控制统一放在切面里维护。

56. 问：项目里怎么做文件存储？
答：auth 服务里抽象了 FileStorageService，并提供本地存储和 OSS 存储实现。FileStorageRegistry 会按配置选择具体实现，业务上传文件时不用关心底层存到本地磁盘还是对象存储。

57. 问：OSS 是什么？
答：OSS = 对象存储服务，适合保存图片、附件、合同、证件等文件。CloudFlow 的 common-oss 使用 S3 兼容客户端封装，方便对接不同云厂商或兼容对象存储。

58. 问：Excel 模块主要解决什么？
答：cloudflow-common-excel 主要封装导入导出能力，比如读取 Excel、收集错误行、输出导出文件、处理字典和大数字格式。业务服务复用它后，不需要每个模块单独写一套 Excel 工具。

59. 问：敏感字段处理适合放在哪里？
答：敏感字段处理适合放在 common-sensitive、日志输出或返回数据处理层统一做。比如手机号、身份证、薪资、Token 这类字段，统一脱敏能减少业务模块漏处理的风险。

60. 问：HR 排班里的班次创建做了哪些校验？
答：创建班次时会校验同租户 shiftCode 不能重复，休息时长、迟到阈值、早退阈值不能小于 0。还会重新计算工作时长，开始和结束时间不能相同，休息时长也不能大于或等于班次总时长。

61. 问：跨天班次怎么计算工时？
答：代码先用 Duration.between(startTime, endTime) 算分钟数，如果结果小于 0，说明跨天，就加上 24 * 60。最后再减去 breakMinutes，得到实际工作分钟数。

62. 问：为什么删除班次前要检查排班计划？
答：班次被未取消的排班计划引用后，直接删除会导致历史排班和日历展示找不到班次信息。项目在 deleteShift 里先查 SchedulePlan，只要存在非 CANCELLED 引用就阻止删除。

63. 问：批量排班为什么限制 31 天？
答：31 天基本覆盖一个自然月，符合排班业务习惯，也能控制一次请求的写入量。批量排班如果不限制范围，用户选很多员工和很长日期会造成大事务和大量插入。

64. 问：排班计划有哪些状态？
答：当前代码主要有 DRAFT、PUBLISHED、CANCELLED。DRAFT 表示草稿，PUBLISHED 表示已发布并可参与考勤统计，CANCELLED 表示已取消，查询冲突时会排除取消状态。

65. 问：为什么同一天同目标不能重复排班？
答：同一个员工、岗位或部门同一天有多条有效排班，会导致考勤计算不知道按哪个班次算。项目创建排班前会查同 tenantId、targetType、targetId、scheduleDate 下未取消的计划。

66. 问：排班里的 targetType 是什么？
答：targetType = 排班目标类型，当前支持 EMPLOYEE、POST、DEPT。员工排班最精确，岗位排班适合一类岗位统一安排，部门排班适合部门整体班制。

67. 问：HR 为什么要同步部门和岗位？
答：部门和岗位属于组织主数据，HR 的员工档案、排班目标、审批展示都会用到。DeptPostSyncService 负责校验和缓存这些数据，减少每次展示都远程查询 auth 服务。

68. 问：工作流发起审批时 HR 做了什么适配？
答：HR 的 WorkflowServiceClient 会把 HR 自己的 ProcessStartDTO 转成 workflow 的启动请求。它会组装 processDefKey、businessKey、variables，并把业务类型、业务 ID、租户、发起人、标题、回调流 Key 一起传给 workflow。

69. 问：businessKey 有什么用？
答：businessKey = 流程实例和业务单据之间的唯一关联标识。项目里通常用 businessType:businessId，比如 HR_TRANSFER:123，后续查流程、回调、排查日志都能用它串起来。

70. 问：工作流审批回调怎么分发到不同业务？
答：WorkflowCallbackServiceImpl 启动时会收集所有 ApprovalResultHandler，实现类按自己支持的 businessType 注册到 Map。回调到来后，根据 businessType 找处理器，再按 APPROVED 或 REJECTED 调用对应方法。

71. 问：为什么回调线程要显式设置租户？
答：审批回调通常来自异步消息或服务间调用，没有前端登录请求上下文。更新 HR/OA 单据时仍然要按租户隔离，所以回调 DTO 里必须带 tenantId，处理前要补到当前上下文。

72. 问：审批结果为什么只接受 APPROVED 和 REJECTED？
答：这两个值对应业务最核心的通过和驳回分支，处理逻辑也最明确。回调入口先把状态收窄，可以避免 workflow 或消息里传来未知状态后把业务单据改错。

73. 问：工作流里的人员分配策略怎么扩展？
答：新增一个 AssignUserStrategy 实现类，标注为 Spring Bean，在 supports 里声明支持的 approverType，在 resolve 或 resolveMultiple 里返回审批人。AssignUserStrategyFactory 会自动收集实现类并按类型调用。

74. 问：工作流节点处理器怎么扩展？
答：实现 INodeHandler，声明自己的 nodeType，并在 handle 里写节点执行逻辑。NodeHandlerFactory 启动时会自动收集所有处理器，流程运行时按节点类型分发。

75. 问：WebSocket 在项目里适合做什么？
答：WebSocket = 浏览器和服务端之间的长连接，适合服务端主动推送消息。CloudFlow 可以用它推送工作流待办变化、审批通知、系统消息，不需要前端频繁轮询。

高级题 76-100

76. 问：工作流启动流程可以怎么完整描述？
答：可以按链路讲：校验流程 Key，检查发起频率，查当前租户下已发布的最新流程定义，校验发起权限和绑定表单，再创建流程实例。实例创建后记录监控和事件，解析流程模型，找到首个可执行节点并开始执行。

77. 问：工作流为什么要查“已发布的最新版本”？
答：流程定义会持续修改，草稿不能直接给用户发起，旧版本也可能已经被新规则替代。发起新流程时查已发布且版本最高的定义，可以保证用户走的是当前正式规则。

78. 问：流程绑定表单时为什么要校验表单租户？
答：流程定义、当前用户和绑定表单都必须属于同一租户。否则 A 租户的流程可能引用 B 租户的表单，审批时就会出现跨租户数据泄露或脏数据。

79. 问：流程变量为什么要做 JSON 序列化？
答：流程变量是动态 Map，不同业务传的字段不完全一样，存成 JSON 比固定列更灵活。后续节点条件判断、标题展示、业务回调、流程查询都可以复用这些变量。

80. 问：流程标题为什么要做 XSS 清理？
答：XSS = 页面脚本注入，流程标题可能来自前端传入的 _title。后端保存前做 sanitizeXss，可以减少恶意脚本进入流程列表、待办列表和详情页的风险。

81. 问：工作流里的分布式锁适合解决什么问题？
答：分布式锁适合解决多实例同时处理同一任务的问题。比如定时扫描 PENDING 消息时，多个 workflow 实例都会触发任务，Redisson 锁可以保证同一批消息只被一个实例处理。

82. 问：本地消息表是怎么保证一致性的？
答：本地消息表的核心是把业务数据变更和“待处理消息”放在同一个本地事务里提交。事务成功后，定时任务扫描 PENDING 消息并重试处理，成功标记 SUCCESS，失败记录原因和重试次数。

83. 问：本地消息表里的 Propagation.MANDATORY 是什么意思？
答：Propagation.MANDATORY = 调用这个方法时外层必须已经存在事务。recordMessage 这样设置，是为了强制消息记录和业务操作处在同一个事务里，避免只写了消息或只写了业务数据。

84. 问：为什么本地消息表适合这个项目？
答：CloudFlow 里很多跨服务动作属于通知、回调、监控、状态同步，允许短时间延迟但需要最终处理成功。本地消息表实现成本低，不依赖额外事务协调器，配合定时重试比较适合这些场景。

85. 问：最终一致性是什么意思？
答：最终一致性 = 短时间内两个服务的状态可能暂时不同，但系统会通过重试、补偿或对账把状态推进到一致。比如流程已经审批通过，HR 单据回调短暂失败，后续重试成功后状态会补上。

86. 问：消息重试为什么要加指数退避？
答：指数退避 = 失败次数越多，下一次重试等待越久。这样外部服务短暂故障时，系统不会每几秒疯狂重试，能降低依赖服务和自身线程池压力。

87. 问：项目里 Seata 模块的定位是什么？
答：cloudflow-common-seata 是分布式事务能力的预留或公共配置入口。当前 workflow 里更常见的是本地消息表加定时重试，说明项目对很多跨服务动作选择最终一致方案。

88. 问：什么时候更适合用 Seata？
答：当一个业务必须同时写多个服务、多个数据库，并且要求强一致时，可以考虑 Seata。比如两个服务的数据必须同成同败，且业务不能接受补偿延迟，就需要更强的分布式事务控制。

89. 问：什么时候更适合本地消息表？
答：通知、审批回调、状态同步、监控记录这类场景更适合本地消息表。它们短时间失败可以重试，业务能接受最终一致，系统复杂度也比强分布式事务低。

90. 问：权限校验放在网关够不够？
答：网关适合做登录态校验和基础拦截，但业务权限必须在下游服务继续校验。因为接口可能来自 Feign、内部任务或绕过前端的请求，下游仍要检查角色、权限、租户和数据范围。

91. 问：为什么网关和下游服务分别用了 Reactor 和 Servlet 体系？
答：cloudflow-gateway 基于 Spring Cloud Gateway，底层是响应式 WebFlux；auth、workflow、oa、hr 是普通 Spring MVC 服务，使用 Servlet 拦截器。两套体系能共存，但上下文传递方式不同。

92. 问：响应式上下文和 ThreadLocal 有什么差异？
答：响应式上下文跟随 Reactor 调用链传递，ThreadLocal 跟随当前线程保存数据。Gateway 里用 Reactor Context 更合适，下游 MVC 服务里用 UserContext、TenantContext 这类 ThreadLocal 更直接。

93. 问：异步审计日志要注意什么？
答：异步审计要保证用户、租户、IP、User-Agent 能传到异步线程，否则审计记录会缺关键信息。执行结束后还要清理上下文，避免线程池复用导致串用户或串租户。

94. 问：定时任务在多实例部署时要注意什么？
答：多实例部署时，每个实例都会触发同一个 @Scheduled 方法。需要用 Redisson 锁或 Redis 锁控制同一时间只有一个实例处理同一批数据，并设置合理锁过期时间。

95. 问：限流里 Redis 出异常为什么选择放行？
答：限流是保护能力，Redis 短暂异常时如果直接拒绝所有请求，会把 Redis 故障扩大成业务不可用。项目选择记录异常后放行，优先保证核心业务可用。

96. 问：防重复提交里的参数摘要有什么风险？
答：当前实现基于参数 hashCode 拼接后做 MD5，简单场景够用。复杂对象的 hashCode 不一定稳定表达完整内容，关键提交接口可以改成排序后的 JSON 摘要，再生成 Key。

97. 问：DataScopeInnerInterceptor 直接拼 SQL 要注意什么？
答：部门 ID 和用户 ID 必须来自登录态或后端可信上下文，字段名也要由后端固定控制。前端输入不能直接拼进 SQL，尤其是列名、排序字段和权限字段。

98. 问：工作流扩展节点时最重要的约束是什么？
答：节点处理器要明确自己的返回语义：true 表示节点处理完后可以自动继续，false 表示需要等待，null 表示没有处理。新增节点时还要保证异常、日志、变量读写和幂等逻辑清楚。

99. 问：做 HR 审批单据时如何保证业务和流程对得上？
答：发起审批时业务单据要保存 businessType、businessId、processInstanceId 或 businessKey。流程回调时再用这些字段定位单据，并校验租户、当前状态和审批结果，防止回调错单或重复处理。

100. 问：如果让你继续优化这个后端，你会先看哪几处？
答：我会先看 5 个风险点：防重复提交参数摘要是否稳定，排班批量插入是否有数据库唯一约束，流程回调是否完全幂等，DataScope 拼 SQL 的字段是否严格白名单，工作流重试失败是否有告警。它们都属于线上出问题后影响范围比较大的位置。

补充题 101-500

101. 问：你平时怎么理解 Java 里的面向对象？
答：面向对象 = 把业务里的东西拆成对象、属性和行为。CloudFlow 里 Employee、Shift、SchedulePlan 这些 Entity 就是业务对象，Service 再围绕这些对象组织规则。

102. 问：封装在项目里有什么体现？
答：封装 = 把细节收在一个类或模块里，对外只暴露稳定方法。比如 TokenService 把 Sa-Token 的细节封住，业务代码只调用 createToken、verifyToken、deleteToken。

103. 问：继承和接口你更常用哪个？
答：业务扩展里我更常用接口，因为接口更适合表达“我能做什么”。项目里的 ApprovalResultHandler、INodeHandler、AssignUserStrategy 都是接口扩展，比继承一个大父类更灵活。

104. 问：多态在项目里怎么体现？
答：多态 = 同一个接口有多个实现，运行时按实际类型执行。工作流回调按 businessType 找不同 ApprovalResultHandler，就是同一个入口处理不同业务审批结果。

105. 问：为什么很多地方用 final 字段配合构造器注入？
答：final 能表达依赖创建后不再变化，构造器注入能让对象创建时就拿齐依赖。ScheduleServiceImpl 里 mapper 和服务都是 final，读代码时能看出它们是必需依赖。

106. 问：String、StringBuilder、StringBuffer 怎么选？
答：普通不可变文本用 String，循环拼接大量字符串用 StringBuilder，多线程共享拼接才考虑 StringBuffer。项目里大多数接口参数、状态码、Key 前缀用 String 就够了。

107. 问：为什么业务状态一般用字符串或枚举？
答：字符串像 DRAFT、PUBLISHED、CANCELLED 直观，日志和数据库也容易看懂；枚举能把可选状态收口，减少拼错。工作流里 WfProcessStatus、WfTaskStatus 就比散落字符串更稳。

108. 问：LocalDate、LocalTime、LocalDateTime 在项目里怎么区分？
答：LocalDate 表示日期，比如排班是哪一天；LocalTime 表示时间点，比如班次开始和结束时间；LocalDateTime 表示具体时刻，比如流程启动时间、消息重试时间。

109. 问：排班为什么适合用 LocalDate 和 LocalTime？
答：排班核心关心“哪一天”和“几点上下班”，不一定需要时区时间戳。ScheduleServiceImpl 用 LocalDate 处理排班日期，用 LocalTime 计算班次分钟数，表达更贴近业务。

110. 问：BigDecimal 一般用在哪些业务里？
答：BigDecimal 适合金额、税费、薪资这类不能接受浮点误差的计算。CloudFlow 的薪资、个税、费用报销方向应该优先用 BigDecimal，而不是 double。

111. 问：List、Set、Map 在项目里怎么用？
答：List 适合有顺序的数据列表，比如排班计划列表；Set 适合去重，比如角色和权限；Map 适合按 Key 取值，比如流程变量和回调处理器映射。

112. 问：为什么 UserContext 里的 roles 和 permissions 用 Set？
答：角色和权限天然不需要重复，Set 可以自动去重。判断用户是否有某个权限时，Set.contains 的表达也更直接。

113. 问：HashMap 在回调处理器里有什么作用？
答：WorkflowCallbackServiceImpl 把 businessType 当 Key，把 ApprovalResultHandler 当 Value。回调来了以后直接通过业务类型定位处理器，避免写一长串 if else。

114. 问：空指针问题你一般怎么预防？
答：入口先校验必填参数，查询数据库后先判断对象是否为空，再访问字段。项目里像 validateApprovalResult、getShift、updateShift 都是先判断对象存在和租户匹配。

115. 问：为什么不要随便 catch Exception 后不处理？
答：吞掉异常会让调用方以为成功，数据可能已经处于错误状态。项目里有些非核心日志和监控失败会 warn 后继续，核心业务失败会重新抛出让事务回滚。

116. 问：什么时候可以捕获异常后继续执行？
答：当这件事不是主流程，比如记录监控、写审计、设置缓存失败，可以记录日志后继续。发起流程时插入实例是主流程，失败就不能继续。

117. 问：RuntimeException 和业务异常有什么关系？
答：业务异常通常继承 RuntimeException，这样能被事务默认回滚，也能被统一异常处理器接住。HrBusinessException、WorkflowException 就承担这个角色。

118. 问：你怎么看工具类？
答：工具类适合放没有业务状态的通用方法，比如日期、字符串、IP、文件处理。和业务规则强相关的逻辑不要塞进工具类，应该留在 Service 或领域方法里。

119. 问：为什么项目里常量要集中管理？
答：常量集中后可以减少拼错，也方便统一修改。比如 SecurityConstants、CacheConstants、WorkflowCallbackStreamConstants 这类常量能让跨模块字段保持一致。

120. 问：equals 比较对象时要注意什么？
答：对象比较要用 Objects.equals 或先判空，避免空指针。项目里判断租户 ID 是否一致时，用 tenantId.equals 之前要确保 tenantId 不为空。

121. 问：为什么 ID 多用 Long？
答：Long 能覆盖更大的主键范围，适合用户、部门、租户、员工这类长期增长的数据。项目里 userId、tenantId、employeeId 都是 Long，跨服务传递也统一。

122. 问：为什么接口入参不要直接用 Entity？
答：Entity 对应数据库表，直接暴露给前端会让字段边界不清楚。DTO 可以只放本次操作允许提交的字段，比如 ShiftCreateDTO 和 ShiftUpdateDTO。

123. 问：为什么返回前端不要直接返回 Entity？
答：Entity 可能包含内部字段，比如 tenantId、createBy、updateBy 或删除标记。VO 可以整理展示字段，比如排班计划 VO 会补 shiftName、targetName 和状态描述。

124. 问：BeanUtils.copyProperties 有什么风险？
答：它按同名字段复制，字段名相同但含义不同时会误复制。关键字段如 id、tenantId、status、createBy 通常复制后还要手动设置或覆盖。

125. 问：Java Stream 在项目里适合怎么用？
答：Stream 适合列表转换、过滤和简单统计，比如把 SchedulePlan 转成 VO、统计已发布排班天数。复杂业务判断不要写成很长的链式 Stream，调试会困难。

126. 问：为什么有些代码还用 for 循环？
答：for 循环更适合带校验、异常、累积对象的复杂逻辑。批量排班要遍历目标和日期，还要查重和创建计划，用循环更清楚。

127. 问：你怎么理解 Java 里的泛型？
答：泛型 = 让集合或方法声明里面装什么类型，编译期就能检查。R<T>、List<ShiftVO>、Map<String, Object> 都是在告诉调用方返回的数据形状。

128. 问：Map<String, Object> 有什么优缺点？
答：优点是灵活，适合流程变量这种字段不固定的场景；缺点是类型不够明确，取值时要做转换和校验。普通业务入参不建议大量用 Map。

129. 问：Optional 适合项目里大量使用吗？
答：Optional 适合方法返回可能没有值的场景，但不一定要到处用。项目里多数 Mapper 返回对象后直接判空，简单直观。

130. 问：你怎么理解不可变对象？
答：不可变对象 = 创建后状态不再被修改，使用起来更安全。String、LocalDate、LocalTime 都是不可变对象，所以排班时间计算时不会意外改掉原值。

131. 问：Spring 的 IOC 是什么？
答：IOC = 对象创建和依赖管理交给 Spring 容器。项目里 Service、Mapper、配置类都由 Spring 管，业务类只声明自己需要什么依赖。

132. 问：Bean 是什么？
答：Bean = 被 Spring 容器管理的对象。@Service、@Component、@Configuration 标记的类启动后会变成 Bean，其他类可以注入使用。

133. 问：@Component、@Service、@Configuration 有什么区别？
答：它们本质都能注册 Bean，但表达含义不同。@Service 表示业务服务，@Configuration 表示配置类，@Component 表示普通组件。

134. 问：为什么启动类要配置 scanBasePackages？
答：scanBasePackages 告诉 Spring 扫描哪些包下面的 Bean。CloudFlow 多模块都在 com.cloudflow 下，扫描这个根包能把 common 和业务服务都纳入容器。

135. 问：@MapperScan 是干什么的？
答：@MapperScan 会扫描 MyBatis Mapper 接口，让它们能被 Service 注入。auth、workflow、hr 都分别配置了自己的 mapper 包。

136. 问：@EnableFeignClients 是干什么的？
答：它开启 Feign 客户端扫描。HR 服务启动类扫描 com.cloudflow.hr.client 后，WorkflowServiceClient 才能作为服务间调用代理使用。

137. 问：为什么有些启动类排除了 DataSourceAutoConfiguration？
答：项目使用动态数据源和自定义数据源配置，排除默认数据源自动配置可以避免 Spring Boot 按默认规则创建不符合项目要求的数据源。

138. 问：@ConfigurationProperties 有什么用？
答：它把配置文件里的字段绑定到 Java 对象。TenantConfigProperties、SecurityProperties、FileStorageProperties 都用这种方式读取项目配置。

139. 问：为什么配置类比直接 @Value 更适合复杂配置？
答：配置类可以把一组配置收在一起，有默认值和结构，读代码更清晰。租户配置、文件存储配置、安全配置都属于这种情况。

140. 问：Spring Bean 默认是不是单例？
答：默认是单例，一个 Bean 在容器里通常只有一个实例。Service 里不要放每个请求独有的可变状态，用户和租户信息要放 UserContext 这种请求上下文里。

141. 问：单例 Service 里为什么不能放当前用户 ID 字段？
答：Service 是多个请求共享的，字段会被并发请求互相覆盖。当前用户 ID 应该从 UserContext 读取，且请求结束后清理。

142. 问：拦截器和过滤器有什么区别？
答：过滤器更靠近 Web 容器或网关入口，拦截器更靠近 Spring MVC 控制器。Gateway 用 AuthFilter 处理入口认证，下游 MVC 服务用 UserContextInterceptor 恢复用户上下文。

143. 问：Spring AOP 一般拦哪些地方？
答：一般拦 Spring Bean 的方法调用，比如 Controller 或 Service 上的注解方法。项目的日志、审计、限流、防重复提交都属于这种拦截。

144. 问：@Around 和 @Before 有什么差异？
答：@Before 只在方法执行前做事，适合限流和防重复提交；@Around 可以包住整个方法，适合审计里先取旧值、执行方法、再比较新值。

145. 问：为什么事务也依赖代理？
答：@Transactional 是 Spring 通过代理在方法前后开启、提交或回滚事务。同类内部直接调用方法时可能绕过代理，事务注解就不会按预期生效。

146. 问：事务边界怎么定？
答：一个业务动作需要一起成功或一起失败时，就把它放进同一个事务。比如创建排班、发布排班、审批回调更新业务状态都应该有事务边界。

147. 问：只读查询要不要加事务？
答：普通简单查询可以不加。复杂一致性读取或需要固定读取视图时才考虑只读事务，CloudFlow 多数查询通过 Mapper 直接读取即可。

148. 问：事务里可以做远程调用吗？
答：能做但要谨慎，远程调用慢或失败会拉长数据库事务时间。更稳的做法是先保存本地状态，再通过消息、回调或补偿推进跨服务动作。

149. 问：为什么工作流会用本地消息表？
答：跨服务动作不一定能和本地数据库同时成功，本地消息表把“要做的事”先和业务数据一起保存下来。后面定时重试保证最终处理完成，失败也有记录可查。

150. 问：Spring 的 @Async 有什么注意点？
答：@Async 会把方法放到线程池执行，当前请求线程不会等待它完成。异步方法要考虑上下文传递、异常日志和线程池容量。

151. 问：线程池为什么要配置？
答：线程池能控制并发数量、队列长度和线程命名，避免异步任务无限创建线程。workflow 里 auditExecutor、notificationExecutor、workflowExecutor 分开后，更容易隔离不同任务。

152. 问：线程池任务里为什么要清理上下文？
答：线程池里的线程会复用，如果不清理，上一个任务的用户和租户可能污染下一个任务。ContextTaskDecorator 的 finally 里清理就是为了防这个问题。

153. 问：@Scheduled 定时任务有什么风险？
答：单实例时很简单，多实例部署时每个实例都会执行。CloudFlow 的重试任务用 Redisson 锁控制，避免多台服务同时重试同一批消息。

154. 问：@PostConstruct 适合做什么？
答：它在 Bean 初始化完成后执行，适合做一次性注册或缓存准备。WorkflowCallbackServiceImpl 用它把所有 ApprovalResultHandler 注册到 Map。

155. 问：为什么有些依赖用 @Autowired(required = false)？
答：表示这个依赖不是必须的，容器里没有也能启动。比如 TimerSchedulerService 或 dataScopeHandle 这类可选能力，缺失时可以降级。

156. 问：@RestControllerAdvice 有什么作用？
答：它集中处理 Controller 抛出的异常，把异常变成统一 JSON 响应。HR 和 common 里都有异常处理，能让前端拿到稳定错误格式。

157. 问：为什么项目需要统一返回错误码？
答：错误码让前端和排查人员能快速判断错误类型。比如 SHIFT_IN_USE、INVALID_APPROVAL_RESULT 比单纯“操作失败”更有定位价值。

158. 问：Spring Boot 自动配置有什么好处？
答：自动配置会根据依赖和配置创建常用 Bean，比如 Web、Redis、Actuator。项目只需要在必要地方覆盖配置，不必从零搭建。

159. 问：为什么还要写自定义配置类？
答：自动配置只解决通用场景，项目规则需要自己定义。MybatisPlusConfig、SecurityWebMvcConfig、RedisConfig、AsyncConfig 都是为了贴合 CloudFlow 的业务要求。

160. 问：你怎么理解 starter？
答：starter = 一组依赖和自动配置的组合。Spring Boot starter、Sa-Token starter、MyBatis-Plus starter 让项目引入一项能力时更省配置。

161. 问：Maven 父 POM 在项目里有什么价值？
答：父 POM 统一 Java 版本、Spring 版本、第三方依赖版本和插件规则。多模块项目靠它避免 auth、hr、workflow 各用一套版本。

162. 问：BOM 是什么？
答：BOM = 依赖版本清单，导入后同一批框架依赖会使用兼容版本。项目用 Spring Boot、Spring Cloud、Spring Cloud Alibaba、Jackson 和 AWS SDK 的 BOM 控制版本。

163. 问：为什么根 POM 要锁 Jackson 版本？
答：Jackson 被 Spring、Redisson、Swagger 等库共同使用，版本漂移容易出现运行时方法缺失。根 POM 统一锁定能减少依赖冲突。

164. 问：maven-enforcer-plugin 是干什么的？
答：它在构建时检查依赖规则，比如重复依赖、模块版本不一致、低版本传递依赖覆盖。这个项目用它把依赖治理前置到 validate 阶段。

165. 问：dependency analyze 有什么意义？
答：它检查声明了但没用、用了但没声明的依赖。多模块项目依赖多，提前发现依赖问题能减少线上或打包时的隐藏风险。

166. 问：为什么有些 starter 被标记为忽略未使用？
答：starter 经常不被源码直接 import，但它们通过自动配置生效。比如 actuator、MyBatis-Plus starter、Sa-Token starter 不能因为源码没直接引用就删掉。

167. 问：Spring Cloud 在项目里主要解决什么？
答：它解决微服务间注册发现、负载均衡、网关、Feign 调用这些问题。CloudFlow 的服务拆开后，需要这些能力把多个服务连接起来。

168. 问：Spring Cloud Alibaba 在项目里主要做什么？
答：它主要接入 Nacos 的服务发现和配置中心。服务通过 Nacos 找到彼此，也从 Nacos 读取公共配置。

169. 问：为什么每个服务都有 application.yml？
答：每个服务有自己的端口、服务名、Nacos import、数据源和日志配置。公共配置可以放 Nacos，但启动所需的基础信息仍要在本地 yml 里。

170. 问：为什么网关服务用 WebFlux？
答：Spring Cloud Gateway 基于 WebFlux，可以用非阻塞方式处理大量转发请求。它和下游 MVC 服务可以共存，只是上下文传递方式不同。

171. 问：数据库连接池为什么重要？
答：连接池复用数据库连接，避免每次请求都创建连接。高并发下连接池配置不合理，会出现接口慢、连接耗尽或数据库压力过大。

172. 问：MySQL 驱动版本为什么要统一？
答：驱动版本影响连接参数、时区、认证方式和 SQL 行为。项目根 POM 统一 mysql-connector-j 8.0.33，能减少各服务连接行为不一致。

173. 问：MyBatis XML 和注解 SQL 怎么选？
答：简单 CRUD 用 MyBatis-Plus 或注解更快，复杂查询、动态 SQL、批量插入更适合 XML。项目里很多 mapper XML 是为了复杂业务查询和批量操作。

174. 问：为什么 Mapper 不应该写业务判断？
答：Mapper 只负责数据访问，业务规则应该在 Service。比如“只能发布草稿排班”这种规则放在 ScheduleServiceImpl，比放 SQL 里更容易维护。

175. 问：分页插件为什么放最后？
答：分页应该作用在已经加完租户和权限条件的 SQL 上。先分页再过滤会导致页数和数据不准。

176. 问：查询条件为空时要注意什么？
答：要明确是查全部还是不查，不能让空条件误查全表。项目里列表查询通常先固定 tenantId，再按可选条件追加。

177. 问：为什么删除很多时候做状态变更而不是物理删除？
答：业务单据和流程记录常需要追溯，直接物理删除会丢历史。排班计划用 CANCELLED 表示取消，仍能保留操作记录。

178. 问：什么时候可以物理删除？
答：配置类数据且没有被引用时可以物理删除，比如未使用的规则适用范围。删除前要检查引用关系，班次被排班计划引用时就不能删。

179. 问：唯一性校验只靠代码够吗？
答：代码校验能给友好提示，但高并发下仍可能同时通过。关键唯一性最好加数据库唯一索引，比如同租户班次编码、同目标同日期有效排班。

180. 问：为什么 batchInsert 要注意大小？
答：一次插太多会让 SQL 太大、事务太久、锁持有太长。排班批量限制 31 天，是业务和性能之间的保守边界。

181. 问：索引在这个项目里怎么考虑？
答：常用查询字段要建索引，比如 tenant_id、business_key、process_instance_id、schedule_date、target_type、target_id。多租户系统里 tenant_id 通常要放在联合索引前面。

182. 问：为什么多租户表的索引常带 tenant_id？
答：大多数查询都会按租户过滤，tenant_id 能先缩小数据范围。再配合业务字段，比如 tenant_id + schedule_date 或 tenant_id + employee_id，查询会更稳。

183. 问：COUNT 查询加数据权限有什么特殊点？
答：COUNT 也必须按同样权限过滤，否则列表数据和总数会不一致。DataScopeInnerInterceptor 对 COUNT 场景会包一层 SQL 再统计。

184. 问：SQL 包一层子查询有什么代价？
答：可读性下降，复杂 SQL 可能影响优化器选择。数据权限统一拦截很方便，但关键慢 SQL 仍要单独 explain 和优化。

185. 问：N+1 查询是什么？
答：N+1 = 查一批主数据后，又对每条数据单独查一次关联数据。convertToSchedulePlanVO 里按计划查班次和目标名就可能有这种风险，列表很大时要批量预加载。

186. 问：怎么优化排班列表里的 N+1？
答：先收集所有 shiftId、employeeId、postId、deptId，批量查出 Map，再转换 VO 时从 Map 取。这样数据库查询次数从 N 次降到几次。

187. 问：事务里循环更新有什么问题？
答：数据量大时事务时间长，失败回滚成本高，还可能锁住多行数据。publishSchedulePlan 当前逐条校验和更新，数量大时可以考虑批量校验后批量更新。

188. 问：为什么先校验再批量更新更安全？
答：先把所有 planId 的数据查出来，确认租户和状态都合法，再统一更新。这样能避免更新到一半才发现某条不合法。

189. 问：数据库状态字段为什么要有明确流转规则？
答：状态没有流转规则会导致随便改，比如已取消又发布、已通过又驳回。排班只能 DRAFT 发布到 PUBLISHED，取消后不应再当有效排班。

190. 问：你怎么设计一个状态流转？
答：先列出所有状态，再列允许从哪个状态到哪个状态，最后在 Service 里集中校验。审批、排班、流程实例都适合这么做。

191. 问：为什么接口查询要限制时间范围？
答：不限制时间范围容易一次扫大量历史数据，影响数据库和接口响应。排班、日志、审计、流程监控这类列表都应该有时间范围或分页。

192. 问：分页参数要怎么校验？
答：pageNum 和 pageSize 要有默认值和上限，比如 pageSize 不允许无限大。这样能避免前端误传 100000 导致数据库压力过大。

193. 问：Mapper 层返回 null 怎么处理？
答：Service 层要把 null 转成业务语义，比如“班次不存在或无权限访问”。直接让空指针抛到前端，用户和开发都不好定位。

194. 问：为什么 Service 里要重复校验租户？
答：多租户插件能拦大多数查询，但 selectById 这类查询后再确认 tenantId 更直观，也能防止特殊场景绕过插件。关键业务要双保险。

195. 问：selectById 在多租户系统里有什么注意点？
答：只按 id 查可能拿到其他租户的数据，所以查完要校验 tenantId，或者写成 tenant_id + id 的条件查询。项目里很多详情接口都做了租户判断。

196. 问：逻辑删除字段要注意什么？
答：查询、唯一性和引用校验都要考虑删除状态。比如同目标同日期排班，如果取消计划不算冲突，查询就要排除 CANCELLED。

197. 问：为什么不要在 SQL 里拼用户输入字段名？
答：字段名不能用参数占位符安全绑定，直接拼用户输入会有 SQL 注入风险。DataScope 里的字段名必须由后端固定配置，不让前端传。

198. 问：SQL 注入是什么？
答：SQL 注入 = 用户输入被当成 SQL 语句的一部分执行。项目里普通值要用 MyBatis 参数绑定，动态字段、排序字段必须白名单控制。

199. 问：排序字段怎么安全处理？
答：前端传 sortField 时后端要映射成固定字段名，比如 createTime -> create_time。不能直接把前端字符串拼进 order by。

200. 问：怎么判断一个慢接口是数据库问题还是代码问题？
答：先看日志耗时和 SQL，再用 explain 看索引命中；如果 SQL 很快，就看代码是否有循环远程调用、N+1 查询、序列化大对象或锁等待。

201. 问：微服务项目为什么要有网关？
答：网关是所有前端请求的统一入口，可以集中做认证、路由、跨域、限流和日志。CloudFlow 用 cloudflow-gateway 先拦请求，后面的服务就不用每个都重复处理入口逻辑。

202. 问：网关只校验 Token 有效，为什么不直接解析用户信息透传？
答：透传用户信息容易被伪造，也容易和下游登录态不一致。项目选择下游服务从原始 Token 自己恢复登录态，身份来源更统一。

203. 问：网关认证失败返回 401 有什么意义？
答：401 明确表示未登录或 Token 失效，前端可以统一跳登录页。项目 AuthFilter 返回 code 401 和“未授权或Token已过期”，用户体验和排查都更直接。

204. 问：为什么 WebSocket 放在网关白名单？
答：WebSocket 握手阶段和普通 HTTP 认证处理不完全一样，项目让网关放行 /ws/**，下游服务的 HandshakeInterceptor 再处理认证。

205. 问：TenantWebFilter 在网关里做了什么？
答：它从 X-Tenant-Id 请求头取租户 ID，没有就用默认租户 100000，并写入 Reactor Context。这个更偏网关链路上下文，不等同于下游 MVC 的 TenantContext。

206. 问：为什么默认租户要谨慎使用？
答：默认租户能降低本地调试成本，但生产环境如果请求漏传租户，可能把数据落到默认租户。上线时要确认登录态、请求头和租户配置都正确。

207. 问：服务间调用时 Token 怎么传？
答：项目通过 UserContext 保存 authToken，Feign 拦截器可以从上下文取出 Token 放到 Authorization 头里。这样 HR 调 workflow 时能继承当前用户身份。

208. 问：Feign 调用失败时为什么要 fallback？
答：服务调用失败不可避免，fallback 可以把网络错误转成业务可理解的失败。比如 workflow 无响应时，HR 可以返回“Workflow 服务无响应”，而不是抛底层异常。

209. 问：Feign 的 name 为什么要写服务名？
答：name 对应 Nacos 里的注册服务名，Feign 会通过服务发现找到实例地址。cloudflow-service-workflow 就是 HR 调工作流的目标服务名。

210. 问：服务名写错会出现什么现象？
答：Feign 找不到服务实例，调用会失败，表现为连接异常、503 或 fallback。排查时先看 Nacos 服务列表和 application.yml 的 spring.application.name。

211. 问：负载均衡在这个项目里怎么体现？
答：当同一个服务有多个实例注册到 Nacos，Feign 和 Gateway 会通过 loadbalancer 选择其中一个实例。调用方不用写具体 IP。

212. 问：为什么服务配置要放 Nacos？
答：Nacos 配置可以集中管理，也能按服务动态调整。CloudFlow 通过 optional:nacos:cloudflow-common.yaml 和服务专属 yaml 读取配置。

213. 问：optional:nacos 有什么含义？
答：optional 表示配置不存在时不阻断启动，适合本地环境或渐进接入配置中心。生产环境仍要确认关键配置存在。

214. 问：认证服务 auth 主要负责什么？
答：auth 负责登录、验证码、用户、角色、菜单、部门、岗位、字典、租户、文件和系统配置。它是用户身份和系统基础数据的核心服务。

215. 问：登录接口通常要做哪些事？
答：校验验证码和账号密码，查询用户角色权限和租户信息，生成 Token，把登录用户信息写入 Sa-Token Session，再返回前端。

216. 问：验证码为什么要单独处理？
答：验证码能降低暴力登录风险。CloudFlow 里有 CaptchaService 和 SliderPuzzleUtil，说明登录前会先做人机校验。

217. 问：为什么 Token 不直接放完整用户信息？
答：完整用户信息可能变动，也可能太大。项目把登录信息放 Sa-Token Session，Token 只作为钥匙，校验时再取服务端保存的登录信息。

218. 问：JWT 和当前 Sa-Token Session 模式有什么区别？
答：JWT 通常把信息签名后放在 Token 里，服务端少存状态；当前项目用 Sa-Token 把登录态存在服务端 Session，服务端更容易踢人、续期和统一管理在线状态。

219. 问：为什么 createToken 里 setIsConcurrent(false)？
答：它表示同一账号不允许多端并发登录，后登录可能挤掉前登录。这个适合后台管理系统控制账号共享风险。

220. 问：setIsShare(false) 是什么意思？
答：它表示每次登录生成独立 Token，不复用旧 Token。配合不允许并发登录，可以让登录态更清晰。

221. 问：TokenService 里的 normalizeToken 为什么重要？
答：有些地方传 Bearer token，有些地方传原始 token，normalizeToken 统一去掉 Bearer 前缀，避免重复写解析逻辑。

222. 问：getTokenTimeout 返回 -2 通常代表什么？
答：在 Sa-Token 语义里 -2 表示 Token 无效或不存在。项目里看到 -2 就当成未登录或已过期处理。

223. 问：在线用户管理怎么做？
答：可以通过 Sa-Token 搜索 Token，再结合 Session 中保存的登录用户信息展示在线用户。登出或强退时调用 logoutByTokenValue 删除指定 Token。

224. 问：权限字符串一般怎么设计？
答：权限字符串要表达资源和动作，比如 system:user:list、hr:schedule:create。面试时可以说项目把权限放进 UserContext.permissions，接口或页面再按权限控制。

225. 问：角色和权限有什么区别？
答：角色是权限集合的业务分组，比如管理员、人事专员；权限是具体能做的动作，比如新增班次、发布排班。用户绑定角色后间接拥有权限。

226. 问：菜单权限和接口权限有什么关系？
答：菜单权限控制前端能不能看到入口，接口权限控制后端能不能执行动作。只做菜单控制不够，因为用户可以直接请求接口。

227. 问：为什么后端权限必须校验？
答：前端按钮隐藏只是体验控制，不能防止伪造请求。后端必须基于 Token、角色、权限和数据范围判断用户能不能操作。

228. 问：@HasPermission 这类注解适合怎么用？
答：适合标在需要权限控制的方法上，由 AOP 统一判断当前用户是否有指定权限。这样比每个 Controller 手写判断更一致。

229. 问：内部接口怎么保护？
答：项目里有 @Inner 和 InnerAspect，可以限制只有内部调用能访问。内部接口仍要谨慎，不要因为“内部”就跳过租户和业务校验。

230. 问：X-Forwarded-For 取 IP 要注意什么？
答：它可能包含多个代理 IP，通常取第一个；但这个头也可能被伪造，生产环境最好由可信网关覆盖。RateLimiterAspect 里按这个逻辑取 IP。

231. 问：接口按 IP 限流适合什么场景？
答：适合登录、验证码、公开查询这类未登录也能访问的接口。用户未登录时没有 userId，用 IP 是更现实的维度。

232. 问：接口按用户限流适合什么场景？
答：适合登录后业务接口，比如导出、审批提交、批量操作。按用户限流比按 IP 更贴近实际使用人。

233. 问：固定窗口限流有什么缺点？
答：窗口边界附近可能出现瞬时双倍流量，比如前 1 秒末尾和后 1 秒开头都打满。简单系统够用，高要求场景可以升级滑动窗口或令牌桶。

234. 问：令牌桶是什么？
答：令牌桶 = 系统按固定速度放令牌，请求拿到令牌才通过。它能允许一定突发流量，又能控制长期平均速率。

235. 问：防重复提交和限流有什么区别？
答：防重复提交针对“同一个用户同一请求短时间重复点”，限流针对“某接口在一段时间内请求太多”。一个防误操作，一个防过载或攻击。

236. 问：防重复提交为什么要带 URI？
答：同一个用户同时调用不同接口不应该互相影响。URI 加进 Key 后，只限制同一接口的重复提交。

237. 问：防重复提交为什么要带参数摘要？
答：同一接口提交不同内容时可能是合理操作。参数摘要能让“相同内容重复提交”和“不同内容连续提交”有区分。

238. 问：匿名用户防重复提交怎么处理？
答：项目里 userId 为空时使用 anonymous。公开接口如果也要防重，可以再加 IP 或设备标识，否则多个匿名用户可能共用同一维度。

239. 问：Redis Key 命名为什么要加前缀？
答：前缀能区分业务类型，方便排查和批量清理。cloudflow:repeat_submit、cloudflow:rate_limit、sys:txn:idempotent 都是这种思路。

240. 问：缓存 Key 为什么要带租户 ID？
答：同一个业务 ID 在不同租户下可能重复，不带 tenantId 会读到别的租户缓存。涉及业务数据的缓存都要把租户维度放进去。

241. 问：Redis 过期时间怎么选？
答：防重复提交按秒级，限流按窗口时间，登录态按安全配置，缓存按数据变化频率。过短缓存效果差，过长容易读旧数据。

242. 问：缓存穿透是什么？
答：缓存穿透 = 查询一个缓存和数据库都没有的数据，每次都打到数据库。可以缓存空值、做参数校验或用布隆过滤器降低风险。

243. 问：缓存击穿是什么？
答：缓存击穿 = 某个热点 Key 过期瞬间大量请求同时查数据库。可以用互斥锁、提前刷新或逻辑过期处理。

244. 问：缓存雪崩是什么？
答：缓存雪崩 = 大量 Key 同时过期或 Redis 故障，导致请求集中打到数据库。可以给过期时间加随机值，核心缓存分批刷新。

245. 问：Redisson 锁释放要注意什么？
答：拿到锁才释放，释放要放 finally。还要设置合理租约时间，避免服务异常后锁一直不释放。

246. 问：tryLock(1, 50, TimeUnit.SECONDS) 怎么理解？
答：最多等 1 秒拿锁，拿到后锁 50 秒自动过期。TransactionConsistencyService 的定时重试用这个避免多个实例同时扫消息。

247. 问：分布式锁能完全替代数据库唯一约束吗？
答：不能。锁能减少并发冲突，但锁配置、网络和代码路径都可能出问题，关键唯一性仍应靠数据库约束兜底。

248. 问：Redis Lua 脚本为什么是原子的？
答：Redis 执行 Lua 脚本时会一次执行完脚本里的命令，中间不会插入其他命令。限流计数就能避免并发下读写错乱。

249. 问：Redis 挂了系统还能不能用？
答：看功能。认证、缓存、限流、防重和分布式锁都会受影响；项目里限流 Redis 异常选择放行，但 Token 校验依赖 Redis 时登录态会受影响。

250. 问：限流 Redis 异常放行会不会有风险？
答：有风险，短时间内接口少了一层保护。但它避免因为 Redis 故障直接打断所有业务，属于可用性优先的取舍。

251. 问：Token 存 Redis 有什么好处？
答：多实例共享登录态，任一服务都能校验 Token，也能集中踢人和续期。微服务部署时这是比较实用的方式。

252. 问：Redis 序列化要注意什么？
答：序列化方式要统一，否则一个服务写的数据另一个服务读不出来。项目统一 Jackson 版本，也有 RedisConfig，都是为了减少兼容问题。

253. 问：Sa-Token Redis 持久化有什么作用？
答：它把 Sa-Token 的登录态存到 Redis，多实例可以共享 Session。服务重启后只要 Redis 数据还在，登录态就不会立刻丢失。

254. 问：用户上下文为什么不直接从 Redis 每次取？
答：每次业务判断都查 Redis 会增加开销，项目在请求入口解析一次写入 UserContext，后续业务直接读线程上下文。

255. 问：UserContext 会不会过期？
答：UserContext 只活在一次请求或异步任务中，请求结束就清理。真正的登录有效期由 Sa-Token 和 Redis 登录态控制。

256. 问：TenantContext 和 UserContext 里的 tenantId 为什么可能同时存在？
答：UserContext 保存用户登录信息里的租户，TenantContext 给 MyBatis 租户插件读取。项目里要保证两者来源一致，避免查数据时租户不一致。

257. 问：当前代码里回调只 set UserContext.setTenantId，有什么要注意？
答：如果 MyBatis 租户插件只读 TenantContext，就还需要确认 SecurityUtils.getTenantId 或拦截器是否同步到 TenantContext。面试时可以说回调线程必须补齐租户上下文，具体要看项目统一封装。

258. 问：SecurityUtils 在项目里通常做什么？
答：SecurityUtils 是读取当前用户、租户、权限等信息的工具入口，业务代码不用直接关心 UserContext 或 Sa-Token 的细节。

259. 问：多租户默认值 100000 适合生产吗？
答：生产可以保留作为兜底，但不能依赖它区分真实租户。真实请求应该从登录态或明确租户头中拿租户 ID。

260. 问：数据权限类型 0 到 4 可以怎么讲？
答：0 表示全部数据，1 表示自定义部门，2 表示本部门及下级，3 表示本部门，4 表示本人。项目在 UserContext 里保存 dsType 和 dsDeptIds，查询时用 DataScope 控制范围。

261. 问：为什么登录时预计算 dsDeptIds？
答：数据权限查询会频繁用到部门范围，登录时预计算可以减少每次查询都递归部门树。代价是部门权限变更后要刷新登录态或缓存。

262. 问：数据权限变更后旧 Token 怎么办？
答：可以让用户重新登录，或更新 Session 里的权限数据，或强制踢掉相关用户。否则旧 Token 里保存的权限范围可能继续生效一段时间。

263. 问：权限缓存多久合适？
答：后台权限变动不算高频，可以缓存，但变更后要有刷新机制。安全性要求高时，关键权限可以实时查或主动清理缓存。

264. 问：菜单缓存要不要带租户？
答：要带。不同租户可能启用不同菜单或角色配置，不带租户会导致菜单串租户。

265. 问：如何防止越权访问别人的员工信息？
答：先校验 Token，再用租户过滤确保不是别的租户，再用数据权限限制部门或本人范围。详情接口也要按 id 查完后确认 tenantId 和权限。

266. 问：越权分几类？
答：常见有水平越权和垂直越权。水平越权是访问同级别别人的数据，垂直越权是普通用户执行管理员动作。

267. 问：CloudFlow 如何防水平越权？
答：通过租户隔离、数据权限和 Service 层对象归属校验防止用户查到不该看的员工、排班、审批数据。

268. 问：CloudFlow 如何防垂直越权？
答：通过角色权限、接口权限注解和后端业务校验控制用户能不能执行新增、删除、发布、审批等动作。

269. 问：XSS 防护在后端怎么做？
答：对会展示到页面的用户输入做清理或转义，比如工作流标题 sanitizeXss 后再保存。前端展示也要避免直接执行 HTML。

270. 问：密码存储要注意什么？
答：不能明文保存，要使用安全哈希算法和盐。面试时可以说登录服务应该只比较哈希值，日志也不能打印密码。

271. 问：Token 放在哪里更安全？
答：Web 管理后台常放 Authorization 请求头，前端存储要注意 XSS 风险。后端只接受 Bearer Token，不从不可信头里读取伪造用户信息。

272. 问：CORS 是什么？
答：CORS = 浏览器跨域访问控制。前端和网关域名不同时，需要网关或后端配置允许的来源、方法和请求头。

273. 问：CSRF 是什么？
答：CSRF = 利用用户已登录状态伪造请求。纯 Bearer Token 放 Authorization 头时风险比 Cookie 自动携带低，但敏感操作仍要注意来源和权限校验。

274. 问：接口幂等是什么意思？
答：幂等 = 同一个请求执行一次和多次，最终结果一致。审批回调、支付类、创建类接口尤其要考虑重复请求。

275. 问：重复提交和幂等有什么关系？
答：防重复提交是在入口拦一部分重复请求，幂等是在业务层保证重复请求来了也不会造成重复数据。关键接口两者都要考虑。

276. 问：审批回调怎么做幂等？
答：可以用 processInstanceId + businessType + businessId + approvalResult 建唯一处理记录，或者在业务状态已是最终状态时直接返回成功。这样重复回调不会重复改数据。

277. 问：发起流程接口怎么做幂等？
答：可以用 businessKey 唯一约束或先查同业务是否已有运行中流程。否则用户重复点击可能为同一单据发起多个流程。

278. 问：本地消息表里的幂等 Key 为什么只设 5 分钟？
答：这是短期防重复执行的保护，适合防止短时间重复调用。长期幂等还要靠业务唯一键或消息状态表。

279. 问：为什么消息 ID 要用 UUID？
答：UUID 能快速生成全局唯一标识，适合消息表、流程实例这类跨服务追踪。缺点是作为数据库主键可能不如自增 ID 紧凑。

280. 问：UUID 做主键有什么性能问题？
答：随机 UUID 插入 B+Tree 索引时可能造成页分裂和索引碎片。高写入表可以考虑雪花 ID、数据库自增或有序 UUID。

281. 问：雪花 ID 是什么？
答：雪花 ID = 按时间、机器号、序列号生成的长整型唯一 ID。它比随机 UUID 更适合数据库索引排序。

282. 问：为什么流程实例 ID 可以用 UUID？
答：流程实例更强调跨系统唯一和外部引用，写入量通常可控。业务主键和流程实例 ID 可以分开设计。

283. 问：审计日志要记录哪些字段？
答：操作者、租户、操作类型、业务对象、旧值、新值、IP、User-Agent、时间和结果。这样出了问题能还原“谁在什么时候改了什么”。

284. 问：操作日志和审计日志有什么区别？
答：操作日志偏接口动作和访问记录，审计日志偏关键数据变更前后的差异。一个看行为，一个看数据变化。

285. 问：为什么审计日志可以异步写？
答：审计日志不是用户主流程结果，异步写能减少接口等待时间。但关键审计场景要确保失败告警或补偿，不能悄悄丢。

286. 问：敏感信息脱敏怎么做？
答：在返回前端、写日志或导出时把敏感字段替换为部分可见格式，比如手机号保留前三后四。项目 common-sensitive 就是为了统一这类处理。

287. 问：文件上传有什么安全风险？
答：风险包括文件类型伪造、超大文件、路径穿越、恶意脚本和公开访问权限错误。后端要校验大小、扩展名、MIME、存储路径和访问策略。

288. 问：MIME 是什么？
答：MIME = 文件内容类型，比如 image/png、application/pdf。只看扩展名不够，上传校验时扩展名和 MIME 都要考虑。

289. 问：OSS 文件为什么要区分公开和私有？
答：头像、公开图片可以公开读，合同、证件、审批附件应该私有读并通过授权 URL 访问。权限错了会造成数据泄露。

290. 问：下载文件时要注意什么？
答：要校验用户是否有权限访问该文件，不能只靠文件 ID。还要设置正确 Content-Type 和文件名，避免浏览器误执行危险内容。

291. 问：接口导出 Excel 要注意什么？
答：要限制导出范围，检查权限，控制最大行数，敏感字段脱敏，并用异步任务处理大导出。直接全量导出容易拖垮服务。

292. 问：为什么导入 Excel 要做结果对象？
答：导入通常会有部分行失败，ExcelResult 可以记录成功数、失败数和错误行，方便用户修正数据。

293. 问：导入员工数据怎么保证不脏？
答：先逐行校验必填、格式、唯一性和租户归属，再统一入库。失败行要给明确原因，不要让半截错误数据落库。

294. 问：接口文档 Knife4j 有什么用？
答：Knife4j 基于 OpenAPI 展示接口文档，方便前后端联调和测试。统一 DTO、VO 注释后，接口说明会更清楚。

295. 问：为什么接口文档不能替代接口校验？
答：文档只是约定，调用方仍可能传错。后端必须用参数校验和业务校验保证接口安全。

296. 问：日志级别怎么选？
答：debug 记录开发排查细节，info 记录关键业务节点，warn 记录可恢复异常，error 记录失败和需要关注的问题。生产环境不要把 SQL debug 长期开得太大。

297. 问：为什么日志要带业务 ID？
答：业务 ID 能把多条日志串成一次操作链路。比如 processInstanceId、businessId、planId、employeeId 都是排查时的关键线索。

298. 问：链路追踪在微服务里有什么价值？
答：一次前端操作可能经过网关、auth、workflow、hr 多个服务，链路追踪能把它们串起来。没有 traceId 时，只能靠时间和业务 ID 手工查。

299. 问：健康检查接口有什么用？
答：健康检查告诉部署平台服务是否还活着，是否能访问数据库、Redis 等依赖。Actuator 提供这类基础能力。

300. 问：Prometheus 指标主要看什么？
答：常看请求耗时、请求量、错误率、JVM 内存、线程、数据库连接和 Redis 状态。业务上还可以加流程待办数、回调失败数、消息重试数。

301. 问：工作流模块在 CloudFlow 里负责什么？
答：它负责流程定义、流程发起、任务审批、会签、节点执行、流程版本、模板、监控、通知和回调。HR 和 OA 业务把审批交给 workflow，自己只关心业务单据状态。

302. 问：流程定义和流程实例有什么区别？
答：流程定义是审批规则模板，比如请假流程怎么走；流程实例是某个具体单据发起后的运行记录，比如张三的 2026-05-03 请假申请。

303. 问：为什么流程定义要有版本？
答：审批规则会变，但已经发起的流程不能被新规则随便影响。新发起用最新已发布版本，老实例继续按它启动时的定义运行。

304. 问：流程发布前要校验什么？
答：要校验模型 JSON 合法、开始节点和审批节点完整、节点连线可达、审批人规则可解析、表单绑定存在、权限配置合理。否则发布后用户发起会在运行时失败。

305. 问：流程模型为什么用 JSON？
答：前端流程设计器天然生成结构化 JSON，后端保存后可以解析节点、连线和配置。JSON 灵活，适合不同类型节点扩展。

306. 问：WorkflowGraphModelResolver 这类解析器做什么？
答：它把前端传来的流程模型解析成后端可运行的图结构，找到首个可执行节点和后续流转关系。这样节点执行服务不用直接面对原始 JSON。

307. 问：节点执行服务一般做什么？
答：它根据当前节点类型找到处理器，创建任务或自动执行节点，再判断是否继续流转。人工审批节点通常等待用户处理，通知或脚本节点可能自动往下走。

308. 问：人工节点和自动节点有什么区别？
答：人工节点要生成待办任务等人处理，自动节点由系统直接执行逻辑。项目里的 ManualNodeHandler、NotificationNodeHandler、ScriptNodeHandler 就代表不同节点类型。

309. 问：会签是什么？
答：会签 = 一个审批节点需要多个人一起处理，根据规则判断全部同意或达到比例后才继续。项目里有 CountersignServiceImpl 和会签任务、投票相关 Mapper。

310. 问：或签是什么？
答：或签 = 多个审批人中任意一个人处理后即可继续。实现时要在第一个有效审批后关闭其他待办，避免重复推进流程。

311. 问：审批人找不到怎么办？
答：要有明确策略，可以报错、转管理员、转发起人上级或挂起流程。项目里策略工厂解析失败会返回 null 或空列表，调用方要决定回退逻辑。

312. 问：审批人策略为什么用工厂？
答：不同审批人来源差异大，有用户、角色、部门、部门负责人、发起人等。工厂统一入口，新增规则只加实现类，不改主流程代码。

313. 问：节点处理器为什么也用工厂？
答：节点类型会不断扩展，工厂按 nodeType 分发处理逻辑。新增定时、脚本、子流程等节点时，不需要改一堆 if else。

314. 问：脚本节点有什么风险？
答：脚本节点能执行动态逻辑，风险是安全边界、执行超时、资源消耗和非法访问。项目里有 ScriptExecutionPolicy 和 SafetyChecker，说明需要限制脚本能力。

315. 问：定时节点怎么实现比较稳？
答：把到期任务写入 Redis ZSet 或数据库，定时扫描到期项，用分布式锁防重复消费。执行失败要能重试，节点状态要能追踪。

316. 问：流程撤回要检查什么？
答：要检查发起人权限、流程是否还在运行、当前节点是否允许撤回，以及撤回后任务和业务状态如何处理。不能只改实例状态。

317. 问：流程作废和撤回有什么区别？
答：撤回一般是发起人把未完成流程收回，作废更像管理员或业务方终止实例。两者权限、原因记录和业务状态处理可能不同。

318. 问：流程暂停有什么用？
答：暂停可以暂时阻止任务继续推进，适合异常处理或业务冻结。恢复后再按原节点继续执行。

319. 问：流程监控要看哪些指标？
答：看实例数量、运行中数量、超时任务、节点耗时、审批通过率、异常告警和待办积压。项目 workflow monitor 相关 Mapper 和 Controller 就服务这些场景。

320. 问：任务超时提醒怎么做？
答：定时任务扫描即将超时或已经超时的任务，生成提醒或告警。提醒要避免重复发送，可以记录提醒时间或提醒次数。

321. 问：流程通知为什么适合异步？
答：通知失败不应该阻塞审批主流程，异步能降低接口耗时。失败要记录日志，重要通知可以进入消息表重试。

322. 问：流程事件发布有什么价值？
答：流程启动、任务完成、流程结束这些事件可以解耦监控、通知、回调和日志。主流程只发布事件，监听器处理附加动作。

323. 问：全局监听器适合处理什么？
答：适合处理所有流程都需要的通用动作，比如创建记录、状态变更记录、通知和监控。业务专属逻辑还是走业务回调处理器。

324. 问：workflow 和 HR/OA 为什么不要互相强耦合？
答：工作流是通用引擎，HR/OA 是业务服务。workflow 不应该直接依赖每个业务表，业务方通过 businessKey、variables 和回调处理自己的状态。

325. 问：流程回调用 Redis Stream 有什么好处？
答：Redis Stream 能保存消息、支持消费组和失败重试，适合把 workflow 审批结果异步推给 HR/OA。相比直接同步调用，抗抖动能力更强。

326. 问：回调里为什么要带 businessType？
答：businessType 告诉业务服务这是哪类单据，比如调岗、请假、报销。服务才能找到对应处理器执行正确的通过或驳回逻辑。

327. 问：回调里为什么要带 tenantId？
答：回调线程没有前端请求上下文，但更新业务单据必须知道租户。tenantId 是防止跨租户误更新的关键字段。

328. 问：回调失败后应该怎么办？
答：记录失败原因，保留消息，定时重试，超过次数后告警和人工处理。不能简单丢弃，否则流程已经结束但业务状态没更新。

329. 问：流程启动成功但业务保存失败怎么办？
答：正常设计应先保存业务草稿，再发起流程并回写实例 ID；如果回写失败，要能按 businessKey 查询流程并补偿，或作废多余流程。

330. 问：业务保存成功但流程启动失败怎么办？
答：业务单据保持草稿或发起失败状态，让用户重试。不要把单据直接标成审批中。

331. 问：审批通过后业务状态怎么改？
答：处理器根据 businessType 找到单据，校验租户和当前状态，把状态从审批中改成已通过，并执行业务落地动作，比如调岗生效或请假确认。

332. 问：审批驳回后业务状态怎么改？
答：一般从审批中改成已驳回或退回修改，并记录驳回原因。是否允许再次提交由业务状态机决定。

333. 问：HR 模块主要有哪些业务？
答：员工、招聘、入职、转正、调岗、离职、考勤、排班、薪资、社保、个税、绩效、汇报线、岗位和组织同步。它覆盖人事管理的核心流程。

334. 问：OA 模块主要有哪些业务？
答：公告、日程、知识、合同、印章、证照借用、费用、付款、采购、出差、资产、车辆、会议室、值班、通讯录和风险提醒。它偏企业日常办公协同。

335. 问：HR 和 OA 为什么都需要工作流？
答：这些业务很多都需要审批，比如请假、加班、调岗、费用报销、合同用印。工作流统一后，不同业务不用各自写一套审批引擎。

336. 问：排班规则的 ruleType 怎么理解？
答：ruleType = 排班制度类型，代码支持 FIXED、ROTATION、FLEXIBLE、COMPREHENSIVE，对应固定班、轮班、弹性工时和综合工时。

337. 问：为什么规则和计划要分开？
答：规则是长期制度，计划是具体某一天安排。分开后可以用规则生成计划，也可以对某些日期做手工调整。

338. 问：排班计划为什么支持员工、岗位、部门三个目标？
答：员工排班最精确，岗位排班适合按岗位统一安排，部门排班适合部门整体班制。不同粒度能覆盖更多业务场景。

339. 问：部门排班和员工排班冲突怎么处理？
答：通常要定义优先级，比如员工个人排班优先于岗位，岗位优先于部门。当前代码主要负责创建和查询，后续考勤计算时应明确覆盖规则。

340. 问：排班计划发布前应该检查什么？
答：检查计划存在、属于当前租户、状态是草稿、班次有效、目标存在、同一天没有冲突。代码里已校验租户和草稿状态，复杂冲突可以继续增强。

341. 问：取消排班为什么不直接删除？
答：取消是业务动作，保留记录能追溯谁取消了哪天排班。删除会让历史不可查，也可能影响考勤解释。

342. 问：排班日历怎么统计预计工时？
答：先查某员工某月的排班计划，再取已发布计划对应班次的 workMinutes 累加，最后除以 60 得到小时数。

343. 问：跨天班次会影响考勤吗？
答：会。比如 22:00 到 06:00 属于夜班，打卡计算要跨日期处理，不能只按当天 00:00 到 23:59 判断。

344. 问：迟到阈值和早退阈值有什么作用？
答：它们定义允许的缓冲分钟数。比如迟到阈值 15 分钟，员工 09:10 打卡可能不算迟到，超过阈值才算异常。

345. 问：休息时长为什么不能大于班次总时长？
答：否则工作时长会变成 0 或负数，考勤和薪资计算都没有意义。ScheduleServiceImpl 明确抛 INVALID_BREAK_MINUTES。

346. 问：班次颜色字段有什么用？
答：颜色主要服务前端日历展示，不影响核心计算。默认颜色 #1890ff 能保证新班次即使没传颜色也能正常显示。

347. 问：排班计划的 createBy 和 updateBy 为什么重要？
答：它们记录谁创建和修改了计划，方便审计和追责。批量排班时同样要写入当前用户 ID。

348. 问：员工不存在时为什么抛“无权限访问”？
答：对外统一说“不存在或无权限访问”能减少信息泄露，避免用户通过错误信息判断某个 ID 在别的租户是否存在。

349. 问：部门和岗位缓存未命中怎么办？
答：可以先触发同步或查询 auth 服务，再放入缓存。ScheduleServiceImpl 的 getDeptFromCacheOrSync 就是缓存未命中时补一次同步思路。

350. 问：组织主数据同步为什么要考虑缓存？
答：部门和岗位名称在列表展示里频繁使用，每条都远程查 auth 会很慢。缓存能减少 Feign 调用和数据库压力。

351. 问：组织缓存什么时候失效？
答：部门或岗位变更、删除、租户切换或定时刷新时应该失效。否则 HR 展示可能还是旧名称。

352. 问：请假、加班、出差这类单据怎么抽象？
答：它们都可以有单据号、申请人、部门、时间范围、原因、状态、流程实例 ID、审批意见和租户字段。差异字段放在各自业务表。

353. 问：单据号怎么生成？
答：可以按业务前缀 + 日期 + 序列号生成，比如 LEAVE202605030001。要考虑并发下序列唯一，最好用 Redis 自增或数据库序列表。

354. 问：为什么业务表要存 processInstanceId？
答：前端查看单据时可以跳到流程进度，回调时也能反查业务单据。它是业务和 workflow 的直接关联字段。

355. 问：为什么流程变量里还要放 businessId？
答：workflow 自己也需要知道这个实例对应哪个业务对象，方便回调和展示。businessKey 是字符串关联，variables 可以放更多业务上下文。

356. 问：业务状态和流程状态不一致怎么办？
答：用对账任务按 businessKey 或 processInstanceId 比对，发现流程已结束但业务仍审批中就补偿处理。关键链路要有告警。

357. 问：审批撤销后业务怎么处理？
答：业务单据一般从审批中回到草稿或已撤销，流程实例作废，并记录撤销原因。已经生效的业务要看能否反向补偿。

358. 问：HR 调岗审批通过后要做什么？
答：更新员工部门、岗位、职级或汇报线，记录调岗生效日期和历史。还要保证这些更新在同一事务里完成。

359. 问：离职审批通过后要做什么？
答：更新员工状态为离职，记录离职日期，处理交接、账号禁用、权限回收和薪资结算。流程通过只是触发点，业务落地仍在 HR。

360. 问：转正审批通过后要做什么？
答：更新员工试用期状态、转正日期、岗位或薪资信息，保留转正申请记录。驳回时保留员工当前试用状态。

361. 问：薪资计算最需要注意什么？
答：金额精度、税前税后、社保公积金、个税专项扣除、考勤扣款和状态版本。薪资数据敏感，权限和审计也要严格。

362. 问：个税配置为什么要有生效时间？
答：税率、扣除项和政策可能变化，历史薪资应按当时配置计算。配置没有生效时间会导致重算历史数据不准确。

363. 问：社保方案为什么不能随便删除？
答：员工社保记录可能引用方案，删除会导致历史缴费无法解释。应该先检查引用，或用停用状态代替删除。

364. 问：考勤记录和排班计划怎么关联？
答：考勤计算会根据员工、日期找到对应排班计划和班次，再用打卡时间判断迟到、早退、缺勤和加班。

365. 问：没有排班计划时考勤怎么处理？
答：要有默认规则，比如按标准班制、按部门规则或标记为未排班。不能直接算异常，规则要和业务方确认。

366. 问：OA 合同审批通过后要做什么？
答：更新合同状态、归档合同文件、记录签署信息和风险提醒。合同金额、供应商、有效期这些字段还会影响后续提醒。

367. 问：用印审批通过后要做什么？
答：更新用印申请状态，记录印章、次数、文件和经办人。印章属于高风险资源，审批、日志和附件权限都要严。

368. 问：费用报销审批通过后要做什么？
答：更新报销单状态，可以生成付款申请或财务待办。金额字段要用 BigDecimal，附件和发票要保留。

369. 问：采购申请和付款申请怎么衔接？
答：采购审批通过后可以生成采购执行记录或付款建议，付款申请再走财务审批。两者通过业务单号或来源单据关联。

370. 问：公告和通知有什么区别？
答：公告偏长期展示和全员阅读，通知偏某个事件触发给特定用户。流程待办通知就属于事件通知。

371. 问：知识库文档要注意什么？
答：要处理分类、权限、附件、版本和搜索。公开知识和部门内部文档访问范围不同，不能只按文档 ID 读取。

372. 问：会议室预约要注意什么？
答：要检查时间冲突、会议室状态、预约人权限和取消规则。并发预约同一时间段时要用数据库约束或锁避免冲突。

373. 问：车辆申请要注意什么？
答：要校验车辆是否可用、时间是否冲突、驾驶人和归还状态。费用报销和车辆使用记录可以关联。

374. 问：资产管理要注意什么？
答：资产状态要清楚，比如闲置、领用、维修、报废。资产领用和归还最好有审批或操作记录。

375. 问：风险提醒模块适合怎么做？
答：按合同到期、证照归还、采购超期、流程超时等规则生成提醒，支持状态流转和负责人处理。提醒要避免重复创建。

376. 问：系统配置为什么放 auth 服务？
答：系统配置属于基础平台能力，很多服务会读取它。TokenService 通过 SysConfigHelper 读取 token 过期时间，就是跨模块配置使用。

377. 问：动态配置有什么风险？
答：配置变更会影响运行中的服务，比如 Token 过期时间、租户开关、限流参数。生产修改要有审核和回滚手段。

378. 问：字典表有什么用？
答：字典表管理状态、类型、枚举展示值。前端显示“启用/禁用”“固定班/轮班”这类文本时，可以减少硬编码。

379. 问：字典值和代码枚举怎么配合？
答：核心流转状态建议代码枚举兜底，字典负责展示和配置。只靠字典会让业务规则太松，只靠枚举又不够灵活。

380. 问：租户管理要有哪些字段？
答：租户名称、状态、套餐或权限、联系人、有效期、默认管理员和资源限制。多租户系统还要考虑租户停用后的登录和数据访问。

381. 问：租户停用后应该发生什么？
答：阻止该租户用户登录和业务操作，保留历史数据。已经在线用户可以强制下线或在下一次请求时拦截。

382. 问：多租户系统备份要注意什么？
答：要能按全库备份，也要考虑按租户导出或恢复。恢复单个租户时 tenant_id 是关键边界。

383. 问：多租户系统里管理员分几类？
答：可以分平台管理员和租户管理员。平台管理员管理租户和系统级配置，租户管理员只管理自己租户内用户和业务。

384. 问：为什么平台管理员查询要跳过租户？
答：平台管理员需要看所有租户的配置或运营数据。跳过租户必须受严格权限控制，并且操作要写审计日志。

385. 问：你怎么设计一个新的审批业务？
答：先建业务表和状态机，再确定流程 Key 和业务变量，然后写发起流程逻辑和回调处理器，最后补权限、租户、日志、幂等和异常处理。

386. 问：你怎么判断一个业务要不要接工作流？
答：看它是否需要多人审核、状态留痕、可撤回、可驳回和审批记录。简单配置变更可能只要权限控制，不一定都要走流程。

387. 问：工作流变量里能不能放敏感数据？
答：尽量不放，变量可能被流程监控、日志或接口展示。敏感信息应该只放业务表，流程变量放必要标识和摘要。

388. 问：流程表单和业务表单有什么区别？
答：流程表单服务流程展示和审批填写，业务表单服务业务落库和计算。两者可以绑定，但业务数据最终要以业务表为准。

389. 问：流程审批意见保存在哪里合适？
答：任务历史或审批记录表里保存处理人、结果、意见、时间和附件。业务表只保存最终状态和必要摘要。

390. 问：审批附件要怎么处理？
答：附件先进入文件服务或 OSS，审批记录只保存文件 ID 或 URL。下载时要根据单据权限校验，不允许直接公开访问。

391. 问：流程任务待办列表怎么查？
答：按当前用户 ID、角色或候选人规则查未完成任务，再关联流程实例标题、发起人、业务类型和时间。要带租户和分页。

392. 问：已办列表怎么查？
答：从任务历史或处理记录按处理人查，展示处理结果和处理时间。已办数据通常增长很快，必须分页和按时间筛选。

393. 问：流程抄送怎么理解？
答：抄送是让相关人知晓流程，不要求审批。实现时可以生成抄送记录或通知，不影响流程主线状态。

394. 问：子流程有什么用？
答：子流程把复杂流程拆成可复用的一段，比如采购流程里嵌入财务审核流程。实现时要处理父子实例状态同步。

395. 问：流程导入导出要注意什么？
答：要校验 JSON 结构、版本兼容、分类、表单引用、节点类型和冲突处理。导入前不能直接覆盖线上已发布流程。

396. 问：流程版本对比有什么价值？
答：能看出新旧版本节点、审批人、条件和表单变化，方便发布前评审。项目有 VersionComparisonServiceImpl，说明支持这类能力。

397. 问：流程模板适合什么场景？
答：适合把常用审批流程沉淀出来，比如请假、报销、采购。新租户或新业务可以基于模板快速创建流程。

398. 问：流程权限包括哪些？
答：至少包括谁能发起、谁能审批、谁能查看、谁能管理定义。项目在发起流程时会校验 startPermissionType 和 startPermissionValue。

399. 问：流程监控异常怎么告警？
答：可以按超时、重试失败、回调失败、节点执行异常生成告警，推给管理员或运维。告警要有 businessKey 和 instanceId，方便定位。

400. 问：面试官问工作流难点，你怎么回答？
答：我会讲 3 点：流程模型解析和节点扩展、审批人与权限的动态计算、业务状态和流程状态的一致性。然后结合 HR 发起审批和回调处理说明具体落地。

401. 问：本地启动后第一个排查点是什么？
答：先看服务是否注册到 Nacos，再看端口是否正常、Actuator 健康检查是否通过。微服务项目不要一上来就查业务代码，先确认服务真的活着。

402. 问：接口 401 怎么排查？
答：先看请求有没有 Authorization: Bearer Token，再看 Token 是否过期或被踢下线，最后看网关白名单和下游 UserContextInterceptor 是否正确恢复登录态。

403. 问：接口 403 怎么排查？
答：403 通常是权限不足。先看当前用户角色和权限，再看接口上的权限要求，最后确认菜单权限和后端权限字符串是否一致。

404. 问：接口 404 怎么排查？
答：先确认前端请求路径，再看网关路由是否配置到对应服务，最后看 Controller 的 RequestMapping 是否和 Feign 或前端路径一致。

405. 问：接口 500 怎么排查？
答：先看后端 error 日志里的异常堆栈和业务 ID，再定位是参数、数据库、空指针、远程调用还是事务问题。不要只看前端提示。

406. 问：服务注册不上 Nacos 怎么排查？
答：检查 Nacos 地址、命名空间、账号密码、网络连通性和 spring.application.name。再看启动日志里 discovery 相关错误。

407. 问：配置读不到 Nacos 怎么排查？
答：检查 spring.config.import、dataId 名称、文件后缀、命名空间和 refresh 配置。CloudFlow 里服务专属配置和 cloudflow-common.yaml 都要确认。

408. 问：数据库连接失败怎么排查？
答：检查 MySQL 地址、端口、账号密码、库名、驱动版本和网络权限。再看是否导入了对应 DB 脚本。

409. 问：Redis 连接失败会影响哪些功能？
答：会影响登录态、缓存、限流、防重复提交、分布式锁和消息相关能力。排查时先连 redis-cli，再看服务配置和序列化错误。

410. 问：Feign 调用超时怎么排查？
答：先看目标服务是否注册和健康，再看网关是否绕错路径，最后看目标接口耗时、数据库慢 SQL 和 Feign 超时配置。

411. 问：流程发起失败怎么排查？
答：先看流程定义是否已发布，再看 processDefKey 是否正确、用户是否有发起权限、绑定表单是否存在、模型 JSON 是否能解析。

412. 问：审批回调没生效怎么排查？
答：看 workflow 是否发出回调消息，HR/OA 是否消费到，businessType 是否有处理器，tenantId、businessId、processInstanceId 是否完整。

413. 问：查不到数据但数据库有数据怎么排查？
答：先看 tenant_id 是否匹配，再看数据权限范围，再看查询条件和状态过滤。多租户项目里租户不一致是高频原因。

414. 问：同一个接口本地正常线上慢怎么排查？
答：看线上数据量、索引、网络、Redis、数据库连接池、日志级别和 JVM 指标。线上慢通常和数据规模或依赖服务有关。

415. 问：如何排查 N+1 查询？
答：打开 SQL 日志或统计 Mapper 调用次数，看列表接口是否每条数据都额外查班次、员工、部门或岗位。发现后改成批量查询 Map。

416. 问：如何排查事务没回滚？
答：看异常有没有被吞掉，方法是不是 public，调用是不是经过 Spring 代理，异常类型是否匹配 rollbackFor。还要确认数据源和事务管理器正确。

417. 问：如何排查异步任务拿不到用户？
答：看线程池是否使用 ContextTaskDecorator 或 TTL 包装，异步方法是否从请求线程提交，UserContext 是否在提交前已经有值。

418. 问：如何排查定时任务重复执行？
答：看服务实例数量和分布式锁是否生效，锁 Key 是否唯一，任务执行时间是否超过锁过期时间。多实例部署时这是常见问题。

419. 问：如何排查 Token 明明没过期却失效？
答：看是否开启单账号不并发登录、是否被其他登录挤掉、Redis 是否清理了登录态、Sa-Token 配置是否变更。

420. 问：如何排查跨租户数据问题？
答：查请求头、Token Session 里的 tenantId、UserContext、TenantContext 和 SQL 实际拼接条件。关键是确认每一层的租户 ID 是否一致。

421. 问：单元测试适合测什么？
答：适合测纯业务方法、规则校验、状态流转和工具类，比如班次工时计算、规则类型校验、审批回调参数校验。

422. 问：集成测试适合测什么？
答：适合测 Controller、Service、Mapper、数据库和 Redis 共同工作的链路。比如发起流程、创建排班、发布排班这类跨层逻辑。

423. 问：工作流测试重点是什么？
答：重点测流程启动、审批通过、驳回、撤回、会签、超时、回调和重复回调。每个状态流转都要有断言。

424. 问：HR 排班测试重点是什么？
答：测试班次时间计算、跨天班次、重复排班、批量 31 天限制、发布草稿、取消计划和租户隔离。

425. 问：权限测试重点是什么？
答：测试未登录、无权限、跨租户、跨部门、本人权限和管理员权限。只测正常管理员路径不够。

426. 问：接口测试时为什么要准备不同角色用户？
答：不同角色能覆盖不同权限和数据范围。比如 HR 专员、部门经理、普通员工、平台管理员看到的数据应该不同。

427. 问：Mock 在测试里有什么用？
答：Mock = 用假的依赖替代真实依赖。测试 HR 发起流程时，可以 Mock WorkflowServiceClient，避免每次都启动 workflow 服务。

428. 问：为什么测试里要固定时间？
答：排班、考勤、Token、消息重试都和时间有关。固定时间能让测试结果稳定，不会因为日期变化导致断言失败。

429. 问：如何测试防重复提交？
答：连续发送两次相同用户、URI、参数的请求，第一次成功，第二次在间隔内失败；间隔过后再提交应成功。

430. 问：如何测试限流？
答：在配置窗口内连续请求超过 count 次，最后一次应被拒绝。还要测 IP 维度和用户维度是否互不影响。

431. 问：如何测试本地消息表重试？
答：先让处理逻辑失败，确认消息保持 PENDING 或 FAILED，再恢复依赖服务，触发定时任务后消息变 SUCCESS。

432. 问：如何测试 Feign fallback？
答：让目标服务不可用或返回超时，调用方应该走 fallback 并返回明确错误信息。不能出现空指针或长时间卡死。

433. 问：代码评审时你会重点看什么？
答：看租户和权限是否漏掉，事务边界是否合理，状态流转是否完整，异常是否被吞，日志是否包含敏感信息，查询是否可能慢。

434. 问：新增接口时你会检查哪些点？
答：路径、方法、入参 DTO、参数校验、权限注解、租户隔离、Service 事务、异常返回、日志、接口文档和测试。

435. 问：新增表时你会检查哪些点？
答：主键、tenant_id、状态字段、创建更新时间、创建更新人、索引、唯一约束、逻辑删除、字段注释和历史追溯需求。

436. 问：新增缓存时你会检查哪些点？
答：Key 命名、租户维度、过期时间、序列化、缓存击穿、数据变更后的删除或刷新策略。

437. 问：新增定时任务时你会检查哪些点？
答：执行频率、是否多实例重复执行、单次处理数量、失败重试、日志、告警和幂等。

438. 问：新增异步任务时你会检查哪些点？
答：线程池隔离、上下文传递、异常处理、任务堆积、超时和业务是否允许最终一致。

439. 问：新增审批业务时你会检查哪些点？
答：流程 Key、业务状态、发起权限、回调处理器、幂等、流程实例 ID 保存、驳回和撤销处理。

440. 问：性能优化先做什么？
答：先定位瓶颈，再优化。没有指标就不要盲目改代码，先看接口耗时、SQL、JVM、Redis、Feign 调用和线程池。

441. 问：数据库优化优先看什么？
答：先看慢 SQL 和 explain，确认是否走索引、扫描行数、排序和临时表。再考虑改索引、改查询或拆分页。

442. 问：接口响应慢但 SQL 不慢怎么办？
答：看是否有远程调用、循环查询、文件处理、JSON 序列化大对象、锁等待或线程池排队。慢接口不一定是数据库问题。

443. 问：如何控制大列表返回？
答：必须分页，限制 pageSize，必要时只返回摘要字段。详情数据放详情接口，不要列表一次返回全部。

444. 问：导出大数据怎么优化？
答：用异步导出、分批查询、流式写 Excel、生成文件后通知下载。同步接口直接导出大表容易超时和占内存。

445. 问：批量导入怎么优化？
答：分批校验、分批写入、错误行单独收集，避免一行失败导致所有上下文丢失。大导入可以做异步任务。

446. 问：JVM 内存问题怎么观察？
答：看堆内存、GC 次数和耗时、线程数、对象增长。导出、导入、JSON 大对象和缓存都可能造成内存压力。

447. 问：线程池满了会怎样？
答：任务会排队或被拒绝，表现为异步通知延迟、流程推进慢、接口等待。线程池要有容量、队列和拒绝策略监控。

448. 问：数据库连接池满了会怎样？
答：请求拿不到连接，会变慢或超时。要看慢 SQL、事务过长、连接泄漏和连接池最大值配置。

449. 问：日志太多有什么影响？
答：会增加磁盘 IO、占用空间、影响接口性能，也会让排查困难。生产环境要控制 debug 和 SQL 日志。

450. 问：怎么设计错误提示更友好？
答：前端用户看到业务语言，比如“该日期已存在排班计划”；日志里保留技术细节，比如 planId、tenantId 和异常堆栈。

451. 问：为什么不要把堆栈直接返回前端？
答：堆栈会暴露代码结构、类名、SQL 和服务器信息。前端只需要错误码和可理解的信息，堆栈留在后端日志。

452. 问：灰度发布要注意什么？
答：新旧版本可能同时运行，数据库字段、消息格式、流程变量要兼容。不能让新版本写的数据旧版本完全读不了。

453. 问：数据库变更怎么做更稳？
答：先加兼容字段，再发代码使用新字段，确认稳定后再清理旧字段。删除字段和改字段类型要特别谨慎。

454. 问：配置变更怎么上线更稳？
答：先在测试环境验证，再小范围灰度，保留回滚值。像认证过期时间、限流阈值、租户开关会直接影响用户。

455. 问：服务启动顺序为什么重要？
答：依赖服务没启动时，调用方可能启动成功但业务调用失败。CloudFlow 本地建议先基础设施，再 auth、workflow，再业务服务和网关联调。

456. 问：Docker 部署要注意什么？
答：镜像环境变量、端口、网络、时区、日志目录、健康检查和依赖服务地址。Java 服务还要设置合适 JVM 参数。

457. 问：时区为什么重要？
答：排班、考勤、Token 过期、消息重试都依赖时间。服务器、数据库、JVM 和前端时区不一致会导致日期错位。

458. 问：为什么 current_date 和业务日期要区分？
答：系统当前时间用于审计和过期判断，业务日期用于排班和申请。用户补录或未来排班时，业务日期不等于当前日期。

459. 问：备份恢复要注意什么？
答：数据库和文件存储要一起备份，业务表和附件要能对应。只恢复数据库不恢复 OSS 文件，会导致附件丢失。

460. 问：日志保留策略怎么定？
答：按合规和排查需求确定，比如操作审计保留更久，普通应用日志保留较短。敏感日志要控制访问权限。

461. 问：你怎么向面试官介绍 CloudFlow 的架构？
答：我会说它是 Java 17 的 Spring Cloud 微服务，网关统一入口，auth 管认证和基础数据，workflow 管审批流，HR/OA 管业务，common 提供租户、权限、Redis、审计、限流等公共能力。

462. 问：你怎么讲一次 HR 审批完整链路？
答：用户在 HR 创建业务单据，Service 保存单据并通过 Feign 调 workflow 发起流程，workflow 创建实例和待办；审批完成后发回调，HR 按 businessType 找处理器更新单据状态。

463. 问：你怎么讲一次普通业务查询链路？
答：请求先过网关校验 Token，下游拦截器恢复 UserContext，MyBatis 插件自动加租户条件，DataScope 根据当前用户加数据权限，Mapper 查询后 Service 转 VO 返回。

464. 问：你怎么讲排班模块？
答：排班模块分班次、规则、规则适用范围和排班计划。班次定义时间和工时，规则定义制度，计划落到具体员工、岗位或部门日期上，发布后用于考勤统计。

465. 问：你怎么讲工作流扩展性？
答：审批人解析用 AssignUserStrategy，节点执行用 INodeHandler，回调用 ApprovalResultHandler。新增规则、节点或业务回调时主要加实现类，不改核心分发逻辑。

466. 问：你怎么讲系统安全设计？
答：入口用网关校验 Token，下游用 Sa-Token 恢复登录态，业务用角色权限和数据权限控制，租户插件隔离数据，敏感信息脱敏，关键操作记录审计日志。

467. 问：你怎么讲系统稳定性设计？
答：Feign 有 fallback，Redis 限流异常放行，本地消息表支持重试，定时任务加分布式锁，Actuator 和 Prometheus 做监控，关键异常写日志。

468. 问：你怎么讲系统可维护性？
答：多模块拆分清楚，common 沉淀公共能力，业务服务按 Controller-Service-Mapper 分层，工作流用策略和处理器扩展，根 POM 统一依赖版本。

469. 问：面试官问你项目难点，你怎么回答？
答：我会选 3 个真实难点：多租户和数据权限统一拦截、工作流和业务状态一致性、异步和定时任务里的上下文与幂等处理。

470. 问：面试官问你做过什么优化，你怎么回答？
答：可以讲减少重复查询、批量处理排班、抽出公共组件、用 Redis 做防重和限流、用本地消息表处理回调重试。回答要带具体场景和结果。

471. 问：面试官问你踩过什么坑，你怎么回答？
答：可以讲 ThreadLocal 在线程池丢上下文、selectById 忘记校验租户、Feign 没传 Token、流程回调重复到达、批量操作缺少范围限制。重点讲发现和修复方法。

472. 问：面试官问你怎么保证代码质量？
答：我会说先按项目分层和公共组件写，关键接口补参数校验、权限、事务和日志；提交前跑测试或至少走主要链路，代码评审重点看租户、权限、状态和异常。

473. 问：面试官问你怎么学习一个新模块？
答：先看 POM 和 application.yml 确认依赖，再看启动类和 Controller 找入口，然后看 Service 主流程和 Mapper SQL，最后结合数据库表理解状态流转。

474. 问：面试官问你为什么选择 MyBatis-Plus？
答：它能简化 CRUD、条件构造和分页，也方便接多租户、数据权限这类拦截器。复杂 SQL 仍可以用 XML 保持可控。

475. 问：面试官问你为什么不用单体？
答：CloudFlow 的认证、工作流、HR、OA 边界比较清楚，拆服务后团队和部署可以独立演进。代价是服务调用、配置、链路排查更复杂，所以 common 和网关要做好。

476. 问：面试官问你微服务缺点是什么？
答：缺点是部署复杂、调用链长、数据一致性难、排查成本高。项目用 Nacos、Feign fallback、本地消息表、监控和日志来降低这些成本。

477. 问：面试官问你如何处理跨服务事务？
答：我会先判断是否必须强一致。CloudFlow 里很多场景用本地消息表和重试保证最终一致，只有强一致要求很高时才考虑 Seata 这类分布式事务。

478. 问：面试官问你如何做权限模型？
答：用户绑定角色，角色绑定权限和菜单，登录时把角色、权限和数据范围放入登录态。接口执行时校验操作权限，查询时按数据权限过滤。

479. 问：面试官问你如何做多租户？
答：每张业务表带 tenant_id，请求入口恢复租户上下文，MyBatis 租户插件自动追加 tenant_id 条件。平台级接口通过受控方式跳过租户，并记录审计。

480. 问：面试官问你如何做数据权限？
答：登录时计算用户可访问部门和数据权限类型，查询时传 DataScope，MyBatis 拦截器把原 SQL 包装后追加用户或部门过滤。

481. 问：面试官问你如何做接口防刷？
答：登录、验证码和导出类接口加限流，按 IP 或用户维度生成 Redis Key，用 Lua 原子计数。核心提交接口再加防重复提交。

482. 问：面试官问你如何做审计？
答：关键修改方法加 @Audit，执行前取旧值，执行后比较新旧值，记录操作者、租户、业务对象、差异、IP 和时间。异步写入时要传递上下文。

483. 问：面试官问你如何做文件上传？
答：接口先校验登录和权限，再校验文件大小、类型和扩展名，存到本地或 OSS，数据库只保存文件元信息和访问地址。下载时再做权限校验。

484. 问：面试官问你如何做接口幂等？
答：入口可以用 Redis 防重复提交，业务层用唯一键、状态判断或处理记录保证重复请求不会重复落库。审批回调和流程发起都要重点考虑。

485. 问：面试官问你如何处理异常？
答：业务异常抛明确错误码和消息，系统异常记录堆栈并返回通用错误。ControllerAdvice 统一响应格式，事务方法让异常向外抛出触发回滚。

486. 问：面试官问你如何做日志？
答：关键链路打 info，失败打 error，非核心失败打 warn，带上 businessId、processInstanceId、tenantId 这类定位字段。敏感信息不能打。

487. 问：面试官问你如何设计缓存？
答：先确认数据是否读多写少，再设计 Key、过期时间、租户维度和失效策略。组织、字典、系统配置适合缓存，强实时数据要谨慎。

488. 问：面试官问你如何保证消息不丢？
答：先把消息落本地表并和业务事务一起提交，再由定时任务扫描处理，成功标记 SUCCESS，失败增加重试次数并记录原因，超过次数告警。

489. 问：面试官问你如何保证消息不重复处理？
答：用 messageId、businessType + businessId 或业务状态做幂等判断。重复消息来了，如果业务已经是最终状态，就直接返回成功。

490. 问：面试官问你如何做版本兼容？
答：接口字段新增要兼容旧调用方，数据库先加字段再启用，流程变量新增不能让旧流程解析失败。微服务多实例灰度时尤其要注意。

491. 问：面试官问你最熟哪个模块怎么答？
答：选一个能讲完整链路的模块，比如 HR 排班或工作流审批。按数据库表、接口入口、Service 规则、事务、权限、异常和联动服务讲。

492. 问：面试官问你在项目里承担什么角色怎么答？
答：可以说负责后端业务接口和公共能力接入，重点参与 HR 排班、审批联动、租户权限或日志审计。回答要落到具体文件、接口和问题。

493. 问：面试官问你如何和前端联调？
答：先用接口文档和 Postman 验证后端，再和前端确认字段、状态码、错误消息和枚举值。复杂页面按“列表、详情、新增、编辑、删除、状态流转”逐个对。

494. 问：面试官问你接口字段变更怎么处理？
答：新增字段优先保持向后兼容，旧字段不要马上删除；DTO、VO、前端类型、接口文档和数据库脚本一起改，避免只改一端。

495. 问：面试官问你如何处理线上问题？
答：先止血和确认影响范围，再用日志、指标和数据库定位根因，修复后补测试和复盘。不要线上直接大范围改配置或删数据。

496. 问：面试官问你如何做回滚？
答：代码回滚要确认数据库变更是否兼容，配置回滚要保留旧值，流程定义回滚要考虑已有实例。不能只回滚服务镜像。

497. 问：面试官问你如何看待代码重构？
答：重构要围绕明确问题，比如重复代码、扩展困难或风险高。先补测试或固定主链路，再小步改，避免把业务逻辑和重构混在一起。

498. 问：面试官问你如何提升可观测性？
答：增加关键日志、指标和告警，比如流程回调失败数、消息重试积压、接口错误率、慢 SQL 和线程池队列。问题要能从指标跳到日志和业务 ID。

499. 问：面试官问你下一步会怎么完善 CloudFlow？
答：我会先补流程回调幂等和告警，再优化排班列表 N+1 查询，然后给关键表补唯一约束和索引，最后完善测试覆盖。

500. 问：最后让你用一段话总结这个项目，你怎么说？
答：CloudFlow Pro 后端是一个围绕企业办公和人事流程的 Spring Cloud 微服务系统，核心是认证租户权限、HR/OA 业务和通用工作流。项目亮点在于把多租户、数据权限、限流、防重、审计、缓存和审批扩展做成公共能力，业务模块可以在统一规则下快速接入。

实施步骤问答

问：本地第一次启动怎么做？
答：准备 JDK 17、Maven、MySQL、Redis、Nacos，导入 cloudflow-backend/DB 下的 SQL，启动 Nacos 和 Redis，再按 gateway、auth、workflow、oa、hr 的顺序启动服务。

问：为什么建议先启动 auth 和 workflow？
答：auth 负责登录和用户上下文，workflow 被 HR/OA 审批调用；这两个服务正常后，业务服务联调更顺。

问：前后端联调先测什么？
答：先测登录拿 Token，再测带 Token 访问业务接口，然后测发起审批、完成审批、回调更新业务状态。

问：新增一个普通业务模块的步骤是什么？
答：建 Entity、DTO、VO、Mapper、Service、Controller，按租户字段和数据权限规范写查询，再补日志、异常、权限和必要的事务。

问：新增一个需要审批的 HR 业务怎么做？
答：先定义业务单据和状态，再通过 WorkflowServiceClient 发起流程，保存 processInstanceId，最后实现 ApprovalResultHandler 处理通过和驳回。

问：新增一个工作流节点怎么做？
答：实现 INodeHandler，写清 nodeType 和 handle 逻辑，注册为 Spring Bean，再在流程模型里使用对应节点类型。

问：新增一种审批人规则怎么做？
答：实现 AssignUserStrategy，supports 匹配 approverType，resolve 返回审批人 ID，resolveMultiple 返回会签审批人列表。

问：新增一个防重复提交接口怎么做？
答：在 Controller 方法上加 @RepeatSubmit，设置合理间隔，提交类接口一般可以从 1 秒到 5 秒开始。

问：新增一个限流接口怎么做？
答：在方法上加 @RateLimiter，按接口、IP 或用户维度配置 time 和 count，登录、验证码、导出这类接口更需要限流。

问：上线前要检查哪些配置？
答：检查 Nacos 地址、MySQL 地址、Redis 地址、Sa-Token 过期时间、服务名、网关路由、租户默认值、OSS 配置和 Prometheus 暴露配置。

注意事项问答

问：写业务查询时最容易漏什么？
答：最容易漏租户和数据权限，项目里优先用公共拦截器和 UserContext/TenantContext，特殊 SQL 要单独确认。

问：写事务时最容易犯什么错？
答：同类内部方法调用会绕过 Spring 代理，@Transactional 可能不生效；关键事务方法要由 Spring Bean 外部调用。

问：写异步任务时最容易漏什么？
答：最容易漏用户、租户和请求上下文传递，导致审计日志缺字段或查错租户数据。

问：写 Feign 调用时要注意什么？
答：服务名、路径、请求对象字段、Token 透传和 fallback 都要对齐，调用失败时要返回业务可理解的信息。

问：处理审批回调时要注意什么？
答：回调要校验租户、流程实例、业务类型、业务 ID 和审批结果，并保证同一个回调重复到达时不会重复改状态。

问：写批量操作时要注意什么？
答：要限制批量范围，提前校验目标是否存在，避免一次请求产生过多数据库写入或部分成功。

问：日志里最不能随便打印什么？
答：不能随便打印 Token、密码、身份证、手机号、密钥和完整附件地址。

问：数据库字段设计要注意什么？
答：多租户业务表要有 tenant_id，状态字段要有明确枚举，关联流程的表要能保存业务 ID、流程实例 ID 和状态。

问：缓存使用要注意什么？
答：Key 要带业务前缀和必要维度，过期时间要明确，涉及租户的数据要带 tenantId，避免不同租户互相读到缓存。

问：面试官追问“你负责哪块”时怎么回答？
答：可以选自己最熟的一条链路讲，比如 HR 排班、审批发起和回调、网关认证、租户数据隔离，按实际代码把入口、处理、存储和异常说清楚。
